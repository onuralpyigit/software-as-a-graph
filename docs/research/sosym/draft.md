# Software-as-a-Graph: An Open-Source Tool for Multi-Layer Graph Modeling, Quality Diagnosis, and Simulation-Verified Refactoring of Publish–Subscribe Architectures

> Generated from `latex/` with pandoc (`pandoc manuscript.tex -t gfm --citeproc`). The LaTeX is authoritative; do not edit this file.

## Abstract

Publish–subscribe middleware such as ROS 2/DDS, Kafka and MQTT decouples components through topics, brokers and Quality-of-Service contracts. That decoupling hides the dependencies along which failures propagate, and mainstream architecture modeling tools represent topics, brokers and QoS only indirectly. We present Software-as-a-Graph (SaG), an open-source tool for modeling and analysing publish–subscribe architectures. SaG's modeling language is a typed multigraph metamodel with six vertex and seven edge types, a JSON concrete syntax, four layer projections, and seven declared rules that derive component dependencies from declared structure. Over these models the tool computes an explainable Reliability–Maintainability quality model grounded in ISO/IEC 25010 and detects nineteen publish–subscribe anti-patterns. It gates changes in continuous integration against their merge-base with a waiver register, and it simulates failure cascades. Its refactoring engine compiles findings into three graph-mutation operators and admits a candidate edit only if its simulated benefit exceeds seed-to-seed noise at every propagation threshold. SaG has a hexagonal architecture with a Neo4j adapter for persistent exploration and an in-memory adapter for throw-away model copies, and its architectural invariants are enforced by about 1,600 tests. It is used through a command-line suite, a Python API, a REST service, a web application and self-contained HTML reports. We apply SaG to a running example, five architecture models of open-source systems and eight synthetic scenarios. Diagnosis and gating take 0.04–79 seconds per model. The delta-aware gate separates new findings from existing debt. 32% of rule-generated refactoring edits fail verification. We report eight lessons learnt, most traceable to defects we found: state on which model view a metric is meaningful, make unmeasured values unrepresentable, test transformation rules on the model at hand, and tie every reported number to the artefact that produced it. SaG is available under GPL-3.0.

**Keywords:** Architecture modeling; Graph metamodel; Publish–subscribe
middleware; Anti-pattern detection; Model refactoring; Simulation-based
verification; Quality gates; Tool paper.

# Introduction

Publish–subscribe (pub–sub) middleware such as ROS 2 over DDS, Apache
Kafka and MQTT is the communication substrate of a large share of
today’s robotics, autonomous-driving, IoT and event-driven microservice
systems (Wang et al. 2015; Pallickara, Bulut, and Fox 2007; Lee, Kang,
and Park 2025). Pub–sub decouples producers from consumers in space,
time and synchronisation: an application publishes to a named topic and
never refers to the applications that consume it. That decoupling is
what makes these systems easy to extend. It is also what makes them hard
to model. The dependencies that decide how a failure spreads (which
subscriber starves when a publisher stops, which applications share a
broker, which processes share a host) are not written down anywhere as
references. They are implied by the combination of topic names, broker
routing tables, deployment descriptors and Quality-of-Service (QoS)
contracts.

Existing modeling tools cover parts of this picture. Architecture
description languages and component models such as AADL (Feiler, Gluch,
and Hudak 2006) and the Palladio Component Model (Becker, Koziolek, and
Reussner 2009) support rich dependability and performance analyses, but
their connectors are oriented towards synchronous calls and buses;
topics, brokers and QoS contracts have no first-class representation.
Architecture-smell detectors such as Arcan (Fontana et al. 2017),
Designite (Sharma, Mishra, and Tiwari 2016) and DV8 (Cai and Kazman
2019) work on module and class dependency graphs recovered from source
code, where a pub–sub interaction is invisible. Code-quality platforms
such as SonarQube operate below the architecture altogether. An
architect who wants to ask “what breaks if this broker’s host fails,
which of my topics is a structural bottleneck, and would moving this
process to another host actually help?” has no single tool that
represents the system at the level where those questions are posed.

This paper presents **Software-as-a-Graph (SaG)**, an open-source tool
that fills this gap for pub–sub architectures. SaG imports a declarative
description of a system (applications, libraries, topics, brokers,
hosts, and optionally network devices, together with their QoS and code
metrics), represents it as a typed, attributed multigraph, derives the
implied component dependencies with seven explicit rules, and then runs
a pipeline of model analyses over that graph: structural quality scoring
grounded in ISO/IEC 25010, detection of nineteen pub–sub anti-patterns,
failure-cascade simulation, a delta-aware CI gate, and a refactoring
engine that proposes graph edits and admits only those whose benefit
survives counterfactual simulation. The tool is used through a
command-line suite, a Python API, a REST service, a web dashboard and a
self-contained HTML report.

## Why a tool, and for whom

The underlying ideas (graph models of pub–sub systems, centrality-based
criticality, simulation as an oracle) have been explored in our earlier
and companion papers
(Section <a href="#sec:intro:prior" data-reference-type="ref" data-reference="sec:intro:prior">1.3</a>).
What those papers do not provide, and what this paper is about, is an
engineered artefact that other people can install, apply to their own
systems, extend and build experiments on. We see four groups of users:

-   *Software and systems architects* who want to review a pub–sub
    design before it is deployed, see its cross-layer structure, and get
    a ranked, explained list of structural risks.

-   *Reliability engineers* who want a first estimate of the blast
    radius of a component or host failure without fault injection on a
    running system.

-   *DevOps teams* who want a pre-merge check that blocks a change only
    if it introduces a new structural problem.

-   *Modeling researchers* who want a metamodel, a scenario corpus, a
    simulation oracle and a set of baselines to evaluate their own
    metrics, detectors or model transformations against.

# Related Modeling and Analysis Tools

## Architecture description languages and component models

Model-driven engineering treats models as primary artefacts that drive
analysis and generation (Schmidt 2006; Combemale et al. 2016). AADL and
its OSATE tooling (Feiler, Gluch, and Hudak 2006) model software and
execution platforms for safety, latency and fault-tree analyses; the
Palladio Component Model (Becker, Koziolek, and Reussner 2009) and
PerOpteryx (Koziolek, Koziolek, and Reussner 2011) predict performance
and reliability of component-based systems and search design
alternatives. Both are mature and far richer than SaG in the analyses
they offer. Their connectors, however, model calls, ports and buses: a
topic that several anonymous publishers write to and several subscribers
read from, routed through a broker, governed by a DDS-style QoS
contract, has to be encoded indirectly. SaG trades breadth for this one
domain: topics, brokers and QoS are first-class, and the dependency
structure is derived from them rather than drawn by hand.

## Architecture-smell and anti-pattern detectors

Object-oriented anti-pattern catalogs (Brown et al. 1998; Fowler 1999;
Suryanarayana, Samarthyam, and Sharma 2014) and microservice smell
taxonomies (Taibi, Lenarduzzi, and Pahl 2020) gave names and detection
rules to recurring design flaws. At the architecture level, Arcan
(Fontana et al. 2017), Designite (Sharma, Mishra, and Tiwari 2016) and
DV8 (Cai and Kazman 2019) detect cyclic, hub-like and unstable
dependencies and architecture hotspots (Mo et al. 2015) from dependency
graphs recovered from code; surveys compare their results (Azadi,
Fontana, and Taibi 2019; Mumtaz, Singh, and Blincoe 2021). Several SaG
patterns are pub–sub counterparts of these (`CYCLE`, `HUB_AND_SPOKE`,
`UNSTABLE_INTERFACE`). The difference is the input: these tools have no
representation of topics, brokers or QoS, so a smell that exists only
through a topic (two applications coupled in both directions through two
topics, a publisher offering weaker reliability than its subscriber
needs) cannot be expressed. Performance anti-patterns (Smith and
Williams 2000, 2002; Trubiani et al. 2023; Pinciroli, Aleti, and
Trubiani 2023; Avritzer et al. 2025) and scalability-bug detectors
(Stuardo et al. 2019; Li et al. 2018) target latency and code-level
resource bottlenecks rather than structural failure propagation, and
static code-quality rules correlate only weakly with fault-proneness
(Lenarduzzi et al. 2020).

## Model refactoring and verification

Model refactoring is commonly expressed as graph transformation (Mens
and Van Gorp 2006), and search-based software engineering explores
architectural design spaces with multi-objective optimisers (Harman,
Mansouri, and Zhang 2012; Aleti et al. 2013; Deb et al. 2002);
PerOpteryx evaluates candidates by simulation inside the search loop
(Koziolek, Koziolek, and Reussner 2011). SaG’s refactoring engine is
deliberately simpler than either: three fixed operators compiled from
diagnosed findings, each candidate edit simulated on its own copy of the
model, and an edit kept only if its measured effect exceeds the
simulator’s seed-to-seed noise at every propagation threshold. The
engine does not search; it filters. What it adds to rule-based
refactoring is that no rule is trusted to improve the model by
construction.

## Quality models and centrality

ISO/IEC 25010 and 25019 define product-quality and quality-in-use
characteristics (ISO/IEC 2023a, 2023b). SaG’s RM model is an intrinsic
decomposition: every score is a declared weighted sum of named
structural terms, so its explanation is the formula itself rather than a
post-hoc attribution of an opaque predictor. Graph centralities are
widely applied to call and service graphs (Freeman 1977; Falci, Gomes,
and Parreiras 2018; Bakhtin et al. 2025). On the current release, the RM
composite out-ranks plain degree centrality on the application layer,
though it remains weak on infrastructure components at the system layer
(Section <a href="#sec:app:synthetic" data-reference-type="ref" data-reference="sec:app:synthetic">7.4</a>);
the tool therefore reports simple centralities alongside RM, and RM’s
primary value is the per-dimension explanation rather than a single
ranking score.

# The SaG Modeling Language

This section introduces the modeling language through a running example,
then defines its abstract syntax (metamodel), concrete syntax,
derivation rules and layer projections.

## Running example: mini-ATM

Mini-ATM is a fifteen-element air-traffic surveillance system that ships
with the tool and is used by all its walkthroughs
(`examples/mini_atm.json`). A *radar* application publishes raw plots on
topic `radar.plots`; a *tracker* fuses them and publishes `tracks`; a
*conflict-detector* consumes tracks and publishes `conflict.alerts`; a
*flight-plan* service publishes `flight.plans`; a *display* consumes
tracks, alerts and plans; a *recorder* archives plots, tracks and plans.
Tracker and conflict-detector share a library, *track-model*. Two
brokers route the topics; `tracks` is routed by both. Radar, tracker and
the sensor broker run on *sensor-host*; everything else runs on
*ops-host*; the two hosts are connected. Only `radar.plots` uses a
`BEST_EFFORT`, `VOLATILE` QoS contract.
Figure <a href="#fig:miniatm" data-reference-type="ref" data-reference="fig:miniatm">[fig:miniatm]</a>
shows the model.

The questions an architect would ask of this design are typical of the
domain: is the sensor host a single point of failure for the display? Is
`tracks`, consumed by three applications and routed by two brokers, a
bottleneck or a redundancy? Does the best-effort contract on
`radar.plots` matter, given who consumes it? The remainder of the paper
answers these with the tool.

## Abstract syntax: the metamodel

A SaG model is a typed, attributed, directed multigraph
*G* = (*V*, *E*, *τ*<sub>*V*</sub>, *τ*<sub>*E*</sub>, *w*<sub>*V*</sub>, *w*<sub>*E*</sub>),
with vertex types
*T*<sub>*V*</sub> = {`Application`, `Library`, `Topic`, `Broker`, `Node`, `NetworkDevice`}
and edge types
*T*<sub>*E*</sub> = {`PUBLISHES_TO`, `SUBSCRIBES_TO`, `ROUTES`, `RUNS_ON`, `USES`, `CONNECTS_TO`, `DEPENDS_ON`}.
The first six edge types are *structural*: they are declared in the
input. `DEPENDS_ON` is *derived*: it is computed from the structural
edges by the rules in
Section <a href="#sec:modeling:rules" data-reference-type="ref" data-reference="sec:modeling:rules">3.4</a>
and never accepted from the input.
Figure <a href="#fig:metamodel" data-reference-type="ref" data-reference="fig:metamodel">[fig:metamodel]</a>
shows the metamodel as a class diagram with the attributes the analyses
read.

#### Weights.

Topic weight combines a QoS score, normalised message size and
normalised rate,
*w*(*t*) = *β* *Q**o**S*(*t*) + *α* *s**i**z**e*(*t*) + *ψ* *f**r**e**q*(*t*);
the QoS score is a weighted sum of reliability, durability and transport
priority whose weights (0.24, 0.62, 0.14) are the priority vector of a
stated AHP pairwise-comparison matrix with consistency ratio below 0.10.
Component weights aggregate the weights of the topics a component
touches. Derived edges carry a weight computed by the rule that created
them (probabilistic union over mediating topics for Rules 1–2, worst
case for Rules 3, 4 and 7, harmonic mean or host weight for Rules 5–6).
All weight helpers are public functions in `saag/core/models.py`, and
the model walkthrough recomputes every weight of mini-ATM from them and
checks it against the repository.

## Concrete syntax

Models are written as JSON
(Listing <a href="#lst:json" data-reference-type="ref" data-reference="lst:json">[lst:json]</a>):
one array per vertex type and one per structural relation. The same
format is produced by the scenario generator from a short YAML
configuration (domain, scale, QoS mix, seed), by the real-world adapter
for the open-source models in
Section <a href="#sec:app:realworld" data-reference-type="ref" data-reference="sec:app:realworld">7.3</a>,
and by `saag-import`’s export; it can therefore be written by hand,
generated, or extracted from code by an external front end such as the
CodeQL extractor of Çalışkan, Yiğit, and Buzluca (2026).

```
{ "applications": [ {"id": "A1", "name": "radar", "app_type": "sensor", "criticality": "HIGH"}, ... ],
  "topics": [ {"id": "T1", "name": "radar.plots", "size": 512, "frequency": 20.0,
               "qos": {"reliability": "BEST_EFFORT", "durability": "VOLATILE",
                       "transport_priority": "MEDIUM", "deadline_ms": 200, "history_depth": 5}}, ... ],
  "brokers": [...], "nodes": [...], "libraries": [...],
  "relationships": {
     "publishes_to":  [{"from": "A1", "to": "T1"}, ...],
     "subscribes_to": [{"from": "A2", "to": "T1"}, ...],
     "routes": [{"from": "B1", "to": "T1"}, ...],   "runs_on": [{"from": "A1", "to": "N1"}, ...],
     "uses":   [{"from": "A2", "to": "L1"}, ...],   "connects_to": [{"from": "N1", "to": "N2"}] } }
```

## Derived dependencies

Pub–sub components do not reference each other, so the dependency
structure that failure analysis needs must be derived. SaG derives
`DEPENDS_ON` edges with the seven rules of
Table <a href="#tab:rules" data-reference-type="ref" data-reference="tab:rules">2</a>.
An edge *u* → *v* means **u* depends on *v**: if *v* fails, *u* is
affected, so failures propagate against edge direction.

<div id="tab:rules">

| **Rule**             | **Derived edge**       | **Structural pattern**                                                                 | **mini-ATM** |
|:---------------------|:-----------------------|:---------------------------------------------------------------------------------------|-------------:|
| 1 `app_to_app`       | subscriber → publisher | both touch topic *t* (also through `USES` chains of up to three libraries)             |            8 |
| 2 `app_to_broker`    | application → broker   | application publishes or subscribes to a topic the broker routes                       |           10 |
| 3 `node_to_node`     | host *B*→ host *A*     | an application on *B* depends on one on *A*, *A* ≠ *B*                                 |            2 |
| 4 `node_to_broker`   | host → broker          | an application on the host depends on the broker                                       |            4 |
| 5 `app_to_lib`       | component → library    | direct `USES`                                                                          |            2 |
| 6 `broker_to_broker` | broker ↔ broker        | both run on the same host                                                              |            0 |
| 7 `node_to_device`   | host → network device  | host *B* depends on host *A* and every network path from *B* to *A* crosses the device |            0 |

The seven `DEPENDS_ON` derivation rules. The last column gives the
number of edges each rule derives on mini-ATM (26 in total from 28
structural relations).

</div>

Rules 1–6 are implemented twice, as Cypher in the Neo4j adapter and in
Python in the in-memory adapter, and a third time inside the simulator,
which may not read derived edges
(Section <a href="#sec:arch:invariants" data-reference-type="ref" data-reference="sec:arch:invariants">5.4</a>).
Rule 7 is a separator test that Cypher cannot express, so all three call
one shared helper in `saag/core/network.py`. A regression test asserts
that the simulator’s derivation produces the same arc set as the
in-memory adapter on every corpus model; the remaining known divergence
between the two adapters (how Rule 1 weights a topic reachable both
directly and through a library) is documented rather than silently
tolerated.

## Layer projections

Analyses run on one of four projections of the derived graph, each
defined by the dependency subtypes it keeps and the vertex types it
reports on:

-   `app`: Rules 1 and 5; reports Applications and Libraries.

-   `infra`: Rules 3 and 7; reports Nodes and NetworkDevices.

-   `mw`: Rules 2, 4 and 6; reports Brokers.

-   `system`: all seven rules; reports every vertex type.

The layer is an explicit argument of every analysis command. This
matters because some metrics are only meaningful on some layers:

<div id="prop:substrate" class="proposition">

**Proposition 1** (Substrate adequacy). *A score term defined by a cut
predicate (articulation point, bridge) is constant on every vertex of a
layer projection that has no cut vertex (respectively no bridge). A
composite score that gives such a term weight *ω* then has at most
1 − *ω* of its range available to discriminate vertices on that
projection.*

</div>

The statement is elementary, but it had practical consequences for the
tool: the application projection of a pub–sub system is often densely
connected through shared topics and has few or no cut vertices, so the
Availability dimension of
Section <a href="#sec:analyses:rm" data-reference-type="ref" data-reference="sec:analyses:rm">4.1</a>
carries little signal there, while the `mw` and `system` projections,
where brokers and hosts mediate many paths, do contain cut structure.
This is why the layer is an explicit argument of every analysis rather
than a hidden setting
(Section <a href="#sec:lessons" data-reference-type="ref" data-reference="sec:lessons">8</a>,
Lesson 1).

# Model Analyses

SaG organises its analyses as pipeline steps over the model: *Model*
(import and derivation,
Section <a href="#sec:modeling" data-reference-type="ref" data-reference="sec:modeling">3</a>),
*Analyze* (structural metrics and RM scores), *Diagnose* (anti-patterns
and the quality gate), *Simulate* (failure cascades), *Validate*
(comparison of predictions with simulation), and *Prescribe* (verified
refactoring). Optional steps cover learned prediction, triage and
deployment planning
(Section <a href="#sec:analyses:more" data-reference-type="ref" data-reference="sec:analyses:more">4.6</a>).
Every step reads the model through the same repository port and writes
JSON results that the next step and the presentation layer consume.

## Structural quality: the RM model

For each vertex of the chosen layer projection, `Analyze` computes a
vector of structural metrics (reverse PageRank, in/out degree,
betweenness, clustering, directed articulation score, bridge ratio,
connectivity degradation, multi-path coupling, topic fan-out,
QoS-weighted degrees, path complexity) and a Code Quality Penalty
*C**Q**P*(*v*) that folds four code metrics (size, complexity, cohesion,
code-level instability) of applications and libraries into \[0, 1\].
These feed a three-level model grounded in ISO/IEC 25010
(Figure <a href="#fig:rm_hierarchy" data-reference-type="ref" data-reference="fig:rm_hierarchy">[fig:rm_hierarchy]</a>):
$$\\begin{aligned}
R(v) &= \\alpha\\,FT(v) + (1-\\alpha)\\,A(v), \\qquad \\alpha = 0.36, \\\\
Q(v) &= 0.80\\,R(v) + 0.20\\,M(v),\\end{aligned}$$
where Fault Tolerance *F**T* estimates cascade reach (dominated by
reverse PageRank and in-degree), Availability *A* estimates
single-point-of-failure exposure (articulation, bridge and
connectivity-degradation terms), and Maintainability *M* estimates
change cost (betweenness, efferent QoS weight, CQP, coupling balance).
The complete formulas are in
Appendix <a href="#app:formulas" data-reference-type="ref" data-reference="app:formulas">11</a>.
The weights are not tuned to any oracle: they are a declared
re-parameterisation of an earlier AHP weighting, and a test asserts the
algebraic relationship. Each vertex is classified into five levels with
box-plot fences over the layer’s score distribution, so classifications
are relative to the system under analysis.

What the tool offers here is less the scores than their decomposition.
Each component’s report lists the weighted terms that produced each
dimension, the dimension that dominates its criticality, and the role
that should look at it; a template-based explanation engine
(`saag/explanation/`) turns this into prose. A projection onto
ISO/IEC 25019 quality-in-use harms is available for presentation, but
because the projection matrix is row-stochastic it is algebraically a
reweighting of *Q*, and the tool and this paper do not treat it as a
separate score.

On mini-ATM at the system layer, the only component classified CRITICAL
is the topic `tracks` (*F**T* = 0.91): three applications subscribe to
it and two brokers route it. Three components follow as HIGH: the ops
host, the tracker and the flight-plan application. The first two lead,
for different reasons. The ops host is rated on reliability, because
most applications run on it. The tracker’s level comes from
Maintainability: its *M* = 0.72 is the highest in the model, because it
sits between the sensor and operations sides and uses the shared
library. A single scalar would rank the two side by side; the
decomposition says that one needs redundancy and the other needs
decoupling.

## Anti-pattern detection

The `AntiPatternDetector` implements the nineteen patterns of

the analysed graph. Thresholds are, wherever possible, relative: a value
is anomalous if it exceeds the box-plot fence
*Q*<sub>3</sub> + *k* *I**Q**R* of its layer’s distribution (*k* = 1.5
in the detector). This makes the catalog scale-free but also means it
can only flag what stands out *within* a system; a pattern such as
`BROKER_OVERLOAD` cannot fire when all brokers are equally overloaded.

pair, or the system as a whole.

Two of the patterns are specific to pub–sub semantics and have no
counterpart in code-level smell tools. `QOS_MISMATCH` flags a dependency
where the publisher offers a weaker contract than the subscriber
requests; in DDS this is not a degraded connection but no connection,
discovered only at run time. `CHATTY_PAIR` flags two applications that
depend on each other through two different topics: coupled as tightly as
a synchronous call, but hidden behind indirection. On mini-ATM, the
catalog reports six findings at the system layer: the display as a
`SPOF`, a `CYCLE` between the two hosts (each runs an application the
other depends on), and all four topics as `ISOLATED`. The last is a
false positive of the system projection: topics are scored by the RM
model but are not endpoints of any derivation rule, so they have no
`DEPENDS_ON` edges in the graph the detector inspects. We report it as
found rather than hide it, and return to it in
Section <a href="#sec:limitations" data-reference-type="ref" data-reference="sec:limitations">9</a>.
At the `mw` layer the catalog flags both brokers as single points of
failure and compound risks and two application–broker links as bridges,
which is the answer to the architect’s first question: each broker is
the only route for some of the topics it carries.

## Quality gate

`saag-diagnose` turns findings into a CI verdict: exit code 0 if nothing
is found, 1 if only MEDIUM findings exist, 2 if any CRITICAL or HIGH
finding exists (or a detector crashed). Applied as an absolute gate,
this blocks almost every realistic system on its existing debt
(Section <a href="#sec:app:ci" data-reference-type="ref" data-reference="sec:app:ci">7.5</a>).
The *delta-aware* mode (`–baseline`) instead compares the candidate
model’s findings with those of the merge-base, keyed by (pattern, entity
type, entity id), and blocks only on new CRITICAL/HIGH keys. Two
refinements came from applying it: a new finding whose metric is within
a fence margin (default 10%) of its threshold is downgraded to a
warning, because global metrics such as edge betweenness move on edges a
change never touched; and new `BOTTLENECK_EDGE` findings only warn in
delta mode. A YAML or JSON *waiver register* (`–waivers`) records
accepted risks with pattern, entity, reason, approver and expiry date;
expired waivers are reported and no longer applied.

## Failure simulation

The `Simulate` step provides the oracle that the other analyses are
checked against. `FailureSimulator` removes one component (or a pair, or
a sampled set) from the *structural* graph and propagates the failure
through publish, subscribe, routing and hosting relations, reporting the
impact *I*(*v*) as a weighted composite of reachability loss,
fragmentation, throughput loss and flow disruption. A separate
`FaultInjector` produces training labels for the learned predictor. The
two are kept apart by design and by test
(Section <a href="#sec:arch:invariants" data-reference-type="ref" data-reference="sec:arch:invariants">5.4</a>).
Message-flow and event-driven simulators, a runtime-rate sweep, and an
emulated CycloneDDS testbed that runs a model’s applications as real
processes with chaos injection are available for deeper studies.

## Verified refactoring

`Prescribe` compiles findings and criticality levels into candidate
edits drawn from three graph-mutation operators
(`saag/prescription/rules.py`):

1.  **Topic split** rewrites topic *t* into per-publisher sub-topics,
    re-pointing subscribers. It is proposed when *t* multiplexes several
    publishers into several subscribers, when *t* is critical and has
    several publishers, or when it feeds a component flagged by
    `GOD_COMPONENT`, `FAILURE_HUB`, `HUB_AND_SPOKE` or
    `BOTTLENECK_EDGE`.

2.  **Anti-affinity reallocation** moves every process but one off a
    host that runs several processes, when the host or one of its
    processes is a SPOF or classified critical.

3.  **QoS hardening** raises a topic to `RELIABLE` and non-volatile
    durability when the topic or one of its endpoints is critical.

The operators are rules, and rules can be wrong. Each candidate edit *δ*
is therefore applied alone to a fresh copy of the model, dependencies
are re-derived, and the exhaustive single-failure simulation is run at
propagation thresholds *Θ* = {0.1, 0.2, 0.5} and seeds
*S* = {42, 123, 456}. The edit is admitted only if its mean impact
reduction exceeds the seed-to-seed spread at every threshold,
$$\\overline{\\Delta I}\_\\theta(\\delta) &gt; \\kappa\\, \\sigma\_{\\text{seed},\\theta}(\\delta) \\quad \\forall \\theta \\in \\Theta, \\qquad \\kappa = 1.
\\label{eq:accept}$$
Admitted edits are then applied together and the combined model is
evaluated again; the tool reports the oracle-measured impact change of
the combined policy and a System Risk Index (SRI) change computed from
the RM dimensions. Because the SRI is computed from the same scores that
proposed the candidates, the tool reports it as a consistency check and
treats the simulated impact change as the outcome. Individually admitted
edits can interact: the combined policy can be worse than its parts, and
the report says so when it is
(Section <a href="#sec:app:synthetic" data-reference-type="ref" data-reference="sec:app:synthetic">7.4</a>).

## Further analyses

Three further analyses share the model and are described only briefly
because they are evaluated elsewhere. *Predict* trains heterogeneous
graph neural networks on simulation labels and is the subject of the
companion learning study. *Triage* intersects a ranking’s top-*K*
shortlist with the RM diagnosis to produce per-component root-cause
profiles, falling back to RM alone when no trained model exists.
*Deploy* (`saag-deploy`) plans the placement of applications on hosts
and network domains with a mixed-integer program and greedy baselines,
and grades placements only on held-out replica-aware simulation, never
on the proxy it optimises.

# Tool Architecture and Implementation

SaG is written in Python (about 65k lines in the core package `saag/`,
the CLI and the REST service) with a TypeScript/React front end (about
24k lines).
Figure <a href="#fig:hexagonal_arch" data-reference-type="ref" data-reference="fig:hexagonal_arch">[fig:hexagonal_arch]</a>
shows its structure.

## Hexagonal structure

The core follows a ports-and-adapters (hexagonal) layout (Martin 2003).
Domain services (`QualityAnalyzer` and `StructuralAnalyzer` for scoring,
`AntiPatternDetector`, `FailureSimulator` and `FaultInjector`,
`PrescribeService` with `EditVerifier`, the GNN models, the deployment
planner) depend only on the abstract port `IGraphRepository`
(`saag/core/ports/graph_repository.py`) and on plain data classes. One
use-case class per pipeline step (`ModelGraphUseCase`,
`AnalyzeGraphUseCase`, `DiagnosticUseCase`, `SimulateGraphUseCase`,
`ValidateGraphUseCase`, `PrescribeGraphUseCase`, `PredictGraphUseCase`,
`TriageUseCase`, `DeployGraphUseCase`, `VisualizeGraphUseCase`, and
others) forms the boundary that every front end calls. The front ends
are thin: the `Client` and fluent `Pipeline` facades of the Python API,
the CLI scripts, and the FastAPI service, whose routers delegate JSON
serialisation to presenter classes.

## Two repository adapters

`IGraphRepository` has two implementations, chosen for opposite
workloads.

`Neo4jRepository` stores the model in Neo4j through the official Bolt
driver and derives `DEPENDS_ON` edges with Cypher `MATCH`/`MERGE`
queries. It is what the web front end and the REST service use: the
model persists between sessions, and an analyst can open the Neo4j
browser and query the model directly.

`MemoryRepository` keeps the same model in plain Python dictionaries and
implements the same derivation rules in Python. It was first written as
a test double, so that the test suite could run without a database; it
became a production component when the refactoring engine needed to
create, mutate and simulate thousands of model copies. In `Prescribe`,
each candidate edit is applied to a deep copy of the model’s JSON,
loaded into a fresh `MemoryRepository`, its dependencies re-derived, and
the copy simulated; edits are verified in parallel worker processes.
Routing these copies through a database would have meant thousands of
create–derive–delete transactions per scenario. With the in-memory
adapter a copy is created and discarded within the worker that simulates
it, and no copy can contaminate another or the baseline (measurements in
Section <a href="#sec:app:synthetic" data-reference-type="ref" data-reference="sec:app:synthetic">7.4</a>).

Keeping several implementations of the derivation rules (Cypher, the
in-memory adapter, and the simulator’s own re-derivation) is the price
of this design, and they have drifted: the simulator once implemented
only one of the rules
(Section <a href="#sec:lessons" data-reference-type="ref" data-reference="sec:lessons">8</a>,
Lesson 2), and the two adapters still weight one Rule 1 corner case
differently, which is documented as a known divergence. The test suite
compares the simulator’s arc set with the in-memory adapter’s on the
whole corpus.

## Pipeline and data flow

The steps of
Section <a href="#sec:analyses" data-reference-type="ref" data-reference="sec:analyses">4</a>
communicate through the repository and through JSON artefacts on disk,
not through in-memory calls between services. `Simulate` writes its
impact scores to a file that `Predict` reads as training labels and
`Validate` reads as ground truth. This has two consequences: any step
can be rerun alone, and a result file can be inspected, versioned or
replaced by an external tool. To make files safe to exchange, artefacts
carry provenance: the reproduction scripts stamp each result with the
commit and a digest of the scenario corpus, and label files carry a
topology fingerprint that is checked before training.

## Invariants enforced by tests

A research tool that produces numbers for papers fails silently: a wrong
number looks exactly like a right one. Over time we turned the
properties the results depend on into tests that fail the build. The
suite has about 1,600 test functions in 130 files; a fast subset runs in
under fifteen seconds before every merge. The architectural invariants
are:

-   *Simulation never reads derived edges.* `saag/simulation/` operates
    only on structural edges, so that the oracle shares no computation
    with the scores it is used to check
    (`test_independence_guarantee.py`).

-   *Labeler and oracle are not interchangeable.* `FaultInjector`
    produces training labels, `FailureSimulator` produces validation
    ground truth, and neither may stand in for the other
    (`test_groundtruth_contract.py`).

-   *Predict does not import Simulate*; labels flow through files
    (`test_predict_simulate_separation.py`).

-   *The simulator’s re-derivation matches the repository’s* for all
    seven rules (`test_simulation_dependency_derivation.py`).

-   *An unmeasured quality gate is `None`, not 0.0* (validation model
    tests).

-   *A label file is checked before training*: wrong labeler, missing
    label, mismatched topology fingerprint or insufficient retest
    reliability are refused (`test_label_safety.py`).

-   *The committed corpus is exactly what its configurations generate*:
    every scenario regenerates byte-identically from its YAML file and
    matches a SHA-256 manifest (`test_scenario_corpus.py`).

-   *Declared weights stay consistent with their derivation*: the RM
    composite weights with the AHP vector they re-parameterise, and the
    topic-QoS weights with their pairwise-comparison matrix
    (`test_quality_model.py`, `test_ahp_shrinkage.py`).

-   *A refactoring is accepted only under
    Eq. <a href="#eq:accept" data-reference-type="eqref" data-reference="eq:accept">[eq:accept]</a>*
    at every threshold (`test_prescription.py`).

Most of these exist because the property was once violated;
Section <a href="#sec:lessons" data-reference-type="ref" data-reference="sec:lessons">8</a>
tells three of those stories.

# Using and Extending the Tool

The same pipeline is reachable from five front ends, each aimed at one
of the user groups of

## Command line

Installing the package (`pip install -e .`, Python ≥ 3.10) provides ten
console scripts. `saag` runs the whole pipeline or selected steps
through flags; the others run one step each:

    saag --all --layer system                            # every step on the imported model
    saag-import   --input examples/mini_atm.json --clear # Model: import and derive DEPENDS_ON
    saag-analyze  --layer mw                             # Analyze: metrics and RM scores
    saag-diagnose --layer system                         # Diagnose: catalog + gate, exit 0/1/2
    saag-diagnose --layer system --baseline merge_base.json --waivers waivers.yaml  # delta gate
    saag-simulate fault-inject --input examples/mini_atm.json --export-json   # Simulate
    saag-visualize --layer system --output output/dashboard.html             # HTML report
    python cli/prescribe_graph.py --layer system         # Prescribe: verified refactoring

Further scripts cover generation of synthetic scenarios from YAML
(`saag-generate`), validation (`saag-validate`), learned prediction
(`saag-predict`, `cli/train_graph.py`) and deployment planning
(`saag-deploy`). The step scripts operate on the model stored in Neo4j
(connection settings via flags or environment variables). Every script
writes JSON, so its output can be consumed by other tools; the baseline
of the delta-aware gate is simply the merge-base’s `saag-diagnose`
output, and `saag-diagnose`’s exit code is the CI verdict.

## Python API

Researchers use the package directly. `saag.Pipeline` is a fluent
builder whose steps run in dependency order; passing a
`MemoryRepository` removes the need for Neo4j:

``` python
import saag
from saag.infrastructure.memory_repo import MemoryRepository

result = (saag.Pipeline.from_json("examples/mini_atm.json", clear=True,
                                  repo=MemoryRepository())
            .analyze(layer="system")
            .simulate(layer="system", mode="exhaustive")
            .diagnose(k=5)
            .validate()
            .prescribe()
            .visualize(output="output/mini_atm.html")
            .run())
print(result.prescription.sri_improvement)
```

For step-by-step control, `saag.Client` exposes one method per step
(`import_topology`, `analyze`, `diagnose`, `detect_antipatterns`,
`simulate`, `validate`, `prescribe`, `deploy`, …). All examples and
walkthroughs in the repository use this API.

## Extension points

The hexagonal structure determines where extensions go:

-   *A new anti-pattern* is a `PatternSpec` entry in `CATALOG`
    (`saag/analysis/antipattern_detector.py`) plus a detection method
    registered in the detector’s dispatch table; the method receives the
    analysed layer and its metric statistics and returns findings. The
    delta gate, reports and API pick it up without change.

-   *A new storage back end* implements `IGraphRepository`, including
    the derivation rules; the simulator’s derivation test then checks it
    against the in-memory reference.

-   *A new refactoring operator* adds a candidate type to
    `PrescriptionPolicy`, a compilation rule in
    `saag/prescription/rules.py` and a model mutation in
    `saag/prescription/mutator.py`; the verifier is operator-agnostic
    and applies
    Eq. <a href="#eq:accept" data-reference-type="eqref" data-reference="eq:accept">[eq:accept]</a>
    to it unchanged.

-   *A new input source* only has to emit the JSON format of
    Listing <a href="#lst:json" data-reference-type="ref" data-reference="lst:json">[lst:json]</a>;
    the real-world adapter (`saag/adapters/realworld_adapter.py`) is an
    example.

-   *A new metric or score* is added to the structural analyzer and
    declared in the metric registry (`saag/core/metric_registry.py`),
    which records for every metric whether it feeds scoring, detection,
    the GNN features, or only reports.

#### Agreement with the oracle.

The tool’s validation step compares any ranking with the simulated
impact. At the `app` layer, the RM composite *Q*(*v*) reaches a mean
Spearman *ρ* of 0.62 with the oracle, against 0.50 for betweenness and
0.49 for degree centrality; *Q* is higher than degree in 8 of 8
scenarios (Wilcoxon signed-rank *p* = 0.008). At the `system` layer,
where components of different types are pooled, the figures must be read
per type: 0.64 for applications, 0.21 for hosts and 0.12 for brokers;
the RM model is therefore informative for applications and weak for
infrastructure components. As Lesson 5 recounts, these figures differ
from those our earlier drafts reported on a previous corpus and
simulator version. The catalog is a sensitive but imprecise screen on
synthetic models: it implicates 94% of components with recall 0.90 and
precision 0.24, largely because edge-scoped findings (`BOTTLENECK_EDGE`,
`QOS_MISMATCH`) implicate both endpoints.

## CI scenario

#### A change to mini-ATM.

Suppose the display starts publishing operator commands on a new topic
that the tracker and conflict-detector consume, a plausible feature that
closes a feedback loop. The absolute gate blocks both before and after
the change (exit 2), so it cannot tell the reviewer anything about the
change. The delta-aware gate compares 6 findings on the merge-base with
13 on the candidate: it carries the 6 pre-existing findings silently,
blocks on 3 new ones (the tracker and recorder becoming single points of
failure, and a new dependency cycle through tracker, conflict-detector
and display), and reports 4 new findings as warnings (three new
bottleneck edges and the new topic). Waiving one blocking finding in the
register leaves the other blocking findings in force; the waiver is
recorded with its approver and expiry.

#### Random edits on the corpus.

To see how the two modes behave on routine changes, we applied 10 random
single-subscription additions to each model under 150 components and
gated each change both ways
(Table <a href="#tab:ci" data-reference-type="ref" data-reference="tab:ci">8</a>);
`DEEP_PIPELINE`, whose path enumeration does not terminate on the larger
models, was disabled for this experiment as for the others. The absolute
gate returns exit 2 for 100% of changes, because the models already
contain HIGH findings; the delta-aware gate blocks 26%, warns on 47% and
passes 28%. The delta-aware blocks all fall on the open-source models
(23 of their 50 changes); on the synthetic models, which carry 39 to
1,993 findings before the change, no change is blocked, plausibly
because an added subscription rarely creates a finding of a kind not
already present there. A blocking verdict in delta mode names the new
findings that caused it, which is the information a reviewer needs.

# Importance for the Community and Lessons Learnt

## Why the tool matters

#### A modeling language for an under-served architectural style.

Pub–sub middleware underlies much of robotics, automotive, IoT and
event-driven cloud software, yet mainstream architecture modeling tools
represent its central elements (topics, brokers, QoS contracts) only
indirectly. SaG offers a small, explicit metamodel for this style, a
concrete syntax that can be written, generated or extracted, and
declared rules that turn declared structure into the dependency
structure analyses need. The rules, the catalog and the operators are
specified in enough detail (and covered by enough tests) to be
re-implemented in other modeling environments, for example as an Ecore
metamodel with Henshin rules.

#### An experimental platform with an oracle.

Architecture-analysis research is often evaluated on a handful of
private systems with no shared ground truth. SaG ships a generator, a
corpus whose files are guaranteed to regenerate from their
configurations, five models of open-source systems, two independent
failure simulators, a validation step that compares any ranking against
them, and a reproduction package. A researcher with a new metric,
detector or refactoring rule can evaluate it against the same oracle and
baselines in an afternoon.

#### Verification as part of model transformation.

The refactoring engine treats every transformation rule as a hypothesis
to be tested on the model at hand. In our measurements a substantial
share of rule-generated edits fails that test
(Section <a href="#sec:app:synthetic" data-reference-type="ref" data-reference="sec:app:synthetic">7.4</a>).
The pattern (generate candidates by rule, accept them by simulation
against a noise margin) is independent of pub–sub and applies wherever a
model can be simulated.

#### Evidence for practitioners.

The CI gate, waiver register and self-contained report bring
architecture-level checks into the place where design changes are
actually reviewed, the pull request, without asking a team to adopt a
modeling IDE.

## Lessons learnt

We report the lessons that we think transfer beyond this tool. Most
began as a defect.

#### Lesson 1 (designing): state on which model view a metric is meaningful.

Our first design computed the whole RM composite on the application
projection, because that is where architects look. The Availability
dimension, 64% of Reliability, is built from cut-vertex and bridge
predicates, and the application projection of a pub–sub system rarely
has cut vertices: topics shared by several applications provide
alternative paths. On the current corpus the `SPOF` detector predicts 7
of 8 scenarios to have no articulation point at all on the `app` layer,
and its mean *F*<sub>1</sub> there is 0.01. Nothing was wrong with the
code; the metric was being evaluated on a view where it is constant
(Proposition <a href="#prop:substrate" data-reference-type="ref" data-reference="prop:substrate">Proposition 1</a>).
*Transferable lesson:* in a multi-view modeling tool, the view a metric
is computed on is part of the metric’s definition and belongs in its
specification, not in a default.

#### Lesson 2 (testing): make “not measured” unrepresentable as a value.

For a long period the simulator’s re-derivation of `DEPENDS_ON`
implemented only Rule 1. The rules it lacked are precisely those that
give applications, brokers and hosts any dependents, so the
maintainability-impact oracle was identically 0.0 for every component
the validation scored. Nothing crashed. The validation step then
evaluated quality gates with a default of 0.0 for missing metrics, so
two gates that had never been measured were reported as *failures*, and
the result looked like an ordinary negative finding. We fixed both
causes and added two safeguards: gates now return `None` when
unmeasured, and a test asserts that the simulator derives exactly the
same arc set as the repository. *Transferable lesson:* in analysis
tools, a missing value silently coerced to zero is indistinguishable
from a measurement; give absence its own representation and test that
the oracle is alive, not only that it runs.

#### Lesson 3 (building): a test double can become the most important adapter.

`MemoryRepository` was written so that tests would not need Neo4j. When
the refactoring engine needed to create, mutate and simulate thousands
of model copies, the test double, already behind the same port as the
database, became the production sandbox: each copy is a deep copy of the
JSON model with dependencies re-derived from scratch, so an edit that
renames a topic cannot leave stale derived edges behind, and copies
cannot leak into each other. The cost is that the derivation rules now
exist in several implementations that can drift (Lesson 2 is one
instance), so they must be tested against each other. *Transferable
lesson:* a ports-and-adapters design pays off most for the adapter you
did not plan; budget for cross-implementation tests from the start.

#### Lesson 4 (testing): never trust a transformation rule on the model at hand.

Each refactoring operator encodes a plausible design heuristic (split a
congested topic, separate co-located critical processes, harden a
critical channel). Simulated on the corpus, 32% of the 1,510
rule-generated edits fail the acceptance test of
Eq. <a href="#eq:accept" data-reference-type="eqref" data-reference="eq:accept">[eq:accept]</a>:
their effect is within seed noise or harmful. Survival differs by
operator, from 55% for topic splits to 72% for reallocations
(Table <a href="#tab:operators" data-reference-type="ref" data-reference="tab:operators">7</a>),
and in 3 of 7 scenarios the combination of individually admitted edits
is worse than the baseline. *Transferable lesson:* rule-based model
refactoring should treat each rule application as a hypothesis, test it
on the model, and test the composition separately from the parts.

#### Lesson 5 (evaluating): conclusions expire with the artefacts that produced them.

Results in SaG are files produced by scripts from a generated corpus.
Twice before, a number could not be reproduced: once because a stale
cache of derived features silently took precedence over regenerated
datasets, once because a script computed a composite oracle without one
of its four criteria. We added a test that every committed scenario
regenerates byte-identically from its configuration and matches a
SHA-256 manifest, and a provenance stamp (commit, corpus digest,
configuration) on every result. The safeguard proved its worth while
writing this paper: re-running the evaluation on the current release,
after the corpus had been regenerated and the simulator fixed
(Lesson 2), reversed one of our earlier conclusions. Earlier drafts
reported that the RM composite ranked failure impact no better than
degree centrality; on the current release it ranks better in all eight
scenarios
(Section <a href="#sec:app:synthetic" data-reference-type="ref" data-reference="sec:app:synthetic">7.4</a>).
*Transferable lesson:* for a tool that is also a research instrument,
tie every reported number to the exact artefact and version that
produced it, and expect to re-measure after fixing the instrument.

#### Lesson 6 (designing): a gate that blocks everything is not a gate.

Relative box-plot thresholds make the catalog scale-free, but every
system has outliers, so an absolute gate blocks every realistic model on
existing debt
(Section <a href="#sec:app:ci" data-reference-type="ref" data-reference="sec:app:ci">7.5</a>)
and would be switched off within a week. A plain diff of findings
against the merge-base was not enough either: global metrics such as
edge betweenness move on edges a change never touched, and on the corpus
a key diff still blocked 40–100% of single-element edits, nearly all
through `BOTTLENECK_EDGE` findings that had sat within 10% of the fence.
Hence the fence margin, the warn-only treatment of that pattern in delta
mode, and the waiver register with expiry dates. A related scalability
lesson came from `DEEP_PIPELINE`: enumerating every source-to-sink path
reported 746 findings on a ten-application model and did not terminate
within minutes even on a 124-component model, so it is excluded from the
prescriptive runs and from every experiment in
Section <a href="#sec:application" data-reference-type="ref" data-reference="sec:application">7</a>.
*Transferable lesson:* design a model-based check for the decision it
feeds (here, “should this change merge?”), including its false-alarm
rate and cost, not only for its detection logic.

#### Lesson 7 (disseminating): executable walkthroughs are documentation that tests itself.

We wrote the nine walkthroughs to explain the tool. Because each
generates its page from the tool’s real output, and several recompute
what they show from public helpers, writing them found discrepancies no
unit test had: the documentation stated a level fence of
*Q*<sub>3</sub> + 1.5 *I**Q**R* while the analyzer ships 0.75; one
component was flagged as a directed cut vertex while its continuous
cut-vertex score was 0.0; a bootstrap confidence bound varied with
Python’s hash seed. *Transferable lesson:* documentation generated from
running the tool on a small, fully understood model catches a class of
drift between code, documentation and intent that tests written by the
same developers do not.

#### Lesson 8 (building): keep the model a multigraph end to end.

The metamodel is a multigraph, but one consumer built its working graph
as a simple directed graph, in which an application that both publishes
and subscribes to the same topic yields one edge, not two. On the ATM
scenario 14 such pairs collapse, and every feature computed on that
graph is affected. The defect is documented and guarded, but fixing it
changes published numbers, so it is scheduled rather than patched in
passing. *Transferable lesson:* when a metamodel’s semantics depend on
parallel typed edges, check that every library data structure the tool
hands the model to preserves them.

# Limitations, Threats to Validity, and Availability

## Limitations of the tool

-   *Input.* SaG analyses a declared model. Its results are only as good
    as that model, and the tool does not yet extract models from ROS 2
    launch files, DDS XML profiles or Kafka configurations; the CodeQL
    extractor of Çalışkan, Yiğit, and Buzluca (2026) is a separate front
    end.

-   *Structure, not behaviour.* The RM model and the catalog are
    structural. Load, timing and queueing enter only through QoS-derived
    weights and the optional message-flow simulator; `BROKER_OVERLOAD`
    is relative to peer brokers, not to capacity.

-   *Known false positives.* At the `system` layer every topic is
    reported as `ISOLATED`, because topics are not endpoints of derived
    dependencies
    (Section <a href="#sec:analyses:catalog" data-reference-type="ref" data-reference="sec:analyses:catalog">4.2</a>);
    edge-scoped findings implicate both endpoints, which makes the
    catalog sensitive but imprecise
    (Section <a href="#sec:app:synthetic" data-reference-type="ref" data-reference="sec:app:synthetic">7.4</a>).

-   *Refactoring.* The three operators are fixed and greedy; the engine
    admits edits individually and does not search for the best subset,
    so the combined policy can regress (Lesson 4).

-   *Front ends.* The step CLIs require Neo4j (the Python API and the
    reproduction scripts do not); the web application offers a 2D graph
    explorer only; the REST service does not yet expose the diagnose,
    prescribe and deploy steps.

-   *Packaging.* The prescribe CLI imports a helper from the
    reproduction package, which is not part of the installable
    distribution; it works from a source checkout.

## Threats to validity of the application study

*Construct validity.* Agreement is measured against SaG’s own failure
simulator. The simulator operates on structural edges only and shares no
code path with the scores (an invariant enforced by test), but it is
still a model of failure propagation, not observed failures. The SRI
used by the whole-policy check is computed from RM dimensions and is
therefore reported only as a consistency check. *External validity.* The
synthetic scenarios come from our generator, and the five open-source
systems are hand-authored architecture models *modelled after* the
projects’ documentation, not extracted from their code; they are not
production deployments. We have no user study; the interface design
rationale in
Section <a href="#sec:usage" data-reference-type="ref" data-reference="sec:usage">6</a>
is a design argument, not measured usability. *Conclusion validity.*
With eight scenarios, per-scenario statistics have wide uncertainty, and
we report descriptive results and one paired test only.
*Reproducibility.* Timings were measured on one 20-core workstation and
depend on hardware.

# Conclusion and Future Work

We presented Software-as-a-Graph, an open-source tool for modeling
publish–subscribe architectures as typed multigraphs and analysing them:
deriving the dependency structure that pub–sub hides, scoring components
with an explainable Reliability–Maintainability model, detecting
nineteen pub–sub anti-patterns, gating changes in CI against their
merge-base, simulating failure cascades, and proposing refactorings that
are admitted only if their benefit survives counterfactual simulation.
The tool is built around a hexagonal core with a persistent and an
in-memory model repository, is used through a CLI, a Python API, a REST
service, a web application and self-contained reports, and protects its
results with invariants enforced by about 1,600 tests.

Applied to a running example, five models of open-source systems and a
synthetic corpus, the tool produces explained diagnoses within seconds
for models of a few hundred elements, a delta-aware gate that separates
new from existing findings, and verified refactoring policies in which a
substantial share of rule-generated edits is rejected. The lessons we
draw are mostly about trust in a modeling tool: state the view on which
a metric is meaningful, make unmeasured values unrepresentable, test
transformation rules on the model at hand, and tie every number to the
artefact that produced it.

Future work follows from the limitations: model extraction from ROS 2,
DDS and Kafka configuration; layer-aware Availability that selects the
projection on which cut structure exists; subset selection for
refactoring policies instead of greedy composition; an Ecore/EMF export
so that the metamodel and rules can be used from model-driven tool
chains; exposing the diagnose and prescribe steps in the REST service;
and a study with practitioners of how the reports and gate are used in
review.

# RM Model Formulas

This appendix lists the formulas implemented by `QualityAnalyzer` and
`StructuralAnalyzer` (`saag/analysis/`) with their shipped default
weights (`saag/analysis/weight_calculator.py`). They are reproduced so
that the model can be re-implemented; their validation is not the
subject of this paper.

#### Code Quality Penalty.

For Applications and Libraries, four code metrics are min–max normalised
within each component type (a zero-variance population maps to 0, so
missing data is not penalised as worst-case debt). With
instability\_code(*v*) = *C*<sub>*e*</sub>(*v*)/(*C*<sub>*a*</sub>(*v*) + *C*<sub>*e*</sub>(*v*)):
*C**Q**P*(*v*) = 0.10 loc<sub>norm</sub>(*v*) + 0.35 complexity<sub>norm</sub>(*v*) + 0.30 instability\_code(*v*) + 0.25 lcom<sub>norm</sub>(*v*).

#### Structural inputs.

Let *ε* = 10<sup> − 9</sup>. The model computes the following structural
metrics on *G*<sub>*l*</sub>:

-   *R**P**R*(*v*): PageRank on the transposed graph
    *G*<sub>*l*</sub><sup>T</sup>, rank-normalized over the population.
    Because `DEPENDS_ON` edges point dependent → dependency, failure
    propagates *against* edge direction; reverse PageRank is thus the
    true cascade-reach estimator.

-   *D**G*<sub>in</sub>(*v*) = deg<sup>−</sup>(*v*)/(\|*V*<sub>*l*</sub>\| − 1)
    and
    *D**G*<sub>out</sub>(*v*) = deg<sup>+</sup>(*v*)/(\|*V*<sub>*l*</sub>\| − 1).

-   **Multi-Path Coupling Index:**
    *M**P**C**I*(*v*) = ∑<sub>*e* ∈ *I**n*(*v*)</sub>max (*p**a**t**h**s*(*e*) − 1, 0) / (\|*V*<sub>*l*</sub>\| − 1),
    where *p**a**t**h**s*(*e*) counts distinct pub–sub channels
    realizing dependency *e*.

-   **Fan-Out Criticality** (Topic vertices):
    *F**O**C*(*t*) = ln (1 + *f*(*t*)) *s*(*t*) / max<sub>*t*′</sub>\[ln (1 + *f*(*t*′)) *s*(*t*′)\],
    for publication frequency *f*(*t*) in Hz and subscriber count
    *s*(*t*).

-   **Directed Articulation Score:**
    *A**P*<sub>*c*, directed</sub>(*v*) = max (*A**P*<sub>*c*</sub><sup>out</sup>(*v*), *A**P*<sub>*c*</sub><sup>in</sup>(*v*)),
    where
    *A**P*<sub>*c*</sub><sup>out</sup>(*v*) = 1 − *L*(*G*<sub>*l*</sub> \\ {*v*})/(\|*V*<sub>*l*</sub>\| − 1)
    and *L*(*H*) is the order of the largest connected component of *H*.

-   **Bridge Ratio:**
    *B**R*(*v*) = \|{*e* ∈ *b**r**i**d**g**e**s*(*G*<sub>*l*</sub><sup>und</sup>) : *v* ∈ *e*}\|/deg<sup>und</sup>(*v*).

-   **Connectivity Degradation Index:**
    *C**D**I*(*v*) = min  (\[*d̄*(*G*<sub>*l*</sub> \\ {*v*}) − *d̄*(*G*<sub>*l*</sub>)\]/*d̄*(*G*<sub>*l*</sub>), 1),
    for *d̄* the average shortest-path length over reachable pairs.

-   *B**T*(*v*): betweenness centrality; *C**C*(*v*): clustering
    coefficient; *P**C*(*v*): normalized path complexity; *w*(*v*):
    normalized QoS component weight; *w*<sub>out</sub>(*v*): normalized
    summed efferent QoS weight.

#### Quality dimensions.

1.  **Fault Tolerance (*F**T*).** Estimates cascade reach. For
    Application, Library, Broker, and Node vertices, an enhanced
    cascade-depth potential *C**D**P**o**t* discounts vertices that
    forward more than they absorb, amplified by multi-path coupling:
    $$\\begin{aligned}
        \\mathrm{CDPot}\_{\\text{base}}(v) &= \\frac{\\mathrm{RPR}(v) + \\mathrm{DG}\_{\\text{in}}(v)}{2}\\left(1 - \\min\\!\\left(\\frac{\\deg^{+}(v)}{\\max(\\deg^{-}(v),\\varepsilon)},\\, 1\\right)\\right) \\\\
        \\mathrm{CDPot}(v) &= \\min\\!\\big(\\mathrm{CDPot}\_{\\text{base}}(v)\\,(1 + \\mathrm{MPCI}(v)),\\; 1\\big) \\\\
        FT(v) &= 0.45\\,\\mathrm{RPR}(v) + 0.30\\,\\mathrm{DG}\_{\\text{in}}(v) + 0.25\\,\\mathrm{CDPot}(v)
        \\end{aligned}$$
    For Topic vertices, the blast surface is the subscriber set
    moderated by publisher redundancy:
    *F**T*<sub>topic</sub>(*t*) = 0.50 *F**O**C*(*t*) + 0.50 *F**O**C*(*t*)(1 − min (*w*<sub>in</sub>(*t*), 1))

2.  **Availability (*A*).** Evaluates single-point-of-failure exposure.
    The interaction term
    *Q**S**P**O**F*(*v*) = *A**P*<sub>*c*, directed</sub>(*v*) ⋅ *w*(*v*)
    deliberately incorporates QoS weight so structural SPOF risk is not
    masked at low weight:
    $$\\begin{aligned}
        A(v) = & \\; 0.25\\,\\mathrm{AP}\_{c,\\text{directed}}(v) + 0.20\\,\\mathrm{QSPOF}(v) \\\\
               & + 0.20\\,\\mathrm{BR}(v) + 0.25\\,\\mathrm{CDI}(v) + 0.10\\,w(v)
        \\end{aligned}$$

3.  **Maintainability (*M*).** Blends betweenness, efferent QoS
    out-degree, CQP, coupling risk, and inverse clustering. With
    *ι*(*v*) = deg<sup>+</sup>(*v*)/(deg<sup>−</sup>(*v*) + deg<sup>+</sup>(*v*) + *ε*):
    $$\\begin{aligned}
        \\mathrm{CouplingRisk\\\_enh}(v) &= \\min\\!\\big(1,\\; \\big\[1 - \|2\\iota(v) - 1\|\\big\]\\,(1 + 0.10\\,\\mathrm{PC}(v))\\big) \\\\
        M(v) = & \\; 0.35\\,\\mathrm{BT}(v) + 0.30\\,w\_{\\text{out}}(v) + 0.15\\,\\mathrm{CQP}(v) \\\\
               & + 0.12\\,\\mathrm{CouplingRisk\\\_enh}(v) + 0.08\\,(1-\\mathrm{CC}(v))
        \\end{aligned}$$

4.  **Reliability Composite (*R*).** Blends Fault Tolerance and
    Availability with *α* = 0.36:
    *R*(*v*) = *α* ⋅ *F**T*(*v*) + (1 − *α*) ⋅ *A*(*v*)

#### Composite and quality-in-use projection.

*Q*(*v*) = 0.80 *R*(*v*) + 0.20 *M*(*v*). The diagnostic vector
**s**<sub>RM</sub>(*v*) = \[*R*(*v*), *M*(*v*)\]<sup>*T*</sup> projects
into ISO/IEC 25019 Quality-in-Use stakeholder harm scores
\[*H*<sub>Ben</sub>, *H*<sub>Risk</sub>, *H*<sub>Acc</sub>\]<sup>*T*</sup>
via transformation matrix **M**<sub>RM → QiU</sub>:
$$\\mathbf{h}\_{\\text{QiU}}(v) = \\mathbf{M}\_{\\text{RM} \\to \\text{QiU}} \\cdot \\mathbf{s}\_{\\text{RM}}(v) = \\begin{bmatrix} 0.75 & 0.25 \\\\ 0.80 & 0.20 \\\\ 0.60 & 0.40 \\end{bmatrix} \\begin{bmatrix} R(v) \\\\ M(v) \\end{bmatrix}$$
**M**<sub>RM → QiU</sub> is row-stochastic, providing a declared
re-presentation of RM in stakeholder-facing terms for routing findings
to responsible engineering roles. Components are classified into five
levels (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `MINIMAL`) by box-plot
fences over the layer’s *Q* distribution: `CRITICAL` above
*Q*<sub>3</sub> + *k* *I**Q**R* with the shipped *k* = 0.75, `HIGH`
above *Q*<sub>3</sub>, `MEDIUM` above the median, `LOW` above
*Q*<sub>1</sub>; below twelve components fixed percentiles are used
instead.
