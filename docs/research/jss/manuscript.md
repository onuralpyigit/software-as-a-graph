# Abstract

Publish–subscribe middleware obscures how failures propagate, yet architects must identify critical components before deployment, without telemetry. We present Software-as-a-Graph (SaG), which derives explicit dependency graphs from deployment manifests to investigate when graph learning improves cascade-impact ranking. We compare graph neural networks, hybrids, and analytical and learned simulator approximations on twelve synthetic architectures under leave-one-scenario-out evaluation against three failure simulators, and zero-shot on five hand-authored models of open-source systems. A reference criterion distinguishes rankings that restate a simulator’s propagation rule from those that predict it.

On a reachability simulator, graph attention on the derived dependency graph reaches Spearman’s $\rho = 0.748$, $+0.072$ above the same model with reverse edges on the raw multigraph, whereas on the raw multigraph the registered primary contrast against a training-free baseline was null. It is not distinguishable from counting direct dependents ($\rho = 0.764$), and its gain survives removing input features that compute part of the simulator. For a queue-flow simulator requiring $12.7$ CPU-hours to label the corpus, a rate-weighted first-order approximation reaches $\rho = 0.830$ in milliseconds, matching or exceeding a learned approximation trained on simulator labels ($\rho = 0.799$; exploratory). Learners that start from that approximation do not improve on it. Learned models transfer zero-shot better than the training-free baseline ($\rho \approx 0.81$ vs. $0.53$), although dependency counts rank higher.

All three simulators admit such approximations, so no regime where learning could exceed one was exercised; findings are conditional on simulation fidelity. Representation mattered more than model complexity, so learned methods should be evaluated against analytical alternatives aligned with the simulator.

**Keywords:** Dependency graphs; cascading failures; publish–subscribe; graph neural networks; graph learning; software architecture; dependability

# 1. Introduction

## 1.1 Motivation and Problem

Large distributed systems now often use asynchronous publish-subscribe (pub-sub) middleware. Examples include ROS 2 for autonomous driving [1], Apache Kafka for enterprise event streams [2], DDS in cyber-physical systems [3], MQTT in IoT [4], and cloud-native microservices [5, 6]. Pub-sub separates producers and consumers by space, time, and synchronization [7]. Instead of direct references, components communicate via topics and brokers, and Quality-of-Service (QoS) policies set at deployment control reliability, durability, priority, and deadlines.

This decoupling also hides how failures spread. Outages, blocking and backpressure travel through brokers, shared topics, colocated hosts and shared libraries [8, 9]: in sequential cascades a slow subscriber fills a broker queue and starves its publishers [10], and in simultaneous blasts a library crash or host outage takes down every colocated service at once. Neither is visible in architecture diagrams or call graphs. The cheapest time to address these risks is before deployment, during design and continuous integration [11, 12], when no telemetry exists, so critical components must be identified from configuration manifests alone.

Current practice leaves a gap between service-level static analysis and system dependability: a system can have no defect in any service yet fail through hidden single points of failure or mismatched QoS contracts [13, 14]. ATAM depends on manual input [15], static code analysis inspects services in isolation [16, 17], and chaos engineering [18], fault injection [19] and dependency tracing [20] need a running system and, in CI, considerable computation and energy [21, 22, 23]. Graph representations have long supported reliability and defect analysis [24, 25], and graph learning has recently been applied to network criticality [26, 27] and microservices [28]. It remains unclear whether such models’ performance comes from the learning algorithm or from the dependency representation it reads, and when learning adds value beyond analytical methods derived from the same dependencies. Software-as-a-Graph (SaG) addresses this question.

## 1.2 The Software-as-a-Graph (SaG) Approach

SaG models an event-driven architecture as a typed, directed multigraph over Applications, Brokers, Topics, Execution Hosts and Shared Libraries (Figure 1; §3.1), derives an explicit DEPENDS\_ON dependency graph through publish–subscribe rules (§3.3), and supports analytical, hybrid and learned cascade-impact rankings on it (§§4 and 5.2).

Rankers never read simulator output. Labels come from three simulators on the raw topology (§4.3) that encode different failure notions: structural reachability ($I^*$), discrete-event queue saturation ($I_{\text{dyn}}$) and multi-criteria fragmentation ($I_{\text{comp}}$); every ranker is evaluated against all three. Because simulators and rankers read the same architecture, some analytical rankings restate a simulator’s rule; a reference criterion (§4.4) reports these as measures of circularity, not as predictors. All conclusions are conditional on simulation fidelity (§7.5).

The simulators give learning different roles. The reachability simulator ranks a corpus architecture in under a second, so a learned approximation of it has no practical use; we study it to calibrate the method, measuring how much of a simulator a learner and a restatement of its rule each recover. The queue-flow simulator is expensive, so approximating it is a genuine surrogate-modelling problem, and that is where we test learners that start from the analytical approximation (§6.1).

## 1.3 Findings in Brief

Explicit dependency representations provide most of the predictive signal for the reachability and queue-flow simulators.

Making dependencies explicit enables graph learning. On the raw multigraph every relation points away from Applications, so message passing never reaches the scored nodes, and the registered primary contrast (a heterogeneous graph transformer against the training-free baseline) was null ($\Delta\rho = +0.069$, $p = 0.266$). On the dependency graph, graph attention reaches Spearman $\rho = 0.748$ against the reachability simulator (`GAT-P-QoS`), against $0.635$ on the raw multigraph. Edge direction does not account for the gain (the derived graph adds $+0.072$ over a raw-graph GAT that passes every edge both ways, Holm $p = 0.014$), nor do the features that compute part of the simulator: with all of them removed, the dependency-graph GAT beats an equally stripped reverse-edge control by $+0.231$ (Holm $p = 0.0068$), while the raw-graph learners collapse.

The same representation enables simple analytical rankings that the learned models do not exceed. Counting direct dependents, publish–subscribe afferent coupling, reaches $0.764$ and is not distinguishable from the best learned model, which approaches it through its degree features. On the queue-flow simulator ($12.7$ CPU-hours to label the corpus), a rate-weighted first-order approximation reaches $0.830$ in milliseconds and exceeds a gradient-boosted approximation trained on the simulator’s labels ($0.799$; exploratory); declared rates and payload sizes, not QoS policies, carry the extra signal.

Learning adds measurable value only relative to a weak comparator. Hybrids that correct a closed-form prior outperform the training-free baseline but not their own base learners, so the gain belongs to the baseline’s weakness. Learners that start from the rate-weighted approximation do not improve on it: as an extra input it leaves a gradient-boosted model at its value, and as a prior it leaves a graph attention network below it ($-0.018$). Learned models transfer zero-shot to five stylized models of open-source systems better than the training-free baseline ($\rho \approx 0.81$ vs. $0.53$), mainly by separating inert from active components, while dependency counts rank higher still and ordering among active components remains weak ($\rho_{>0} \le 0.342$). All three simulators are well approximated by low-order functions of the dependency graph, so the benchmark did not exercise a regime in which learning could exceed an aligned analytical ranking.

In practice, the results favor training-free dependency analysis for routine use. Recovering 80% of the true critical set requires reviewing about 40–45% of Applications, so rankings suit prioritized review rather than blocking gates (§7.4).

## 1.4 Research Questions

Establishing when learning is unnecessary is as informative as showing when it succeeds. Software engineering research has repeatedly shown that simple metrics can match the performance of more complex models when the right information is available [25, 29, 30, 31]. Analytical rankings can also be easier to explain, validate, and run in Continuous Integration and Continuous Deployment (CI/CD) pipelines. We therefore evaluate learned models against analytical rankings derived from the same dependencies, not only against structural baselines. Four research questions guide the study:

-   **RQ1 (Ranking accuracy):** *How accurately do analytical, hybrid, and learned approaches rank components by cascading-failure impact on unseen architectures, and how close do they come to reference rankings that restate a simulator’s propagation rule?*

-   **RQ2 (Sources of predictive performance):** *At matched model capacity, which factors contribute most to ranking performance: the dependency representation, degree information, relation typing, Quality-of-Service (QoS) information, or the model family (attention or sum aggregation; graph neural network or gradient-boosted trees)?*

-   **RQ3 (Transfer):** *How well do learned models trained on synthetic architectures transfer zero-shot to stylized models of five open-source systems, hand-authored by a single modeler, and does their ordering of components that actually propagate failures hold?*

-   **RQ4 (Cost):** *What do analytical and learned approaches cost at CI/CD time in latency and estimated energy, which stage dominates, and how does this compare with running each simulator directly?*

The evaluation follows an analysis plan pre-specified in the replication repository, where each entry carries a commit timestamp; it was not lodged with a third-party registry, and “registered” in this paper means pre-specified in that plan. Only the plan’s two co-primary contrasts are confirmatory, and both were null. We registered the matched $2\times2$, the hybrids, the reference counts, the dependency-graph learners (whose contrasts were declared exploratory), the full-population queue-flow labels, the sensitivity arms and the controls of §6.2 as planned extensions. We registered each before its own tests ran but after we knew the main result, and we report them as secondary results; no confirmation corpus generated after the analysis was frozen has yet tested them (§7.5). The rest of the analysis is exploratory (§5.3). One change from the plan, not applying the registered nested hyperparameter selection, is disclosed and tested. The replication repository records the revision history and shows how these four research questions fit into the plan.

## 1.5 Contributions

This paper makes five contributions:

1.  **Dependency derivation for publish–subscribe architectures** (§3). A method for deriving explicit dependency graphs from deployment manifests using typed architectural rules, extending the Application-level rule of [32] with library-mediated dependencies (Rule 5); infrastructure rules are defined but not evaluated.

2.  **An evaluation guideline for simulator-labeled benchmarks** (§4.4). An operational criterion, a truncation of the simulator’s own computation, that identifies rankings restating a simulator’s propagation rule, so that learned rankers are compared with them rather than credited for agreement they encode.

3.  **A controlled comparison of analytical, hybrid, and learned ranking methods** (§§5.2 and 6.1–6.3). A study that separates the effects of dependency representation, degree information, relation typing, QoS information, and model family on cascade-impact ranking.

4.  **Analytical and learned approximations of an expensive simulator** (§§5.2 and 6.1). A rate-weighted first-order approximation of a queue-flow simulator (Eq. 7), compared with learned approximations trained on the simulator’s labels.

5.  **A reproducible benchmark, cost analysis and practitioner guidance** (§§5.1, 6.4 and 7.4). A reproducible benchmark of seventeen architectures with three simulators, a like-for-like cost analysis, and recommendations for pre-deployment cascade-impact analysis.

A previous conference paper [32] introduced the publish–subscribe multigraph, the Application-level subscriber-to-publisher dependency (Rule 1 of Table 2), and a closed-form betweenness–articulation score similar to the training-free baseline (Eq. 5, unweighted and with weights $0.7$/$0.3$), which it validated against a reachability-loss simulation on synthetic topologies and two ROS 2 benchmarks. This paper adds the Library and infrastructure rules, QoS weighting and the QoS edge encoding, the reference criterion, the learned and hybrid rankers, the analytical and learned simulator approximations, LOSO and zero-shot evaluation, the second and third oracles, the matched control, and the cost analysis. The closed-form score family validated in [32] is the weakest analytical ranker in the present evaluation, which adds reference rankings, the Application population and three oracles; the present results supersede that paper’s implicit recommendation of it.

§2 reviews related work. §§3 and 4 present the model and the rankers. §§5 and 6 cover the evaluation. §7 discusses the findings and threats, and §8 concludes.

# 2. Related Work

## 2.1 Dependability and Failure-Impact Analysis of Distributed Systems

Runtime dependability methods like broker clustering, backpressure, autoscaling, failover, and chaos engineering [18] require a running cluster, can interrupt service, and consume significant computing resources. This resource use is a major concern in green software engineering and Green AI [21, 22, 23], where the carbon footprint of large execution clusters in continuous integration encourages lightweight, energy-efficient static alternatives. Pre-production methods, such as service-level fault injection testing [19] and microservice dependency localization with PageRank (MicroRank [20]), offer lighter options before deployment. Benchmark platforms with cataloged, replayable faults, like Train-Ticket [33], help measure the impact of failures on a running deployment, which this study has not yet validated (§7.6). Architecture-based reliability prediction has a long history. Yacoub and Ammar’s method for architecture-level reliability risk analysis [24] was one of the first to combine component dependency graphs with complexity and failure severity to rank components by risk. State, path, and additive reliability models reviewed by Goseva-Popstojanova and Trivedi [34] are classic examples, as is the Palladio Component Model [35].

Error propagation has also been analyzed at the architecture level. Abdelmoez et al. [36] estimated error propagation probabilities between architectural components, and Popic et al. [37] added them to architecture-based reliability models of component-based systems. Cortellessa and Grassi [38] analyzed how error propagation affects system reliability, and Hiller et al. [39] profiled how data errors propagate across software modules (EPIC). In safety-critical systems, model-based failure analysis is standard practice, including Hierarchically Performed Hazard Origin and Propagation Studies (HiP-HOPS [40]) and the Architecture Analysis & Design Language (AADL) Error Model Annex [41]. These frameworks derive propagation paths from structural descriptions, serving as conceptual precursors to SaG’s dependency projection. However, these approaches need component failure-mode annotations, propagation probabilities or operational profiles, which deployment manifests do not carry; SaG asks a narrower question using only the manifests.

Telemetry-based methods find faults in running microservices. Examples include Seer [42], MicroRCA [43], and recent GNN-based root-cause frameworks like Eadro [44], which Zhang et al. [45] thoroughly review. In synchronous microservices, failures can spread because of thread-pool exhaustion, RPC timeouts, and retry storms [33]. In publish-subscribe systems, issues spread through queue saturation and message starvation. All these methods need data from a live system, but SaG works before any code is run. Production traces also show that real dependency graphs are large and dynamic [46], and that some outages, such as metastable failures, are sustained by load feedback rather than by the dependency structure that failed [47, 48]; a structural ranking cannot see such failures. SaG’s focus is similar to change impact analysis [49] and dependency management in microservice fleets [50]. Ranking by impact is related to learning-to-rank defect prediction [51], which explicitly optimizes the ranking measure, as our listwise loss does (§4.2).

Rankings of failure impact are often evaluated against a failure model or simulator rather than against observed outages. Such evaluation creates an interpretive challenge: a ranking may agree with a simulator because it predicts the simulator’s behavior, or because it encodes the simulator’s propagation rule. The underlying concern is not new. Simulation methodology treats a model used as ground truth as something to be validated in its own right [52]; in network science, simple neighborhood counts are known to track the outcome of spreading processes closely when propagation is short-range [53]; and in machine learning, models are known to exploit shortcuts that encode the labeling rule rather than the intended task [54]. What we add is an operational check for simulator-labeled ranking benchmarks: the ranking obtained by truncating the simulator’s own computation, against which learned rankers are compared (§4.4).

## 2.2 Static Analysis and Architectural Dependency Metrics

Static code analysis (SCA) tools like SonarQube [16] measure complexity [55], cohesion, and coupling [17] within individual services to identify modules likely to have defects [56, 57]. Software engineering defect prediction has long compared complex graph measures with simple structural metrics. For example, Zimmermann and Nagappan [25] studied network analysis on dependency graphs, while Premraj and Herzig’s replication study [29] showed that simple code and coupling metrics frequently perform as well as network measures. SCA cannot detect inter-service messaging, broker saturation, or issues that spread across hosts. Architecture recovery tools rebuild system-level structure from code [58], and HAROS [59] and ROSDiscover [60] recover and check the run-time architecture of ROS systems before launch, which is the kind of extraction SaG’s models would need on real systems. SaG’s static system analysis (SSA) uses the declared topology instead, spreading code-level metrics across architectural dependencies. Architecture-level coupling metrics count a service’s consumers, such as afferent coupling [61], the Absolute Importance of the Service [62], and service fan-in [63]. In publish–subscribe systems, these counts are not simply a single edge lookup, since consumers reach producers only via topics, brokers, and shared libraries. They require a typed two-hop query (publisher to topic to subscriber), which SaG’s dependency rules define clearly. Because this count corresponds to the first propagation wave of the reachability oracle used here, this paper reports it as a reference that restates the oracle, not as a predictor (§4.4). This helps teams find structural anti-patterns [64, 65] and architectural technical debt [66] in CI/CD [67]. These studies suggest that much of the information about architectural criticality can be recovered directly from explicit dependency structure. They leave open whether learned methods add predictive information beyond such dependency-based analyses.

## 2.3 Multi-Criteria Weighting

Combining QoS policies or failure effects into a single, auditable weight is a multi-criteria decision problem. The Analytic Hierarchy Process (AHP) [68] is the standard method, and SaG uses it for the topic weights in §3.2. AHP’s consistency ratio can find inconsistent judgments, but it does not detect matrices that have been filled in to match a chosen answer, so the weights of the composite oracle (§4.3) are reported as declared rather than elicited.

## 2.4 Graph Learning on Dependency Structures

Closed-form indices [69, 70, 71, 72], including one used as this study’s training-free baseline, and cascade models of network robustness [10, 8, 9] assume homogeneous, usually undirected graphs. This means a single untyped score can mix up different elements like topics, libraries, and hosts. Learned node-importance methods, such as FINDER [26], DrBC [27], and PowerGraph [73], also assume homogeneity, as does learned approximation of betweenness and closeness [74]; GENI [75] estimates node importance on heterogeneous knowledge graphs, the closest learned analogue to a typed ranker. Homogeneous GNNs like Graph Attention Networks (GAT [76]) ignore relation identity unless it is added as a feature. Softmax attention averages over neighbors and cannot count them, while sum aggregation can [77, 78]; theoretically, standard message-passing GNNs are strictly limited in counting substructures without explicit features [79]. Since the main reference here is neighbor count, this difference matters (§6.2). Heterogeneous GNNs, like the Heterogeneous Graph Transformer (HGT [80]), learn transformations specific to each relation. However, extensive benchmarking by Lv et al. [81] demonstrated that heterogeneous GNNs often fail to outperform well-tuned homogeneous baselines like GAT, directly paralleling our typing ablation findings. More broadly, Shchur et al. [82] showed that GNN rankings are sensitive to data splits and tuning, while Huang et al. [83] showed that label propagation combined with shallow models can outperform GNNs on transductive node classification. We test both types with the same capacity (§6.2). Khodabandeh et al. [28] use graph attention on microservice call graphs to predict upcoming interactions. In contrast, we predict the effect of removing a node from a declared topology. These studies show that graph learning can exploit structural information in software and network graphs. Their evaluations typically compare learned models with selected baselines; fewer examine whether performance originates from the graph representation or from the learning algorithm applied to it.

## 2.5 Positioning of This Study

This study builds on findings that simple baselines can perform as well as more complex learning methods [30, 31], and that network measures on dependency graphs [25] add little over simple coupling metrics once those are included [29]. In line with Green Software Engineering and Green AI principles [21, 22, 23], the cost of learned models in continuous integration should also be weighed against that of simple static analyses.

The study differs from prior work in three ways. First, it derives explicit dependency graphs from publish–subscribe deployment manifests rather than starting from an existing architectural graph. Second, it evaluates analytical, hybrid, and learned ranking methods using the same representation and asks where their ranking performance originates. Third, it applies an operational reference criterion, a truncation of the simulator’s own computation, to separate rankings that restate a simulator’s rule from those that predict its outcomes. Rather than asking whether graph learning can rank cascade impact, the study asks when it adds measurable value beyond rankings derived directly from the explicit dependency structure. More broadly, the study contributes to understanding the limitations of AI techniques for reliability analysis by identifying when apparent predictive accuracy reflects restatement of the evaluation simulator rather than learned skill.

This common representation enables controlled comparisons between methods that differ in complexity but operate on identical dependency information.

## 3.1 Multigraph Definition

A distributed system is described as a typed, weighted, directed multigraph:

$$\tag{1}
\mathcal{G} = (V, E, \tau_V, \tau_E, w_V, w_E)$$

where:

-   $V = V_{\text{app}} \cup V_{\text{broker}} \cup V_{\text{topic}} \cup V_{\text{host}} \cup V_{\text{lib}}$ holds the five entity types $\mathcal{T}_V$ of Table 1; $V_{\text{host}}$ denotes physical or virtual *Execution Hosts*.

-   $E$ is the set of directed edges, and $\tau_V: V \to \mathcal{T}_V$ and $\tau_E: E \to \mathcal{T}_E$ assign entity and relation types.

-   $w_V: V \to (0, 1]$ and $w_E: E \to (0, 1]$ weight entity criticality along with connection strength. In the implementation evaluated here, $w_V$ of an Application is a power mean of the QoS weights $w(t)$ (§3.2) of the topics it publishes or subscribes to, and a Library takes the largest weight among its own topics and its consuming Applications, amplified by its fan-out. A code-quality penalty (CQP), computed from lines of code, cyclomatic complexity, instability and cohesion, does not enter $w_V$; it and its four inputs appear only as node features of the learned rankers (§3.5).

The raw multigraph is denoted $G_{\text{structural}}$. The simulation oracles run on it, and the raw-graph learners pass messages over its edges. The analysis graph $G_{\text{analysis}}$ is $G_{\text{structural}}$ augmented with the derived `DEPENDS_ON` edges (§3.3) and the typed node properties computed from them (§3.5). Its Application–Library `DEPENDS_ON` projection is the graph the analytical rankings and the `-P` learners read. Supplementary §S1 lists the notation.

**Scope of Evaluation and Entity Roles.** While the multigraph formalizes five entity types, this study concentrates its empirical study specifically on *Applications* ($V_{\text{app}}$). An *Application* (the term used by OMG DDS and ROS 2) corresponds to a microservice container, service agent or communicating process: the developer-authored code that changes in CI/CD, and hence the target of pre-deployment triage. Brokers, Topics, Execution Hosts and Libraries are modeled because failures propagate through them, but ranking them is a provisioning question rather than a commit-time one, so the evaluation ranks Applications only; brokers and hosts remain an extension (§7.6).

**Table 1.** Entity types and structural edge types in the SaG model.

| **Entity Type ($\mathcal{T}_V$)**      | **Architectural Role**                        | **Concrete System Examples**                   |
|:---------------------------------------|:----------------------------------------------|:-----------------------------------------------|
| **Application** ($V_{\text{app}}$)     | Process producing/consuming messages          | ROS 2 node, Kafka microservice, MQTT client    |
| **Broker** ($V_{\text{broker}}$)       | Message routing and queuing intermediary      | RabbitMQ exchange, Mosquitto, EMQX broker      |
| **Topic** ($V_{\text{topic}}$)         | Named logical communication channel           | `/sensor/lidar`, `orders.payment.completed`    |
| **Execution Host** ($V_{\text{host}}$) | Physical or virtualized execution environment | Bare-metal server, Kubernetes worker, Cloud VM |
| **Library** ($V_{\text{lib}}$)         | Shared software package or runtime dependency | Kafka client, OpenCV, Protobuf runtime         |
| **Structural Edge ($\mathcal{T}_E$)**  | **Direction**                                 | **Semantic Meaning**                           |
| `PUBLISHES_TO` / `SUBSCRIBES_TO`       | App/Library $\to$ Topic                       | Component publishes to / consumes from topic   |
| `ROUTES`                               | Broker $\to$ Topic                            | Broker manages and routes topic traffic        |
| `RUNS_ON`                              | App/Broker $\to$ Host                         | Process is hosted on host                      |
| `CONNECTS_TO`                          | Host $\to$ Host                               | Network link between hosts                     |
| `USES`                                 | App $\to$ Library                             | Application links to shared library            |

## 3.2 Quality-of-Service Link Weighting

A link’s strength is conceptually determined by its Quality-of-Service (QoS) contract. For example, a `RELIABLE` topic with `TRANSIENT_LOCAL` durability creates a stronger connection between services than a `BEST_EFFORT` telemetry stream. Each topic $t$ has an overall weight $w(t) \in (0, 1]$ that combines its QoS policies (reliability, durability, priority) with payload size and publication frequency. We set the reliability, durability, and priority weights employing an Analytic Hierarchy Process (AHP) pairwise-comparison matrix, which we defined independently and did not adjust to fit a target vector ($CR = 0.016$, non-degenerate; Supplementary §S6).

The evaluation tests whether this contractual information improves cascade ranking, and it does not: declared QoS policies carried no measurable signal on either the reachability or the queue-flow simulator (§§6.1 and 6.2). For the reachability simulator this null is largely fixed by design, because $I^*$ barely reads QoS (§4.3); the queue-flow simulator does read QoS policies, so there the null may be informative, although its sensitivity to them was not measured. The weighting is retained for completeness; the dependency counts reported in this paper are unweighted and do not use $w(t)$.

## 3.3 Logical Dependency Projection (`DEPENDS_ON`)

Structural edges do not directly show how failures spread. For example, a subscriber depends on a publisher, but pub-sub topologies have no direct edge between them. SaG therefore derives an explicit semantic relation, `DEPENDS_ON`, from the dependent to the dependency: if the target fails, the source is affected. The derived edges expose the architectural pathways through which failures may propagate, and the resulting dependency graph is the common input for analytical rankings, hybrid methods, and graph-learning models. Table 2 lists the rules.

**Table 2.** The `DEPENDS_ON` logical dependency projection rules. $^\dagger$Defined for completeness; not exercised by the Application-level evaluation.

|    **Rule**     | **Dependency Category** | **Structural Pattern ($\text{Dependent} \to \text{Dependency}$)**           | **Derived Weight ($w$)**                                                 |
|:---------------:|:------------------------|:----------------------------------------------------------------------------|:-------------------------------------------------------------------------|
|      **1**      | `app_to_app`            | Subscriber $\to$ Publisher (via shared Topic)                               | $1 - \prod_{t \in T}(1 - w(t))$                                          |
| **2**$^\dagger$ | `app_to_broker`         | Publisher/Subscriber $\to$ Broker routing its topics                        | $1 - \prod_{t \in T}(1 - w(t))$                                          |
| **3**$^\dagger$ | `host_to_host`          | Host $\to$ Host (lifted from inter-host app dependencies)                   | $\max_{u \in \text{hosted}(h_1), v \in \text{hosted}(h_2)} w_E(u \to v)$ |
| **4**$^\dagger$ | `host_to_broker`        | Host $\to$ Broker (lifted from hosted app dependencies)                     | $\max_{u \in \text{hosted}(h)} w_E(u \to b)$                             |
|      **5**      | `app_to_lib`            | Application $\to$ Shared Library it `USES`                                  | $H(w_V(\text{app}), w_V(\text{lib}))$                                    |
| **6**$^\dagger$ | `broker_to_broker`      | Broker $\leftrightarrow$ Broker (shared fault-domain colocation, symmetric) | $w_V(\text{host})$                                                       |

Rules 1 and 2 combine topics $T$ that connect a pair using probabilistic union [84], so that having multiple failure paths increases the connection strength. Rule 5 uses the harmonic mean $H(x, y) = 2xy/(x+y)$ [85].

**Sequential cascades and simultaneous blasts.** Rule 1 describes sequential cascades, where if a publisher fails, its subscribers are affected because they do not receive messages. Rule 5 describes simultaneous blasts, where if a library crashes, all applications that depend on it fail at the same time. Neither mechanism is stated explicitly in a deployment manifest; each rule makes one of them visible. Shared-library dependencies are included because they create simultaneous blast failures that message-flow topology alone does not represent. Libraries that publish or subscribe are also endpoints for Rule 1, and an Application can reach a library’s topics through Rule 5. `InDeg`, `Reach`, `Topo-QoS` and the graphs the `-P` learners read apply Rule 1 to direct subscriptions only (Eq. 2). The node-property extraction, which produces the in-degree feature every learner receives, additionally follows up to three `USES` links, so an Application that subscribes through a library it uses counts as a Rule 1 dependent in that feature only. The two counts differ for 940 of the 1,321 Applications, the feature always being the larger, and agree in rank at $\rho = 0.55$–$1.00$ per fold. Rules 2, 3, 4, and 6 (host failure domains and broker routing) are defined for completeness and are not used in the Application-level evaluation.

**Remark 1 (the dependency count is a typed two-hop count).** Let $G_{\text{flow}}$ be the Application–Library projection (Rules 1 and 5) and $v$ an Application. By construction, $$\tag{2}
\texttt{InDeg}(v) \;=\; \bigl|\{\,u \neq v : \exists t \in V_{\text{topic}},\; (v, t) \in \texttt{PUBLISHES\_TO} \wedge (u, t) \in \texttt{SUBSCRIBES\_TO}\,\}\bigr|.$$ Since Rule 5 edges end at Libraries, every edge into an Application is a Rule 1 edge $u \to v$, which exists exactly when $u \neq v$ (an Application or a Library) directly subscribes to a topic that $v$ publishes; in the presence of multiple parallel topics between the same pair, parallel topics collapse into a single directed dependency edge in $G_{\text{flow}}$.

The right side of Eq. 2 represents publish–subscribe afferent coupling (fan-in, or the Absolute Importance of the Service [61, 62]), and is a typed two-hop query on the raw multigraph. `InDeg` can be computed directly without projection; the projection defines which typed query to use. We checked this equality on all seventeen corpus graphs, with a maximum absolute difference of $0$. We measure the value of the derivation separately: including Rule 5 raises the agreement of transitive reach with $I^*$ by $+0.058$ (9 of 12 folds, Holm $p = 0.0068$; §6.1). Since the primary oracle’s first propagation wave matches this set (§4.4), `InDeg` and its transitive version `Reach` are used as reference points in this paper, not as predictors.

## 3.4 Dual Graph Views

The **structural graph** $G_{\text{structural}}$ is the raw deployment topology. The **analysis graph** $G_{\text{analysis}}$ adds the `DEPENDS_ON` edges and code metrics (see Figure 2). Every ranker’s node features are computed on $G_{\text{analysis}}$; the learners pass messages either over the edges of $G_{\text{structural}}$ or over the `DEPENDS_ON` projection (Table 4), and no ranker reads simulator output (§4.4). The two views also differ for a learner: on $G_{\text{structural}}$, every relation points away from Applications, so forward message passing does not reach them. In the `DEPENDS_ON` graph, each Application receives messages from its dependents (§6.2). The raw multigraph is therefore also a comparison point in the evaluation: it exposes communication structure but not cascading dependencies. Because the two views also differ in edge direction, §6.2 adds a raw-graph learner that passes every message in both directions, so that dependency semantics can be separated from direction.

## 3.5 Typed Node Feature Encoding

The rankers use typed node properties from $G_{\text{analysis}}$. All five entity types share a base set of 18 normalized metrics (in $[0, 1]$): PageRank, Reverse PageRank, betweenness, closeness, eigenvector centrality, in-degree, out-degree, clustering, an articulation score (a continuous directed cut-vertex score that the implementation stores in two columns, the 18 including both), bridge ratio, node QoS weight, incoming and outgoing dependency weights, multi-path coupling, path complexity, fan-out criticality, and the Connectivity Degradation Index (CDI). We calculate four centrality features (PageRank, Reverse PageRank, betweenness, and closeness) over weighted edges, so they include QoS information. This means the so-called QoS-off condition is not entirely free of QoS effects. Several of these features compute part of what the reachability simulator computes. The in-degree feature and the incoming dependency weight $w_{\text{in}}$ (a QoS-weighted version) are close to `InDeg`; CDI is the connectivity lost when the node is removed, a removal-and-reachability computation on $G_{\text{analysis}}$; and multi-path coupling, reverse PageRank and the articulation score are also aligned with that simulator. Every published learner reads them, so the learners inherit part of the oracle’s circularity; §6.2 reports learners with all of them removed. Type-specific blocks add more features, extending the vector to 19–25 dimensions (Applications and Libraries add the code-quality penalty and its four static-code inputs; the full schema is in Supplementary §S13). CDI measures structural connectivity loss using a fixed-scale breadth-first sample to keep computation time reasonable (§6.4). We discuss its sensitivity to hash-seeded tie-breaking in §7.5.

In this study, SaG therefore serves two roles. It provides a dependency representation from which analytical rankings can be computed directly, and it provides a graph on which learned and hybrid methods operate. The evaluation in §§5–7 examines how much ranking performance arises from this representation and how much from the models applied to it.

# 4. Ranking Methods, Simulation Oracles, and the Reference Criterion

The study compares analytical rankings derived directly from dependency structure (the training-free baseline `Topo-QoS`, QoS-weighted betweenness on the dependency graph, and the references of §5.2), hybrid methods that correct an analytical prior with a learned model, and learned methods: graph neural networks on the typed multigraph or the dependency graph, and gradient-boosted models on per-Application features (Figure 3). All are trained on or evaluated against simulation oracles that run on a separate graph view (§4.3). Full hyperparameters and training commands are in the replication repository’s experiment pages (§5.1).

## 4.1 Heterogeneous Graph Transformer and Attention Networks

The main learned ranker, `HGT-QoS`, is a three-layer Heterogeneous Graph Transformer (HGT) [80] built with PyTorch Geometric [86]. It uses a hidden dimension of $D=64$ and $H=4$ heads; on the dependency graph, which has fewer relation types, `HGT-P-QoS` uses width $100$ so that its parameter count ($430{,}680$) stays within $1\%$ of `HGT-QoS` ($434{,}620$). Entity-specific linear projections map raw node features $x_v \in \mathbb{R}^{19\text{--}25}$ into the hidden space, with $h_v^{(0)} = \text{LayerNorm}(\text{GELU}(W_{\tau(v)} x_v))$. For each meta-relation $\langle \tau(u), \phi(e), \tau(v)\rangle$, attention uses type-parameterized keys, queries, and values, scaled by a learned per-meta-relation prior $\mu_{\langle \tau(u), \phi(e), \tau(v)\rangle}$; full layer-wise formulations are in Supplementary §S2. HGT passes messages over its input graph and its transpose: $G_{\text{structural}}$ for `HGT-QoS` and the `DEPENDS_ON` projection for `HGT-P-QoS`. The GATs pass messages forward only, except the direction control `GAT-QoS-R`, which also passes every edge in reverse. In the raw multigraph $G_{\text{structural}}$, native relations point away from Applications (e.g., `PUBLISHES_TO`, `RUNS_ON`, `USES`), so forward message passing cannot propagate messages to the scored Application nodes, and forward GNNs on it collapse into per-node models over precomputed features (§7.2). The dependency graph directs edges from dependents to dependencies, so forward message passing aggregates information from each Application’s dependents. The homogeneous Graph Attention Network (`GAT-QoS`, and `GAT-P-QoS` on the dependency graph) uses a three-layer architecture with four attention heads and width $D=288$ ($D=296$ in the unweighted control for parameter matching), projecting all node types into a joint embedding space before applying homogeneous `GATConv` layers.

Each directed edge has a 16-dimensional vector. Index 0 represents the coupling weight, index 1 is the normalized path count, indices 2 to 8 are a one-hot encoding of the relation, and indices 9 to 15 are middleware QoS parameters such as reliability, durability, priority, transport departure mode, deadline constraints, and max-blocking time. The edge vector is projected and added before attention. Because indices 2 to 8 encode the relation, the “untyped” `GAT-QoS` receives relation identity as an edge feature. This matters only where messages reach Applications: on the raw multigraph forward GAT messages never do, and on the dependency projection every edge carries the same relation, so the encoding is constant.

## 4.2 Prediction Head and Training Objective

A composite head predicts the simulated cascade impact, supplemented by an auxiliary head $\hat{a}_1$ regressing on $I^*_R$, the reliability component that the same simulator run records beside $I^*$. The operational training objective combines mean-squared error regression with listwise and margin-ranking terms: $$\tag{3}
\mathcal{L} = \text{MSE}(\hat{I}^*, I^*) + 0.5 \cdot \text{MSE}(\hat{a}_1, I^*_R) + 0.3 \cdot \mathcal{L}_{\text{rank}} + 0.1 \cdot \mathcal{L}_{\text{pairwise}},$$ where $\mathcal{L}_{\text{rank}}$ is Listwise Maximum Likelihood Estimation (ListMLE) [87] over the permutation $\pi$ induced by the simulated labels, $$\tag{4}
\mathcal{L}_{\text{rank}} = -\frac{1}{N}\sum_{i=1}^N \Big( \hat{s}_{\pi_i} - \log \sum_{j=i}^N \exp(\hat{s}_{\pi_j}) \Big),$$ and $\mathcal{L}_{\text{pairwise}}$ is a margin-ranking loss with $\gamma = 0.05$ over pairs differing by more than $\gamma$. Tied labels, which affect about 31% of Applications with $I^* = 0$, enter $\pi$ in input order, which is the generator’s creation order. This injects an arbitrary ordering among inactive nodes into ListMLE; the margin-ranking term ignores pairs separated by less than $\gamma = 0.05$, and a control that permutes node order before training tests whether the ordering leaks into the results (§6.2).

Models are trained with AdamW ($\eta = 3 \times 10^{-4}$, weight decay $10^{-4}$) using cosine warm restarts for up to 300 epochs. We set early stopping at 60 epochs of patience on a 20% node-level validation split from the largest training scenario of each fold (when the corpus’s largest scenario is held out, the next largest takes its place), using five fixed seeds ($\{42, 123, 456, 789, 2024\}$); while this node-level split is transductive with respect to that scenario’s internal graph, all reported evaluations are strictly inductive under leave-one-scenario-out cross-validation. We set hyperparameters and loss coefficients before the first sweep and kept them the same across all experiments. This approach differs from the registered plan, which called for selecting every hyperparameter using nested inner-LOSO selection (two-fold inner holdout). Instead, the published results use one fixed configuration, chosen during the main experiments to keep computation manageable across seeds and folds. We explain this difference in §5.3. We ran the registered selection later as a sensitivity analysis on the eight-configuration stage-1 grid (varying depth and rank normalization of features and labels). That harness also holds one training scenario out for early stopping, so it trains on one scenario fewer and stops on a different signal; it therefore compares two protocols, not only two hyperparameter choices, which is why it does not reproduce the published scores on the folds where it selected the published configuration (§6.2). The main null finding does not change under nested tuning.

## 4.3 Simulation Oracles

Labels come from three failure simulators (“oracles”), which define different notions of cascade impact rather than observations of real failures and run on the raw multigraph $G_{\text{structural}}$:

-   **Primary reachability cascade oracle ($I^*$):** Crashes component $v$, propagates outages through dependent topics, brokers and links via breadth-first traversal on $G_{\text{structural}}$, and computes the mean fractional feed loss across intact subscribers. Feed loss is scaled by a declared, uncalibrated QoS severity ladder ($\times 1.2$ `RELIABLE`, $\times 1.15$ high priority, $\times 1.05$ medium) and clamped to $[0, 1]$. Each propagation wave is processed in a seeded random order, which decides ties at the propagation threshold; the label is the mean over five seeds. Disabling QoS scaling leaves the Application ordering largely intact ($\rho = 0.965$ across the twelve folds), and substituting durability-aware rescaling moves it less still ($\rho = 0.977$), showing that $I^*$ is predominantly a topological reachability metric.

-   **Queue-flow discrete-event oracle ($I_{\text{dyn}}$):** A discrete-event SimPy [88] simulation of message emission rates, queue saturation and network latency that measures the drop in delivered message rate for surviving consumers, using declared rates, payload sizes and QoS contracts that $I^*$ ignores. QoS policies act on the queues (drop order on overflow, durable replay, priority, deadlines and lifespans, history depth); no run with them disabled was made, so its sensitivity to QoS is not quantified. Its mechanism differs from reachability, but its first-order effect, consumers losing a failed publisher’s messages, is again subscriber loss, and it models configured parameters, not operating-system dynamics. It provides labels for all $1{,}321$ Applications, averaging over five seeds, and takes $12.7$ CPU-hours for the full corpus, compared to seconds for $I^*$. A sensitivity check restricted to the first $30$ Applications per fold in lexicographic order is reported in Supplementary §S40 (Table S63). $I_{\text{dyn}}$ agrees with $I^*$ at a mean $\rho = 0.711$ $[0.625, 0.794]$. Across seeds, a single $I_{\text{dyn}}$ run agrees with another at $\rho = 0.43$–$0.96$ per fold; the five-seed mean used as the label has an estimated reliability of $r = 0.79$–$0.99$ (Spearman–Brown), so no ranker can agree with it by more than $\sqrt{r} \approx 0.89$–$0.996$ per fold. Every ranker in Table 6 stays below even $r$ on every fold; per-fold values are in the replication package.

-   **Composite multi-criteria failure oracle ($I_{\text{comp}}$):** An auxiliary benchmark uses the Validate-stage failure simulator. We run it on all $1{,}321$ Applications with QoS weighting and a primed baseline flow. Each removal is scored as a linear combination of four degradation components: $I_{\text{comp}}(v) = 0.35\,\text{RL}(v) + 0.25\,\text{FR}(v) + 0.25\,\text{TL}(v) + 0.15\,\text{FD}(v)$, representing Reachability Loss ($\text{RL}$), Fragmentation ($\text{FR}$; $0.70$ structural component loss $+\,0.30$ severity), Throughput Loss ($\text{TL}$), and Flow Disruption ($\text{FD}$). The weights are declared, not elicited, so $I_{\text{comp}}$ serves as a declared multi-objective stress test of fragmentation and throughput disruption rather than just subscriber loss. Since fragmentation and flow disruption occur with almost every removal, $I_{\text{comp}}(v) > 0$ for nearly every Application. $I_{\text{comp}}$ is never used as a training label.

## 4.4 Input–Label Separation and the Reference Criterion

No simulation output is used as an input: features are computed on $G_{\text{analysis}}$ and labels come only from the oracles (a regression test enforces this), although the raw-graph learners pass messages over the structural edges the oracles traverse.

Procedural separation does not remove construct overlap: a ranking may agree with a simulator because it reproduces the simulator’s rule rather than because it infers impact from independent evidence.

**The reference criterion.** We defined the criterion post hoc, after simple dependency counts performed strongly, and state it here in operational form. A ranking $R$ is an *order-$k$ reference* for an oracle $O$ if $R$ is what $O$ computes when its propagation is truncated after $k$ waves, with stated simplifications, from the same inputs $O$ reads. Whether a ranking qualifies is therefore decided by derivation from the simulator’s definition, not by its score. For $I^*$: the first-order expansion (Eq. 6) is the expected feed loss after one wave; `InDeg` is the support of that first wave, its size without the per-topic fractions (Remark 1; classical publish–subscribe afferent coupling [61, 62]); and `Reach` is the unweighted support of the untruncated cascade. For $I_{\text{dyn}}$, the rate-weighted expansion (Eq. 7) is the delivered-rate loss after one wave, ignoring queueing. A reference measures how much of $O$ its own rule recovers, a property of the oracle rather than predictive skill, so comparisons with it are not claims of superiority. All other rankers, namely the training-free baseline and the learned and hybrid methods, are *predictors*. For $I_{\text{comp}}$, no ranking is a truncation; its fragmentation and flow terms respond to removing high-degree and high-betweenness nodes, so `Topo-QoS` and raw degree are *term-aligned* with it. They are not references under the definition above, but their performance is interpreted with the same caution. How much of each oracle its own rule recovers is read directly from the reference rows: the first-order expansion reaches $\rho = 0.808$ on $I^*$, and the rate-weighted expansion $0.830$ on $I_{\text{dyn}}$ (Tables 5 and 6). The learned methods are not references by this definition, but this does not make them less circular: they are fitted to the oracle they are scored against and read features that compute part of it (§3.5). We therefore apply the same accounting to them, reporting each learner’s agreement with $I^*$ after the first-order expansion is partialled out (§6.1), and learners with the oracle-aligned features removed (§6.2). Two analyses limit the circularity without removing it: every ranker is scored on all three oracles, and its agreement with $I_{\text{dyn}}$ is also reported after removing $I^*$ or the first-order term (§6.1). Neither replaces validation against real failures (§7.5).

**Training-free baseline.** `Topo-QoS` is computed on the Application–Library `DEPENDS_ON` graph (Rules 1 and 5): $$\tag{5}
\text{Topo-QoS}(v) = 0.6 \cdot \text{BT}_{w}(v) + 0.4 \cdot \text{AP}(v),$$ where $\text{BT}_{w}$ is betweenness over edge distances $d(e) = 1/(w(e) + 10^{-6})$, so tightly coupled edges attract shortest paths, and AP flags articulation points. Because of an implementation defect (an index mismatch when the articulation scores are read), the AP term is zero for every node, so the score that was executed, and that every table reports, is QoS-weighted betweenness alone. Restoring the term lowers `Topo-QoS` from $0.553$ to $0.533$, so the defect does not favor the reference counts; Table 5 reports the corrected value beside it, and hybrids retrained on the corrected prior are reported in §6.1. The comparator was fixed when the analysis plan was written, before the dependency counts had been analyzed, and continues the closed-form score family of [32]; in hindsight, afferent coupling would have been the natural comparator, and it is reported beside the baseline as a reference. The unweighted Topo baseline is reported in Supplementary §S42.

Three training-free rankings restate the reachability oracle’s propagation rule and are reported as references. The first is the post hoc first-order expansion of $I^*$ (Analytic $I^*$): $$\tag{6}
\hat{I}^*_1(v) = \sum_{t \in \text{pub}(v)} \frac{|\text{sub}(t)|}{|\text{pub}(t)|},$$ where $|\text{pub}(t)| \ge 1$ holds for all published topics $t \in \text{pub}(v)$ by construction ($v$ publishes to $t$), preventing any division by zero. The second is `InDeg`$(v)$, the number of direct dependents of $v$ on the Application–Library `DEPENDS_ON` graph, which for an Application equals publish–subscribe afferent coupling and is exactly the set $I^*$’s first wave reaches (Remark 1). The third is `Reach`$(v)$, the number of its transitive dependents normalized by $|V| - 1$, which is the set a reachability cascade can visit. For the queue-flow simulator $I_{\text{dyn}}$, the corresponding reference is the rate-weighted first-order expansion $$\hat{I}^{\mathrm{rate}}_{\mathrm{dyn},1}(v) \;=\; \sum_{t \in \mathrm{pub}(v)} \frac{r_t}{|\mathrm{pub}(t)|}\,\lvert \mathrm{sub}(t) \rvert,
\tag{7}$$ where $r_t$ is the declared publication frequency of topic $t$. Eq. 7 weights each term of the first-order expansion of $I^*$ (Eq. 6) by the topic’s declared publication rate. It is therefore a first-order truncation of the queue-flow simulator $I_{\text{dyn}}$, which reads the same rates, and it is reported as a reference for $I_{\text{dyn}}$ rather than as a predictor. It was evaluated after the registered analyses and is exploratory. It is the natural reference for learned approximations of that simulator, and in practice a training-free ranking for queue-flow impact (§7.4). Raw-multigraph topic counts (Pubs-raw) and transitive closure without Rule 5 (Reach-R1) are archived in the replication repository. References carry no contrast against `Topo-QoS`, and a learner’s distance from them is reported as such, not as a test. The one exception is the paired comparison between the rate-weighted reference and the learned queue-flow approximation (§6.1), which is labeled exploratory.

## 5.3 Metrics, Protocols and Statistics

**Population.** Every ranker is scored on the Application set $V_{\text{app}}$.

Metrics. We use Spearman $\rho$ to measure ranking against the simulation oracles. To distinguish between active components and those with zero impact, we report both the full-population Spearman $\rho$ and the active-stratum Spearman $\rho_{>0}$, which only includes components with true impact greater than zero. To identify critical sets, we use Overlap@$K$, the fraction of the true top-$K$ recovered by the predicted top-$K$, where $K$ is about 20% of $|V_{\text{app}}|$. PR-AUC, $F_1@\tau$, and nDCG@10 are reported in Supplementary §S17.

Protocols. In the LOSO setup, we train learned models on eleven scenarios and test on the twelfth, repeating this for all 12 folds and five random seeds. The reported value is the average $\rho$ across seeds. For zero-shot transfer, we evaluate models built on all twelve scenarios across the five system models without any fine-tuning. Training-free rankers are not fitted to any data, so for them, both protocols become per-scenario analyses on the same twelve scenarios and five models. We include them in the same tables to ensure every row is scored on the same scenarios and labels.

Statistics. The analysis emphasizes effect sizes with confidence intervals rather than a single winner; “matches” means not significantly different, not statistically equivalent (§7.5). The summary $\rho$ is the mean Spearman correlation over folds or systems, with a 95% bootstrap interval over folds ($B = 2{,}000$) [89]; contrasts use paired two-sided Wilcoxon signed-rank tests across folds [90, 91] (smallest attainable $p = 0.00049$), and, because LOSO folds share ten of eleven training scenarios, every registered contrast is also tested with the Nadeau–Bengio corrected resampled $t$-test [92]. As the effect size we report the number of folds on which a ranker beats its comparator (“won”), the paired probability of superiority; the unpaired Vargha–Delaney $\hat{A}_{12}$ does not apply to fold-paired data. Fisher-$z$ averaging does not change the row order of Table 5; weighting folds by $|V_{\text{app}}|$ changes it for `Topo-QoS` (§6.1). Spearman $\rho$ gives ties their average rank; Overlap@$K$ breaks ties at the boundary by node order, so §6.1 also reports tie-aware recall.

**Analysis plan and the status of each result.** The protocol is pre-specified in the replication repository with commit timestamps, not lodged with a third-party registry; seventeen numbered amendments were registered, none withheld. Every result has one of three tiers. *Confirmatory*: the plan’s two co-primary contrasts (`HGT-QoS` and `HGT` vs. `Topo-QoS`, Holm across the two), both null. *Registered secondary*: arms committed before they ran but after the primary null was known, including the matched $2\times2$, the hybrids, the reference counts, the derivation value, the full-population queue-flow labels, the sensitivity, direction and corrected-prior arms, and the oracle-aligned-feature, node-order and learning-on-Eq. 7 controls, each Holm-corrected within its family. *Exploratory*: post hoc analyses, the dependency-graph learners’ contrasts (declared exploratory when the arms were registered), the reference reclassification (which changed no figure), and the rate-weighted reference (Eq. 7) with the attribution of the learned queue-flow approximation. **Plan deviation**: the registered nested selection was replaced by one fixed configuration, with the registered rule run later as a sensitivity check (§6.2). Because sequential amendments accumulate family-wise error, an omnibus Holm correction is also applied across the 13 decision-bearing contrasts: the two co-primary contrasts, the two hybrids against `Topo-QoS` and against their base learners, the three effects of the matched $2\times2$, and four typing controls (`HGT-QoS` against `GAT-QoS`, `GAT-w` and `HGT-QoS-U`, `HGT` against `GAT`). The hybrid contrasts survive it (Hybrid-GAT $p_{\text{omni}} = 0.019$, Hybrid-HGT $p_{\text{omni}} = 0.041$) and the primary contrast stays null ($p_{\text{omni}} \ge 0.46$); the amendment log (Supplementary §S27) lists every family. The headline findings of this paper are therefore registered secondary or exploratory, not confirmatory.

Taken together, the rankers allow comparison of representation-centric and model-centric explanations of ranking performance. If performance arises primarily from the dependency representation, analytical and learned rankers built on that representation should perform similarly. If learning adds information, learned rankers should outperform analytical alternatives built on the same dependencies. §6 reports the results against these two expectations.

## 6.1 RQ1: Ranking Accuracy

**Summary.** *For the reachability and queue-flow oracles, explicit dependency graphs, rather than model complexity, carry most of the ranking signal. The strongest learned model, the graph attention network on the dependency graph (`GAT-P-QoS`, $\rho = 0.748$), approaches without exceeding the direct-dependent reference ($0.764$; not distinguishable, equivalence not established). On the expensive queue-flow oracle, a gradient-boosted approximation trained on its labels reaches $0.799$ because it reads declared publication rates and payload sizes; the rate-weighted reference, which reads the same rates without training, reaches $0.830$ and exceeds the learned approximation ($+0.031$, 10 of 12 folds; exploratory), and learners that start from the reference do not improve on it. On the multi-criteria oracle, training-free scores aligned with its terms rank highest and pure neural models drop sharply. The registered primary comparison on the raw multigraph (`HGT-QoS` vs. `Topo-QoS`) was null ($\Delta\rho = +0.069$, $p = 0.266$).*

Learned rankers are trained on eleven scenarios and scored on the twelfth; training-free rankers are scored on all twelve (26 to 300 Applications, $K$ between 5 and 60). Table 5 reports all of them against $I^*$, with the reference rankings of §5.2 in a separate block: they restate $I^*$’s rule, so their rows measure the circularity and carry no contrast.

## 6.2 RQ2: Sources of Predictive Performance

**Summary.** *Attention-based learners improve on the dependency graph, where messages reach the scored Applications from their dependents ($0.748$ vs. $0.635$ on the raw multigraph), and the gain survives two controls: a raw-graph GAT that passes every edge in both directions ($+0.072$ over it), and the removal of every oracle-aligned feature ($+0.231$ over the equally stripped reverse-edge control). Its closeness to the direct-dependent count comes from its degree features ($-0.136$ without them), whereas a sum-aggregation GNN, which can count, needs none: with no node features at all it reaches $0.719$. QoS inputs add nothing measurable once weighted in-degree is held, and the typing comparison is uninformative because it ran where messages are inert. Node order before training moves the learned values by about $0.04$ (three permutations average $0.729$ for `GAT-P-QoS`), a source of variance rather than a favourable published order.*

**The “QoS” factor was mostly the weighted in-degree.** In the capacity-matched $2\times2$ on the raw multigraph (Supplementary Table S25; cell means $0.563$, $0.548$, $0.635$, $0.622$), relation typing has no effect ($-0.014$, $p_{\text{Holm}} = 0.940$) and the “QoS” inputs add $+0.073$ ($p_{\text{Holm}} = 0.127$). The QoS-off arms, however, also zero $w_{\text{in}}$, a QoS-weighted version of `InDeg`. With $w_{\text{in}}$ held in both arms (Table 7, F4), the “QoS” effect drops to $+0.030$ $[-0.023, +0.085]$ (Holm $p = 0.33$), so more than half of it was the weighted in-degree. Closed-form controls agree: unweighted betweenness ($0.591$) and constant topic weights ($0.595$) match or exceed QoS-weighted betweenness ($0.553$), and permuting QoS profiles across topics has no effect ($\Delta = -0.006$, $p = 0.733$). Because messages never reach Applications on the raw multigraph, this $2\times2$ compares per-node models and says nothing about relational typing (§7.2).

**What the dependency-graph learner needs.** Each learner receives in-degree and $w_{\text{in}}$ as node properties and, on the dependency graph, also aggregates its dependents, so its closeness to `InDeg` could come from either. Removing the two degree columns lowers `GAT-P-QoS` by $0.136$, and also removing the three centralities most correlated with in-degree by $0.161$ (Table 7, F1). Theory predicts this: softmax attention averages over neighbors and cannot count them, whereas sum aggregation can [77, 78], and a GINE network of the same size keeps $0.721$ and $0.711$ without the same columns. These aggregator contrasts are not significant after Holm correction ($+0.108$ and $+0.124$, $p_{\text{Holm}} = 0.157$); with every oracle-aligned feature removed, the corresponding contrast is (below). In zero-shot, the degree columns matter little ($0.810$–$0.821$ without them), because the system models are ranked mostly by separating inert from active components.

**Direction versus dependency semantics.** On the raw multigraph a forward GAT never delivers a message to an Application (§4.1), so the $+0.113$ gain of `GAT-P-QoS` over `GAT-QoS` could come from edge direction rather than from dependency semantics. A control passes every raw-graph edge in both directions, with shared weights and an unchanged parameter count (`GAT-QoS-R`; Table 9). It reaches $0.676$: direction alone recovers $+0.041$ of the gain, which is not significant (Holm $p = 0.064$), and `GAT-P-QoS` still exceeds it by $+0.072$ $[+0.034, +0.113]$ on 10 of 12 folds (Holm $p = 0.014$). The derived dependency graph therefore adds beyond edge direction. Reverse edges also cost transfer: `GAT-QoS-R` reaches $0.744$ zero-shot, against $0.805$ for `GAT-QoS` and $0.806$ for `GAT-P-QoS` (Table 10).

**Without the oracle-aligned features.** Every published learner reads features that compute part of what $I^*$ computes (§3.5). Zeroing all of them (in-degree, $w_{\text{in}}$, reverse PageRank, the articulation score, multi-path coupling, fan-out criticality and CDI; Table 8, F11) tests whether the representation gain is carried by those features. It is not. The raw-graph learners collapse without them (`GAT-QoS` to $0.369$, the reverse-edge control to $0.378$), whereas the dependency-graph GAT keeps $0.610$ and beats the reverse-edge control by $+0.231$ (10 of 12 folds, Holm $p = 0.0068$). The oracle-aligned set costs `GAT-P-QoS` $0.138$, about what the two degree columns alone cost ($0.136$), so the remaining features add little. With them removed, sum aggregation beats attention on the dependency graph ($+0.115$, 9 of 12 folds, Holm $p = 0.027$): once the count is not supplied as a feature, the aggregator that can count matters. Without any node features at all, a sum-aggregation GNN on the dependency graph reaches $0.719$, $0.045$ below `InDeg` (1 of 12 folds): from structure alone it learns most of the dependent count, which the derived graph makes available and the raw multigraph does not.

# 7. Discussion, Threats to Validity, and Limitations

## 7.1 Dependency Representation versus Model Complexity

The central finding of this study is that, for the reachability and queue-flow simulators, explicit dependency representations contributed more to ranking performance than model complexity. The derived dependency graph enabled both analytical and learned approaches. Attention-based learners improved on it relative to the raw multigraph, and the improvement survives a control that passes raw-graph edges in both directions (§6.2). It also survives the removal of every feature that computes part of the reachability simulator, without which the raw-graph learners collapse. Yet rankings computed directly from the same graph, the direct-dependent count for the reachability simulator and the rate-weighted first-order expansion for the queue-flow simulator, were not distinguishable from, or exceeded, the best learned models. Pure learners on the raw multigraph did not outperform the training-free baseline, because messages never reached the scored components. In this corpus, explicit dependency derivation is therefore the principal source of predictive signal, not a preprocessing step for learning. The multi-criteria simulator is the exception: there, raw degree and betweenness, whose terms align with fragmentation, ranked highest.

## 7.2 When Learning Adds Value, and Relative to What

The study does not show that learning is never useful; it shows where learning adds value and against which comparator. Relative to the training-free baseline, learning helped in two ways, both weak evidence for learning. Hybrids that correct a closed-form prior outperformed that baseline, also with its defect corrected, but not their own base learners, so the gain belongs to the baseline’s weakness rather than to the correction; given the direct-dependent count as their prior, they reproduce it. And learned models transferred zero-shot better than the baseline, mainly by separating inert from active components. Relative to analytical references built on the same dependencies, no learned model showed additional skill: the references were indistinguishable from or exceeded the learned models in-distribution, ranked higher in transfer, and ordering among components that actually propagate failures remained weak for every learned model ($\rho_{>0} \le 0.342$). The most direct test of learning beyond an aligned analytical ranking, learners that start from the rate-weighted approximation, found no improvement on it (§6.1). Learning is therefore likely to contribute most where impact depends on mechanisms that no available analytical approximation captures, a condition this corpus did not exercise. A per-regime breakdown by architecture type is given in Supplementary §S36.

**How message passing contributes.** On the raw multigraph, learning used node properties, not relations: gradient-boosted trees on the same per-node features and no graph (`GBM-Feat`) reach $\rho = 0.642$ under LOSO, similar to `GAT-QoS` ($0.635$); forward GAT convolutions send no message to Applications; and removing HGT’s reverse pass, its only route to them, has no effect. On the derived dependency graph, three layers of message passing gather the dependent neighborhood. Attention still needs the degree columns to approach the dependent count, whereas sum aggregation recovers most of it from structure alone (§6.2).

**What the study can say about relation typing.** Little. On the raw multigraph, where typing was compared at matched capacity, messages never reach Applications, so that comparison is between per-node models and carries no information about relational message passing (Supplementary Table S25). On the dependency graph, where messages do reach Applications, the projection has only two relation types, and the heterogeneous transformer (`HGT-P-QoS`) ran in one untuned configuration (width 100) in which some seeds converged to rankings anti-correlated with the oracle (mean within-fold seed standard deviation $0.254$, mean $\rho = 0.514$), while `GAT-P-QoS` was stable ($0.030$, $\rho = 0.748$). That is an optimization failure of one configuration, not evidence about typing; testing typing would need a substrate with active message passing and more relation types, and a tuned heterogeneous model.

**Why the learned queue-flow approximation does not exceed the formula.** The gradient-boosted approximation ($0.799$) beats the unweighted first-order expansion ($0.706$) because it reads the declared publication rates and payload sizes that $I_{\text{dyn}}$ uses. Once rates enter the analytical expansion (Eq. 7), it reaches $0.830$ and exceeds the learned approximation (exploratory), so the deficit is not one of missing inputs. Starting the learners from the formula does not help either: given it as an input, the tree model only matches it, and a GAT given it as a prior stays below it (§6.1).

## 7.3 Restatement versus Prediction

Several of the highest-scoring rankings largely restate a simulator’s propagation rule: the direct-dependent count and the first-order expansion for the reachability simulator, and the rate-weighted first-order approximation for the queue-flow simulator. The reference criterion (§4.4) distinguishes recovering a simulator’s definition from predicting its outcomes, and it changes how both analytical and learned results should be read. A learned model that approaches a reference has learned the simulator’s first-order rule, not necessarily anything beyond it. Because simulation-labeled benchmarks are common in architecture analysis, the criterion offers a general check for evaluations of this kind: before crediting a learned model with predictive skill, compare it against the simplest ranking that restates the simulator’s own computation.

## 7.4 Practical Consequences

**Choosing a ranker by simulator cost.** If the simulator is cheap, like $I^*$ ($0.01$–$0.72$ s per pass over a corpus architecture’s Applications), its ranking can be computed directly from the manifest, and publish–subscribe afferent coupling [61, 62], not distinguishable from any GNN tested, costs a fraction of that; its value is cost, not predictive skill, because it restates the simulator’s first wave. If the simulator is expensive, like $I_{\text{dyn}}$ ($12.7$ CPU-hours for the corpus), the rate-weighted expansion approximates it at $\rho = 0.830$ in milliseconds and exceeds a gradient-boosted approximation trained on its labels ($0.799$; exploratory). Neither simulator, nor any approximation of it, has been shown to predict real outages.

**Choosing a ranker by failure notion.** Table 12 summarizes the evidence by oracle. It is conditional on simulation fidelity: where a simulator misses a physical failure mode (partial partitions, disk thrashing), rankings on real clusters could diverge. For reachability impact, running $I^*$ itself is the simplest and cheapest option; no learned ranker is distinguishable from the direct-dependent count. For queue-flow impact, the rate-weighted expansion is the recommended ranker, and declared publication rates and payload sizes, not QoS policies, are the only declared information that carried signal. For fragmentation and throughput loss, betweenness-based scores rank highest because they align with the oracle’s terms. On unfamiliar topologies, learned rankers transfer better than the training-free baseline, but active-stratum agreement is weak and the evidence rests on five models by one author.

**Mitigating Alert Fatigue with a Two-Tiered Triage Protocol.** Using a top-20% threshold on the direct-dependent count (`InDeg`) recovers about half of the true top-20% set on $I^*$ ($0.49$), while the rest of the flagged items are not in that set; the best learned ranker does no better (`GAT-P-QoS`, $0.48$). Figure 5 shows the trade-off: recovering 80% of the critical set takes the top 45% by `InDeg` ($0.83$) or the top 40% by `GAT-P-QoS` ($0.81$), `Topo-QoS` does not reach this level within the top 50%, and no predictor reaches 90% within the top 50%. A gate that catches most critical components would flag nearly half the system, so these rankers are unsuitable as automated pass/fail filters.

We instead propose a two-tiered triage protocol as an inspection heuristic; it is a proposal that needs human-factors and workflow validation before adoption:

1.  **Tier 1 (Commit-stage triage):** When reviewing pull requests, compute the direct-dependent count (milliseconds, well under a joule) and the rate-weighted first-order expansion (Eq. 7; about a millisecond; an exploratory result, not confirmed on new data). Show the top 5 components by each as an informational note in the pull request review. This highlights potential cascade risks for peer review without blocking developers or causing alert fatigue.

2.  **Tier 2 (Staging and sprint verification):** During nightly builds or sprint architecture reviews, run the simulators on the Tier-1 shortlist within a fixed inspection budget, such as the ten highest-ranked services, and reserve redundant broker routing or chaos fault injection for the components the simulation confirms.

## 7.5 Threats to Validity

**Construct validity and oracle circularity.** All labels are simulated: no ranker is validated against observed failures, and no fault was injected into a running cluster, so the findings establish what can be predicted within the evaluated simulators, not what predicts real failures. The simulators omit runtime dynamics such as buffer bloat, thread-pool exhaustion, garbage-collection pauses and retry storms, and some real outages are sustained by load feedback rather than by structure [47, 48]; there, structural rankings, analytical or learned, may misestimate criticality. Validation on real topologies and real failures is therefore the first priority (§7.6). The circularity is analyzed in §4.4: the dependency counts restate $I^*$, the rate-weighted expansion restates $I_{\text{dyn}}$, closed-form centrality is term-aligned with $I_{\text{comp}}$, and the learned rankers inherit part of the overlap through the features they read and through being fitted to the oracle. The counts were reclassified as references after all results were final; no number changed. The two other oracles bound, but do not remove, the threat, and all three are well approximated by low-order functions of the dependency graph (a first-order expansion recovers $0.808$ of $I^*$ and a rate-weighted one $0.830$ of $I_{\text{dyn}}$), so the benchmark cannot exhibit a regime in which learning exceeds an aligned analytical ranking; its absence here is a property of these oracles, not evidence that none exists. The reverse-edge control shares one set of weights across both directions; a direction-typed variant was not tested. Rules 2–4 and 6, which govern brokers and hosts, are untested.

**Internal validity, reproducibility, and drift.** No ranker reads simulator output (regression tests verify this), although the raw-graph learners read the structural edges the oracles traverse. Capacity, depth and early stopping were held constant across comparison arms; the registered selection rule was not applied to the published learned results (§5.3), so every learned result is conditional on one fixed configuration. The learned rankers are seed-sensitive: the mean within-fold standard deviation of $\rho$ is $0.099$ for `HGT-QoS`, $0.254$ for `HGT-P-QoS` and $0.024$–$0.030$ for the GATs, and one of 60 `HGT-QoS` runs and four of 60 `HGT-P-QoS` runs converge to rankings anti-correlated with the oracle (none for either GAT). They are kept in the per-seed means, as registered, so the `HGT` rows reflect training instability as much as typing. Across revision cycles and compute devices, the absolute value of a learned cell drifted by up to $0.172$, so learned cells from different sweeps or devices should not be compared. Every learned-versus-learned contrast this paper tests is instead paired within one CPU sweep in which the re-run comparators reproduce their published per-seed $\rho$ (exactly, or within $1.2\times10^{-4}$ for one); the exception, the nested-selection check, compares two harnesses and is reported as a protocol comparison (§4.2). Paired contrasts were not repeated on a second device. Node order is a further source of variance: three permutations of the input order move `GAT-P-QoS` by about $0.04$ per fold around a mean $0.019$ below the published value (§6.2), so learned-ranker differences of that size are not interpretable. CDI uses hash-dependent tie-breaking, so `PYTHONHASHSEED=0` is fixed, and all reported values are reconciled mechanically against released artifacts.

**External validity and the single-modeler threat.** Synthetic topologies come from a single generator family, which may induce parametric regularities not representative of heterogeneous industrial architectures. The five system models are hand-authored approximations (22–41 Applications) of open-source projects, each written by the first author from public documentation. All five RQ3 results are exposed to this threat, and it is not mitigated: no second modeler authored any model independently, and no inter-modeler reliability or agreement metric is reported. The system models also differ structurally from the synthetic folds: a larger share of their Applications has zero simulated impact, and their fan-in is more concentrated, favoring `Reach` and inflating full-population $\rho$. Two of the five (Train-Ticket and Online Boutique) are RPC systems re-expressed as publish–subscribe meshes; the translation keeps bidirectional dataflow but drops synchronous blocking, timeouts and thread starvation. No topology in the study was extracted from a real deployment manifest. We did not evaluate architectures with tens of thousands of components; we timed the counting path up to $10{,}000$ components (§6.4), and we did not evaluate the learned rankers or the oracles. We did not reproduce published learned criticality models (FINDER, DrBC) because they do not support typed multigraphs or pub-sub semantics.

**Sustainability and energy estimation validity.** Energy figures (§6.4) are wall-clock time multiplied by the processor’s $28$ W base power (`reproduce/energy_estimate.py`), not readings from RAPL counters or power meters. They ignore frequency scaling, turbo power above base (up to $64$ W on this processor), DRAM and idle power, and attribute whole-package power to single-threaded work. They support order-of-magnitude comparisons between milliseconds and hours of computation, not energy or emissions accounting.

**Conclusion validity.** Only the plan’s two co-primary contrasts are confirmatory, and both were null (§5.3); everything else was designed after that result was known. LOSO folds share ten of eleven training scenarios, so Wilcoxon $p$-values are nominal and anti-conservative; the Nadeau–Bengio corrected test leaves the hybrid contrasts significant and the primary null. Twelve folds from one generator make the effective sample small, bootstrap CIs coarse, and the study underpowered for equivalence at $\pm 0.05$ (the $90\%$ interval of the `GAT-P-QoS`–`InDeg` difference is $\pm 0.076$); “matches” therefore means not significantly different. Weighting folds by $|V_{\text{app}}|$ raises `Topo-QoS` to the level of the raw-graph learned rankers.

## 7.6 Limitations and Future Work

Six directions follow from the study’s central question, in order of priority:

1.  **Real topologies and real failures:** automatic extraction of SaG models from real artifacts (ROS 2 launch files with HAROS or ROSDiscover [59, 60], docker-compose and Kubernetes manifests), so that the derivation is exercised on real manifests, followed by controlled fault injection on ROS 2, Kafka and MQTT deployments (for example with Chaos Mesh or ChaosBlade), reference systems with known faults such as Train-Ticket [33], and incident data from industrial publish–subscribe systems. This should be coupled with runtime distributed tracing standards (e.g., OpenTelemetry, W3C Trace Context) to empirically validate whether static declared dependency paths faithfully reflect dynamic runtime message flow trajectories under normal and degraded conditions.

2.  **A confirmation corpus:** scenarios generated after the analysis is frozen, on which the registered secondary and exploratory claims of this paper, all specified after the primary null, are re-tested.

3.  **Infrastructure and broker validation:** extending cascade-impact evaluation beyond Applications to message brokers, topics, and compute hosts (evaluating Rules 2–4 and 6), which were outside the Application-scoped evaluation of this study.

4.  **Independent modelers:** replication of the five system models by additional modelers, with inter-modeler agreement reported.

5.  **Alternative impact models:** testing whether the conclusions hold for simulators with different failure mechanisms, including synchronous call semantics, which the current dependency rules do not model, and oracles with non-first-order mechanisms such as backpressure onto publishers, retry amplification and heterogeneous service capacity, where an aligned analytical approximation may not exist.

6.  **When learning exceeds analytical methods:** identifying impact-generation mechanisms whose predictive signal no aligned analytical approximation captures, and testing learners there; in this corpus, learners started from the rate-weighted approximation did not improve on it.

Further extensions are integration with service mesh telemetry and distributed tracing (e.g., OpenTelemetry, Jaeger) for runtime dependency drift detection; hardware-measured energy accounting (RAPL counters required privileges unavailable for this study); a queue-flow run with QoS policies disabled; a tie-aware listwise loss with scenario-level validation; a full hyperparameter search for every learned model; and validation of the proposed explanation layer.

# 8. Conclusion

This paper presented Software-as-a-Graph (SaG), a pre-deployment framework that derives explicit dependency graphs from publish–subscribe deployment manifests and supports analytical, hybrid, and learned approaches to cascade-impact ranking. Using twelve synthetic architectures, three failure simulators and five stylized models of open-source systems, the study examined when graph learning improves on rankings derived directly from explicit architectural dependencies. The primary registered contrast was null, and the findings below are registered secondary or exploratory.

For the reachability and queue-flow simulators, explicit dependency representations provided most of the predictive signal. Attention-based learners benefited from the derived dependency graph, and that gain survives a control for edge direction, and the removal of every feature that computes part of the reachability simulator, but simple analytical rankings built on the same dependencies were not distinguishable from, or exceeded, every learned model: counting direct dependents on the reachability simulator, and a rate-weighted first-order expansion, computed in milliseconds, on the queue-flow simulator, whose labels took $12.7$ CPU-hours to generate. Learners that start from the rate-weighted approximation matched it at best.

Learning added value only relative to a weak comparator: hybrids beat the training-free baseline, which they nest, but not their own base learners, and learned models transferred zero-shot better than that baseline, while dependency-based references remained stronger and ordering among components that actually propagate failures remained weak. For researchers, the results show why graph-learning approaches should be evaluated against analytical alternatives aligned with the simulator, and why prediction should be distinguished from restatement of a simulator’s rule. For practitioners, training-free dependency analysis is effective and inexpensive support for prioritizing architectural review. Learned models can be expected to add value only where no aligned analytical approximation exists; all three simulators here admit one, so this corpus could not exercise that condition.

These findings concern simulated failures on synthetic architectures and single-modeler system models, and their validation against real outages is the natural next step (§7.6). More broadly, the study suggests that the central challenge in architecture-level cascade-impact analysis is not selecting increasingly sophisticated learning algorithms, but deriving meaningful dependency representations and understanding when learning adds value beyond them. By making this comparison explicit and by releasing a reproducible benchmark with reconciled results, Software-as-a-Graph provides a foundation for more principled evaluation of analytical and learned methods for pre-deployment architecture analysis.
