# Abstract

Publish–subscribe middleware obscures the paths through which failures propagate, yet architects must identify critical components before deployment, when no telemetry exists. We present Software-as-a-Graph (SaG), which derives explicit dependency graphs from deployment manifests to evaluate when graph learning improves cascade-impact ranking. We compare graph neural networks, hybrids, and analytical and learned simulator approximations with training-free rankings on twelve synthetic architectures under leave-one-scenario-out evaluation against three failure simulators, and zero-shot on five hand-authored models of open-source systems. A reference criterion distinguishes rankings that restate a simulator’s propagation rule from those that predict it.

While the primary registered contrast was null, graph attention on the derived dependency graph reaches Spearman’s $\rho = 0.748$ against a reachability simulator, whereas pure learned models on the raw multigraph do not outperform a training-free baseline. The learned model is not statistically distinguishable from counting direct dependents ($\rho = 0.764$), though equivalence within $\pm 0.05$ is not established. For a queue-flow simulator requiring $12.7$ CPU-hours to label the corpus, a rate-weighted first-order approximation reaches $\rho = 0.830$ in milliseconds, rivaling a learned approximation trained on simulator labels ($\rho = 0.799$). Hybrids correcting a closed-form prior outperform that baseline, and learned models transfer zero-shot better than it ($\rho \approx 0.81$ vs. $0.53$), driven by separating inert components.

All findings evaluate pre-deployment surrogate approximation of topological simulators rather than physical failure prediction. Representation mattered more than model complexity, highlighting the importance of evaluating learned methods against analytical baselines aligned with the simulator.

**Keywords:** Dependency graphs; cascading failures; publish–subscribe; graph representation learning; software architecture; dependability; empirical study

# 1. Introduction

## 1.1 Motivation and Problem

Large distributed systems now often use asynchronous publish-subscribe (pub-sub) middleware. Examples include ROS 2 for autonomous driving [1], Apache Kafka for enterprise event streams [2], DDS in cyber-physical systems [3], MQTT in IoT [4], and cloud-native microservices [5, 6]. Pub-sub separates producers and consumers by space, time, and synchronization [7]. Instead of direct references, components communicate via topics and brokers, and Quality-of-Service (QoS) policies set at deployment control reliability, durability, priority, and deadlines.

This decoupling also makes it harder to see how failures spread. Since publishers and subscribers are not directly connected, problems like outages, blocking, and backpressure can move through undetected paths involving brokers, shared topics, colocated hosts, and shared libraries [8, 9]. Failures usually appear in two ways. In sequential cascades, a slow subscriber fills up a broker queue and gradually starves its publishers [10]. In simultaneous blasts, a crash in a shared library or a host outage can bring down all colocated services at once. These issues are not visible in architecture diagrams or static call graphs. The best time to handle these risks is before deployment, during design and continuous integration [11, 12], when runtime telemetry is unavailable. Therefore, architects must identify the most critical application services, topics, and links using only configuration manifests.

Current practices leave a serious architectural gap between service-level static analysis and distributed system dependability. A distributed system might have no compile-time bugs in any service but still face major outages due to hidden single points of failure, unbuffered queue bottlenecks, or mismatched QoS contracts [13, 14]. Approaches like the Architecture Tradeoff Analysis Method (ATAM) depend on manual input [15]. Static code analysis inspects services in isolation [16, 17]. Chaos engineering [18] needs a working cluster, and pre-production tests like fault injection [19] and dependency tracing [20] require runnable environments. In continuous integration, heavy fault injection or chaos experiments use significant computing power and energy, so pre-deployment static analysis is a greener option if it is accurate enough [21, 22, 23]. Graph-based representations have long supported reliability and defect analysis [24, 25], and graph learning has recently been applied to network criticality [26, 27] and to microservice architectures [28]. Such models can combine structural and contractual information, but it remains unclear whether their predictive performance arises from the learning algorithm or from the dependency representation it operates on, and when learning adds value beyond analytical methods derived from the same dependencies. Software-as-a-Graph (SaG) addresses this question by deriving explicit dependency graphs from deployment manifests and enabling a controlled comparison of analytical, hybrid and learned approaches to cascade-impact ranking before deployment.

## 1.2 The Software-as-a-Graph (SaG) Approach

Software-as-a-Graph (SaG) is a pre-deployment analysis framework for event-driven architectures (Figure 1). It models an architecture as a typed, directed multigraph over Applications, Brokers, Topics, Execution Hosts and Shared Libraries (§3.1), and derives an explicit DEPENDS\_ON dependency graph through publish–subscribe rules (§3.3). On this basis, it supports analytical, hybrid and learned approaches to cascade-impact ranking (§§4 and 5.2). This study uses it to determine when learned models add value beyond rankings derived directly from explicit dependencies.

Rankers read only the analysis graph. Labels come from three simulators that run on the raw structural topology (§4.3) and encode different failure notions: structural reachability ($I^*$), discrete-event queue saturation ($I_{\text{dyn}}$) and multi-criteria fragmentation ($I_{\text{comp}}$). To avoid depending on one simulator’s assumptions, every ranker is evaluated against all three. Because simulators and rankers read the same architecture, some analytical rankings restate a simulator’s own propagation rule. A reference criterion (§4.4) reports these as references that measure circularity rather than as predictors. To bound, though not remove, this circularity, we also report partial correlations after removing the primary simulator, and we time the cost of running each simulator directly (§6.4). All conclusions are strictly conditional on simulation fidelity; validation against real failures in physical distributed environments remains future work (§7.5).

**Organization of the empirical inquiry.** To evaluate when graph learning adds value, we compare learned GNNs and gradient-boosted trees against both training-free baselines and analytical references across three failure simulators. By evaluating models across raw structural topologies and derived dependency graphs, the study isolates the contribution of explicit dependency representation from learning algorithm complexity, while timing and power profiling contextualize the cost of static triage versus full simulation in continuous integration pipelines.

## 1.3 Research Questions

Establishing when learning is unnecessary is as informative as showing when it succeeds. Software engineering research has repeatedly found that simple metrics can match more complex models once the right information is available [25, 29, 30, 31], and that analytical rankings are easier to explain, validate, and run in Continuous Integration and Continuous Deployment (CI/CD) pipelines. We therefore evaluate learned models against analytical rankings derived from the same dependencies, not only against structural baselines. Four research questions guide the study:

-   **RQ1 (Ranking accuracy):** *How accurately do analytical, hybrid, and learned approaches rank components by cascading-failure impact on unseen architectures, and how close do they come to reference rankings that restate a simulator’s propagation rule?*

-   **RQ2 (Sources of predictive performance):** *At matched model capacity, which factors contribute most to ranking performance: the dependency representation, degree information, relation typing, Quality-of-Service (QoS) information, or the model family (attention or sum aggregation; graph neural network or gradient-boosted trees)?*

-   **RQ3 (Transfer):** *How well do learned models trained on synthetic architectures transfer zero-shot to stylized models of five open-source systems, hand-authored by a single modeler, and does their ordering of components that actually propagate failures hold?*

-   **RQ4 (Cost):** *What do analytical and learned approaches cost at CI/CD time in latency and estimated energy, which stage dominates, and how does this compare with running each simulator directly?*

The evaluation uses a version-controlled analysis plan. Only two contrasts in the plan are confirmatory. We registered the matched $2\times2$, the hybrids, the reference counts, the dependency-graph learners, the full-population queue-flow labels, and the sensitivity arms as planned extensions. We registered each before its own tests ran but after we knew the main result, and we report them as secondary results. The rest of the analysis is exploratory (§5.3). One change from the plan, not applying the registered nested hyperparameter selection, is disclosed and tested. The replication repository records the revision history and shows how these four research questions fit into the plan.

## 1.4 Contributions

Evaluated with leave-one-scenario-out (LOSO) cross-validation on twelve synthetic architectures, against three failure simulators, and zero-shot on five hand-authored models of open-source systems, this paper makes five contributions:

1.  **Explicit dependency derivation for publish–subscribe architectures** (§3). Typed rules derive dependency graphs from deployment manifests and expose sequential cascades through shared topics and simultaneous blasts through shared libraries. The derived graph is the main source of predictive signal: attention-based learners improve on it compared with the raw multigraph (`GAT-P-QoS` $0.748$ vs. `GAT-QoS` $0.635$), and its library-mediated rule adds $+0.058$ in transitive reach. We define infrastructure and colocation rules for completeness, while focusing our empirical evaluation strictly on developer-authored Application services.

2.  **A reference criterion for interpreting simulator-based evaluations** (§4.4). The criterion distinguishes rankings that restate a simulator’s rule from rankings that predict it, so that analytical and learned methods can be interpreted on the same terms. Applied here, it shows that publish–subscribe afferent coupling recovers most of the reachability simulator.

3.  **A controlled study of when graph learning adds value beyond dependency analysis** (§§6.1–6.3). Matched-capacity comparisons and ablations separate the contributions of five factors: the dependency representation, which matters most; degree information, without which the learner loses $0.136$; relation typing, which has no effect; QoS information, where declared rates and payloads add signal only on the queue-flow simulator and QoS policies or QoS-weighted scores add none (revealing that declared QoS contracts carry negligible predictive utility for cascade ranking); and the model family. Hybrids that correct a closed-form prior significantly outperform the training-free baseline, but they transfer less well than pure learned models.

4.  **Analytical and learned approximations of an expensive simulator** (§§5.2 and 6.1). On a queue-flow simulator that takes $12.7$ CPU-hours to label the corpus, a rate-weighted first-order approximation reaches $\rho = 0.830$ in milliseconds without training, rivaling or exceeding a gradient-boosted approximation trained on the simulator’s labels ($0.799$; exploratory, added after the registered analyses).

5.  **A reproducible benchmark, cost analysis and practitioner guidance** (§§5, 6.4 and 7.4).

    -   The benchmark comprises seventeen architectures (2,812 components), three simulators labeling all 1,321 synthetic Applications, a version-controlled analysis plan with disclosed amendments, byte-identically regenerable datasets, and mechanically reconciled results.

    -   Latencies measured on the same graphs, with coarse Thermal Design Power (TDP)-derived energy estimates, support practical guidance on when training-free dependency analysis suffices.

A previous conference paper [32] introduced the publish–subscribe multigraph, the Application-level subscriber-to-publisher dependency (Rule 1 of Table 2), and a closed-form betweenness–articulation score similar to the training-free baseline (Eq. 5, unweighted and with weights $0.7$/$0.3$), which it validated against a reachability-loss simulation on synthetic topologies and two ROS 2 benchmarks. This paper adds the Library and infrastructure rules, QoS weighting and the QoS edge encoding, the reference criterion, the learned and hybrid rankers, the analytical and learned simulator approximations, LOSO and zero-shot evaluation, the second and third oracles, the matched control, and the cost analysis.

§2 reviews related work. §§3 and 4 present the model and the rankers. §§5 and 6 cover the evaluation. §7 discusses the findings and threats, and §8 concludes.

# 2. Related Work

## 2.1 Dependability Analysis of Distributed Systems

Runtime dependability methods like broker clustering, backpressure, autoscaling, failover, and chaos engineering [18] require a running cluster, can interrupt service, and consume significant computing resources. This resource use is a major concern in green software engineering and Green AI [21, 22, 23], where the carbon footprint of large execution clusters in continuous integration encourages lightweight, energy-efficient static alternatives. Pre-production methods, such as service-level fault injection testing [19] and microservice dependency localization with PageRank (MicroRank [20]), offer lighter options before deployment. Benchmark platforms with cataloged, replayable faults, like Train-Ticket [33], help measure the impact of failures on a running deployment, which this study has not yet validated (§7.6). Architecture-based reliability prediction has a long history. Yacoub and Ammar’s method for architecture-level reliability risk analysis [24] was one of the first to combine component dependency graphs with complexity and failure severity to rank components by risk. State, path, and additive reliability models reviewed by Goseva-Popstojanova and Trivedi [34] are classic examples, as is the Palladio Component Model [35].

Architectural error propagation analysis has a rich foundation in software metrics and component-based reliability. Abdelmoez et al. [36] formalized error propagation across software architectural components, and Popic and Goseva-Popstojanova [37] modeled error propagation probabilities in component-based dependability. Cortellessa and Grassi [38] analyzed error propagation impact on component reliability, while Hiller et al. [39] introduced the EPIC framework for architecture-level failure propagation. In safety-critical systems, model-based failure analysis is standard practice, including Hierarchically Performed Hazard Origin and Propagation Studies (HiP-HOPS [40]) and the Architecture Analysis & Design Language (AADL) Error Model Annex [41]. These frameworks derive propagation paths from structural descriptions, serving as conceptual precursors to SaG’s dependency projection. However, classic approaches require operational profiles or fault matrices unavailable at commit time; SaG asks a narrower question using only deployment manifests.

Telemetry-based methods find faults in running microservices. Examples include Seer [42], MicroRCA [43], and recent GNN-based root-cause frameworks like Eadro [44], which Zhang et al. [45] thoroughly review. In synchronous microservices, failures can spread because of thread-pool exhaustion, RPC timeouts, and retry storms [33]. In publish-subscribe systems, issues spread through queue saturation and message starvation. All these methods need data from a live system, but SaG works before any code is run. SaG’s focus is similar to change impact analysis [46] and dependency management in microservice fleets [47]. Ranking by impact is related to learning-to-rank defect prediction [48], which explicitly optimizes the ranking measure, as our listwise loss does (§4.2).

## 2.2 Static Code Analysis and Static System Analysis

Static code analysis (SCA) tools like SonarQube [16] measure complexity [49], cohesion, and coupling [17] within individual services to identify modules likely to have defects [50, 51]. Software engineering defect prediction has long compared advanced graph measures with simple structural metrics. For example, Zimmermann and Nagappan [25] studied network analysis on dependency graphs, while Premraj and Herzig’s replication study [29] showed that simple code and coupling metrics frequently perform as well as network measures. SCA cannot detect inter-service messaging, broker saturation, or issues that spread across hosts. Architecture recovery tools rebuild system-level structure from code [52], and HAROS [53] checks ROS systems before launch. SaG’s static system analysis (SSA) uses the declared topology instead, spreading code-level metrics across architectural dependencies. Architecture-level coupling metrics count a service’s consumers, such as afferent coupling [54], the Absolute Importance of the Service [55], and service fan-in [56]. In publish–subscribe systems, these counts are not simply a single edge lookup, since consumers reach producers only via topics, brokers, and shared libraries. They require a typed two-hop query (publisher to topic to subscriber), which SaG’s dependency rules define clearly. Because this count corresponds to the first propagation wave of the reachability oracle used here, this paper reports it as a reference that restates the oracle, not as a predictor (§4.4). This helps teams find structural anti-patterns [57, 58] and architectural technical debt [59] in CI/CD [60].

## 2.3 Multi-Criteria Weighting

Combining QoS policies or failure effects into a single, auditable weight is a multi-criteria decision problem. The Analytic Hierarchy Process (AHP) [61] is the standard method, and SaG uses it for the topic weights in §3.2 and the composite oracle in §4.3. AHP’s consistency ratio can find inconsistent judgments, but it does not detect matrices that have been filled in to match a chosen answer. This study notes that distinction for its weights.

## 2.4 Graph Learning and Explainability

Closed-form indices [62, 63, 64, 65], including one used as this study’s training-free baseline, and cascade models of network robustness [10, 8, 9] assume homogeneous, usually undirected graphs. This means a single untyped score can mix up different elements like topics, libraries, and hosts. Learned node-importance methods, such as FINDER [26], DrBC [27], and PowerGraph [66], also assume homogeneity, as does learned approximation of betweenness and closeness [67]. Homogeneous GNNs like Graph Attention Networks (GAT [68]) ignore relation identity unless it is added as a feature. Softmax attention averages over neighbors and cannot count them, while sum aggregation can [69, 70]; theoretically, standard message-passing GNNs are strictly limited in counting substructures without explicit features [71]. Since the main reference here is neighbor count, this difference matters (§6.2). Heterogeneous GNNs, like the Heterogeneous Graph Transformer (HGT [72]), learn transformations specific to each relation. However, extensive benchmarking by Lv et al. [73] demonstrated that heterogeneous GNNs often fail to outperform well-tuned homogeneous baselines like GAT, directly paralleling our typing ablation findings. More broadly, Shchur et al. [74] highlighted severe evaluation pitfalls and data-split sensitivity in GNN benchmarking, while Huang et al. [75] showed that simple label propagation and shallow models frequently exceed complex GNNs across network tasks. We test both types with the same capacity (§6.2). Khodabandeh et al. [28] use graph attention on microservice call graphs to predict upcoming interactions. In contrast, we predict the effect of removing a node from a declared topology. GNN explainers like GNNExplainer [76] describe models using their internal features. SaG’s explanation layer instead names ISO/IEC 25010 quality sub-characteristics [77] and a remediation class for each flagged component, but this is not evaluated here.

This study aligns with research showing that simple baselines perform as well as more advanced learning methods [30, 31]. In software engineering, it also supports findings that network measures on dependency graphs [25] add little value over simple coupling metrics once those are included [29]. Crucially, in line with Green Software Engineering and Green AI principles [21, 22, 23], complex deep learning architectures in continuous integration pipelines must be justified against the latency, carbon footprint, and energy costs of simple static heuristics. Following rigorous statistical testing guidelines in empirical software engineering [78], we report paired non-parametric tests, effect sizes with confidence intervals, and multiple-testing corrections throughout. The main contribution here is an evaluation of learning on derived dependency graphs for a pre-deployment ranking task. On the two oracles for which a closed-form first-order expansion exists, that expansion, or a known architecture metric built on the same dependencies, matches or exceeds every learned model, including one trained on the costly oracle’s own labels.

# 3. The Software-as-a-Graph (SaG) Architectural Model

Figure 1 shows the full SaG framework architecture. The shared front end handles Architecture-as-Code manifests, builds a typed multigraph, derives a logical dependency layer that makes runtime failure paths explicit, and extracts typed node properties. This representation supports graph-learning pipelines and makes software dependencies explicit, so analytical, hybrid, and learned cascade-impact rankings can be computed from the same architectural representation (§§4 and 5.2). This common representation enables controlled comparisons between methods that differ in complexity but operate on identical dependency information. The proposed explanation layer reads the same properties separately, with no shared parameters.

## 3.1 Multigraph Definition

A distributed system is described as a typed, weighted, directed multigraph:

$$\tag{1}
\mathcal{G} = (V, E, \tau_V, \tau_E, w_V, w_E)$$

where:

-   $V = V_{\text{app}} \cup V_{\text{broker}} \cup V_{\text{topic}} \cup V_{\text{host}} \cup V_{\text{lib}}$ holds the five entity types $\mathcal{T}_V$ of Table 1; $V_{\text{host}}$ denotes physical or virtual *Execution Hosts*.

-   $E$ is the set of directed edges, and $\tau_V: V \to \mathcal{T}_V$ and $\tau_E: E \to \mathcal{T}_E$ assign entity and relation types.

-   $w_V: V \to (0, 1]$ and $w_E: E \to (0, 1]$ weight entity criticality along with connection strength. In the multi-layer metamodel, $w_V(v) = 1 - \text{CQP}(v)$ incorporates static code quality penalties for Applications and Libraries; in the empirical benchmarks reported here, $w_V(v) = 1.0$ is held across all components to focus strictly on architectural topology.

The raw multigraph is denoted $G_{\text{structural}}$ (used exclusively by simulation oracles), while $G_{\text{analysis}}$ denotes the logical `DEPENDS_ON` projection from which all rankers, analytical and learned, are computed. A comprehensive reference of mathematical notation is provided in the replication repository.

**Scope of Evaluation and Entity Roles.** While the multigraph formalizes five entity types, this study concentrates its empirical study specifically on *Applications* ($V_{\text{app}}$). In this work, the term *Application* is adopted to align with publish–subscribe standards (such as OMG DDS and ROS 2 participant nodes); conceptually, it corresponds directly to individual microservice containers, autonomous service agents, or communicating daemon processes in distributed architectures. Applications represent the developer-authored, code-level services that are often changed, refactored, and tested in CI/CD pipelines, so they are the main focus for pre-deployment triage. Brokers, Topics, Execution Hosts, and Libraries are also modeled and included because they are important for understanding indirect failure propagation. For example, we cannot analyze message routing, shared fault-domain colocation, or library-related failures without them. However, ranking infrastructure components like Brokers and Hosts is more relevant to operational provisioning than to software triage at commit time, so we treat this as a separate operational issue. Consequently, the empirical evaluation in this paper focuses strictly on ranking developer-authored Applications ($V_{\text{app}}$); evaluating broker queue bottlenecks and physical host outages remains an important operational extension (§7.6).

**Table 1.** Entity types and structural edge types in the SaG model.

| **Entity Type ($\mathcal{T}_V$)**      | **Architectural Role**                        | **Concrete System Examples**                   |
|:---------------------------------------|:----------------------------------------------|:-----------------------------------------------|
| **Application** ($V_{\text{app}}$)     | Process producing/consuming messages          | ROS 2 node, Kafka microservice, MQTT client    |
| **Broker** ($V_{\text{broker}}$)       | Message routing and queuing intermediary      | RabbitMQ exchange, Mosquitto, EMQX broker      |
| **Topic** ($V_{\text{topic}}$)         | Named logical communication channel           | `/sensor/lidar`, `orders.payment.completed`    |
| **Execution Host** ($V_{\text{host}}$) | Physical or virtualized execution environment | Bare-metal server, Kubernetes worker, Cloud VM |
| **Library** ($V_{\text{lib}}$)         | Shared software package or runtime dependency | Kafka client, OpenCV, Protobuf runtime         |
| **Structural Edge ($\mathcal{T}_E$)**  | **Direction**                                 | **Semantic Meaning**                           |
| `PUBLISHES_TO` / `SUBSCRIBES_TO`       | App/Library $\to$ Topic                       | Component publishes to / consumes from topic   |
| `ROUTES`                               | Broker $\to$ Topic                            | Broker manages and routes topic traffic        |
| `RUNS_ON`                              | App/Broker $\to$ Host                         | Process is hosted on host                      |
| `CONNECTS_TO`                          | Host $\to$ Host                               | Network link between hosts                     |
| `USES`                                 | App $\to$ Library                             | Application links to shared library            |

## 3.2 Quality-of-Service Link Weighting

A link’s strength is conceptually determined by its Quality-of-Service (QoS) contract. For example, a `RELIABLE` topic with `TRANSIENT_LOCAL` durability creates a stronger connection between services than a `BEST_EFFORT` telemetry stream. Each topic $t$ has an overall weight $w(t) \in (0, 1]$ that combines its QoS policies (reliability, durability, priority) with payload size and publication frequency. We set the reliability, durability, and priority weights employing an Analytic Hierarchy Process (AHP) pairwise-comparison matrix, which we defined independently and did not adjust to fit a target vector ($CR = 0.016$, non-degenerate; the framework’s other AHP matrices also use a declared vector).

Although we formalize this multi-criteria weighting to capture declared middleware contracts, the evaluation in §6 tests whether this contractual information improves cascade ranking. It does not: on the reachability and queue-flow simulators, declared QoS policy parameters carried no measurable signal. On the reachability oracle, more than half of the apparent QoS effect came from the QoS-weighted in-degree feature, and the remainder was not significant (§6.2). On the queue-flow oracle, the gains came from declared publication rates and payload sizes, while QoS-policy shares added $-0.005$ ($p = 0.68$; §6.1). We retain the full AHP formalization for architectural completeness and reproducibility; in this corpus, omitting QoS policy weighting did not reduce ranking accuracy. The dependency counts reported in this paper are unweighted and do not use $w(t)$.

## 3.3 Logical Dependency Projection (`DEPENDS_ON`)

Structural edges do not directly show how failures spread. For example, a subscriber depends on a publisher, but pub-sub topologies have no direct edge between them. SaG therefore derives an explicit semantic relation, `DEPENDS_ON`, from the dependent to the dependency: if the target fails, the source is affected. The derived edges expose the architectural pathways through which failures may propagate, and the resulting dependency graph is the common input for analytical rankings, hybrid methods, and graph-learning models. Table 2 lists the rules.

**Table 2.** The `DEPENDS_ON` logical dependency projection rules. $^\dagger$Defined for completeness; not exercised by the Application-level evaluation.

|    **Rule**     | **Dependency Category** | **Structural Pattern ($\text{Dependent} \to \text{Dependency}$)**           | **Derived Weight ($w$)**                                                 |
|:---------------:|:------------------------|:----------------------------------------------------------------------------|:-------------------------------------------------------------------------|
|      **1**      | `app_to_app`            | Subscriber $\to$ Publisher (via shared Topic)                               | $1 - \prod_{t \in T}(1 - w(t))$                                          |
| **2**$^\dagger$ | `app_to_broker`         | Publisher/Subscriber $\to$ Broker routing its topics                        | $1 - \prod_{t \in T}(1 - w(t))$                                          |
| **3**$^\dagger$ | `host_to_host`          | Host $\to$ Host (lifted from inter-host app dependencies)                   | $\max_{u \in \text{hosted}(h_1), v \in \text{hosted}(h_2)} w_E(u \to v)$ |
| **4**$^\dagger$ | `host_to_broker`        | Host $\to$ Broker (lifted from hosted app dependencies)                     | $\max_{u \in \text{hosted}(h)} w_E(u \to b)$                             |
|      **5**      | `app_to_lib`            | Application $\to$ Shared Library it `USES`                                  | $H(w_V(\text{app}), w_V(\text{lib}))$                                    |
| **6**$^\dagger$ | `broker_to_broker`      | Broker $\leftrightarrow$ Broker (shared fault-domain colocation, symmetric) | $w_V(\text{host})$                                                       |

Rules 1 and 2 combine topics $T$ that connect a pair using probabilistic union [79], so that having multiple failure paths increases the connection strength. Rule 5 uses the harmonic mean $H(x, y) = 2xy/(x+y)$ [80]. Rules 3 and 4 assign dependencies to hosts by taking the maximum value.

**Sequential cascades and simultaneous blasts.** Rule 1 describes sequential cascades, where if a publisher fails, its subscribers are affected because they do not receive messages. Rule 5 describes simultaneous blasts, where if a library crashes, all applications that depend on it fail at the same time. Neither mechanism is stated explicitly in a deployment manifest; each rule makes one of them visible. Shared-library dependencies are included because they create simultaneous blast failures that message-flow topology alone does not represent. Libraries that publish or subscribe are also endpoints for Rule 1, and an Application can reach a library’s topics through Rule 5. For counting, `Topo-QoS` and all `-P` learners use Rule 1 only for direct subscriptions. The repository’s method for creating node properties also follows up to three `USES` links, so if an Application subscribes through a library it uses, it is considered a Rule 1 dependent. Rules 2, 3, 4, and 6 cover infrastructure and broker dependencies (see Table 2), which define physical host failure domains and broker routing bottlenecks. Since this evaluation focuses on Application-level code, these four rules are not used in the ranking benchmarks but are included for completeness.

**Remark 1 (the dependency count is a typed two-hop count).** Let $G_{\text{flow}}$ be the Application–Library projection (Rules 1 and 5) and $v$ an Application. By construction, $$\tag{2}
\texttt{InDeg}(v) \;=\; \bigl|\{\,u \neq v : \exists t \in V_{\text{topic}},\; (v, t) \in \texttt{PUBLISHES\_TO} \wedge (u, t) \in \texttt{SUBSCRIBES\_TO}\,\}\bigr|.$$ Since Rule 5 edges end at Libraries, every edge into an Application is a Rule 1 edge $u \to v$, which exists exactly when $u \neq v$ (an Application or a Library) directly subscribes to a topic that $v$ publishes; in the presence of multiple parallel topics between the same pair, parallel topics collapse into a single directed dependency edge in $G_{\text{flow}}$.

The right side of Eq. 2 represents publish–subscribe afferent coupling (fan-in, or the Absolute Importance of the Service [54, 55]), and is a typed two-hop query on the raw multigraph. `InDeg` can be computed directly without projection; the projection defines which typed query to use. We checked this equality on all seventeen corpus graphs, with a maximum absolute difference of $0$. We measure the value of the derivation separately: including Rule 5 raises the agreement of transitive reach with $I^*$ by $+0.058$ (9 of 12 folds, Holm $p = 0.0068$; §6.1). Since the primary oracle’s first propagation wave matches this set (§4.4), `InDeg` and its transitive version `Reach` are used as reference points in this paper, not as predictors.

Simulation oracles run on view (a); all rankers, analytical and learned, read view (b).*

## 3.4 Dual Graph Views

The **structural graph** $G_{\text{structural}}$ is the raw deployment topology. The **analysis graph** $G_{\text{analysis}}$ adds the `DEPENDS_ON` edges and code metrics (see Figure 2). All ranker inputs are computed on $G_{\text{analysis}}$, while simulation oracles run strictly on $G_{\text{structural}}$ (§4.4). The two views also differ for a learner: on $G_{\text{structural}}$, every relation points away from Applications, so forward message passing does not reach them. In the `DEPENDS_ON` graph, each Application receives messages from its dependents (§6.2). The raw multigraph is therefore also a comparison point in the evaluation: it exposes communication structure but not cascading dependencies, which allows the effect of the representation to be separated from the effect of the learning architecture (§6.2).

## 3.5 Typed Node Feature Encoding

Both the ranking pathway (§4) and the proposed explanation layer use typed node properties from $G_{\text{analysis}}$. All five entity types share a base set of 18 normalized topological metrics (ranging from $[0, 1]$): PageRank, Reverse PageRank, betweenness, closeness, eigenvector centrality, in-degree, out-degree, clustering, articulation, bridge ratio, node QoS weight, incoming and outgoing dependency weights, multi-path coupling, path complexity, fan-out criticality, and the Connectivity Degradation Index (CDI). We calculate four centrality features (PageRank, Reverse PageRank, betweenness, and closeness) over weighted edges, so they include QoS information. This means the so-called QoS-off condition is not entirely free of QoS effects. The in-degree feature and the incoming dependency weight $w_{\text{in}}$ (a QoS-weighted version) ensure that all learners receive information closely related to `InDeg`, so the learners inherit some overlap with the oracle’s reference counts (§6.2). We did not use any learner missing both columns. Type-specific blocks add more features, extending the vector to 19–25 dimensions (the full schema is in the replication repository). CDI measures structural connectivity loss using a fixed-scale breadth-first sample to keep computation time reasonable (§6.4). We discuss its sensitivity to hash-seeded tie-breaking in §7.5.

In this study, SaG therefore serves two roles. It provides a dependency representation from which analytical rankings can be computed directly, and it provides a graph on which learned and hybrid methods operate. The evaluation in §§5–7 examines how much ranking performance arises from this representation and how much from the models applied to it.

# 4. Ranking Methods, Simulation Oracles, and the Reference Criterion

This study evaluates three categories of ranking methods: analytical rankings derived directly from dependency structure, hybrid methods that combine an analytical prior with a learned correction, and learned methods that infer rankings from graph representations. The training-free baseline, `Topo-QoS`, applies QoS-weighted betweenness to the dependency graph, and §5.2 defines the analytical references. The learned methods use graph neural networks on the typed multigraph and the dependency graph, and gradient-boosted models with per-Application dependency-graph features (§§4.1–4.2 and 5.2). Hybrid methods adjust the `Topo-QoS` score with a learned correction (Figure 3). All methods are trained on or evaluated against simulation oracles that run on a separate graph view (§4.3). Because several rankings are derived from the same failure-propagation assumptions the simulators use, the evaluation distinguishes rankings that restate a simulator’s rule from those that predict its outcomes (§4.4). Figure 3 illustrates the methods and their evaluation; full hyperparameters and training commands are in the experiment pages of the replication repository (§5.1).

## 4.1 Heterogeneous Graph Transformer and Attention Networks

The main learned ranker, `HGT-QoS`, is a three-layer Heterogeneous Graph Transformer (HGT) [72] built with PyTorch Geometric [81]. It uses a hidden dimension of $D=64$ and $H=4$ heads. Entity-specific linear projections map raw node features $x_v \in \mathbb{R}^{19\text{--}25}$ into the hidden space, with $h_v^{(0)} = \text{LayerNorm}(\text{GELU}(W_{\tau(v)} x_v))$. For each meta-relation $\langle \tau(u), \phi(e), \tau(v)\rangle$, attention uses type-parameterized keys, queries, and values, scaled by a learned per-meta-relation prior $\mu_{\langle \tau(u), \phi(e), \tau(v)\rangle}$; full layer-wise formulations are in the replication repository. Message passing runs over both $G_{\text{analysis}}$ and its transpose. In the raw multigraph $G_{\text{structural}}$, native relations point away from Applications (e.g., `PUBLISHES_TO`, `RUNS_ON`, `USES`), so forward message passing cannot propagate messages to the scored Application nodes. As a result, forward GNNs on $G_{\text{structural}}$ collapse structurally into per-node MLPs operating over precomputed centrality features (§7.2). In contrast, the derived dependency graph $G_{\text{analysis}}$ explicitly directs edges from dependents to dependencies, allowing forward message passing to aggregate information from downstream consumers. The homogeneous Graph Attention Network (`GAT-QoS`, and `GAT-P-QoS` on the dependency graph) uses a three-layer architecture with four attention heads and width $D=288$ ($D=296$ in the unweighted control for parameter matching), projecting all node types into a joint embedding space before applying homogeneous `GATConv` layers.

Each directed edge has a 16-dimensional vector. Index 0 represents the coupling weight, index 1 is the normalized path count, indices 2 to 8 are a one-hot encoding of the relation, and indices 9 to 15 are middleware QoS parameters such as reliability, durability, priority, transport departure mode, deadline constraints, and max-blocking time. The edge vector is projected and added before attention.

## 4.2 Prediction Head and Training Objective

A composite head predicts the simulated cascade impact, supplemented by an active auxiliary head $\hat{a}_1$ regressing on the simulator’s reliability column $I^*_R$. (A secondary maintainability head defined in the schema is masked out of backpropagation because the simulator produces no maintainability labels.) The operational training objective combines mean-squared error regression with listwise and margin-ranking terms: $$\tag{3}
\mathcal{L} = \text{MSE}(\hat{I}^*, I^*) + 0.5 \cdot \text{MSE}(\hat{a}_1, I^*_R) + 0.3 \cdot \mathcal{L}_{\text{rank}} + 0.1 \cdot \mathcal{L}_{\text{pairwise}},$$ where $\mathcal{L}_{\text{rank}}$ is Listwise Maximum Likelihood Estimation (ListMLE) [82] over the permutation $\pi$ induced by the simulated labels, $$\tag{4}
\mathcal{L}_{\text{rank}} = -\frac{1}{N}\sum_{i=1}^N \Big( \hat{s}_{\pi_i} - \log \sum_{j=i}^N \exp(\hat{s}_{\pi_j}) \Big),$$ and $\mathcal{L}_{\text{pairwise}}$ is a margin-ranking loss with $\gamma = 0.05$ over pairs differing by more than $\gamma$. Tied labels, which affect about 31% of Applications with $I^* = 0$, enter $\pi$ in a fixed deterministic sequence (ordered by entity identifier). While this injects an arbitrary ordering among inactive nodes into ListMLE, the margin-ranking term explicitly ignores pairs separated by less than $\gamma = 0.05$, dampening gradient penalties from tied inactive components.

Models are trained with AdamW ($\eta = 3 \times 10^{-4}$, weight decay $10^{-4}$) using cosine warm restarts for up to 300 epochs. We set early stopping at 60 epochs of patience on a 20% node-level validation split from the largest training scenario, using five fixed seeds ($\{42, 123, 456, 789, 2024\}$); while this node-level split is transductive with respect to that scenario’s internal graph, all reported evaluations are strictly inductive under leave-one-scenario-out cross-validation. We set hyperparameters and loss coefficients before the first sweep and kept them the same across all experiments. This approach differs from the registered plan, which called for selecting every hyperparameter using nested inner-LOSO selection (two-fold inner holdout). Instead, the published results use one fixed configuration, chosen during the main experiments to keep computation manageable across seeds and folds. We explain this difference in §5.3. We ran the registered selection later as a sensitivity analysis on the eight-configuration stage-1 grid (varying depth and rank normalization of features and labels). This analysis also used early stopping on a held-out training scenario, which is another difference from the published protocol (§6.2). The results confirm that the main null finding does not change under nested tuning.

## 4.3 Simulation Oracles

The simulators define three different notions of cascade impact rather than direct observations of real failures, so they serve as evaluation criteria whose assumptions can favor some ranking methods over others. Labels come from three failure simulators, which serve as label oracles (we use the two terms interchangeably), on the raw structural multigraph $G_{\text{structural}}$:

-   **Primary reachability cascade oracle ($I^*$):** Crashes component $v$, propagates outages through dependent topics, brokers and links via breadth-first traversal on $G_{\text{structural}}$, and computes the mean fractional feed loss across intact subscribers. Feed loss is scaled by a QoS severity ladder ($\times 1.2$ `RELIABLE`, $\times 1.15$ high priority, $\times 1.05$ medium) and clamped to $[0, 1]$. Each propagation wave is processed in a seeded random order, which decides ties at the propagation threshold; the label is the mean over five seeds. Disabling QoS scaling leaves the Application ordering largely intact ($\rho = 0.965$ across the twelve folds), and substituting durability-aware rescaling moves it less still ($\rho = 0.977$), showing that $I^*$ is predominantly a topological reachability metric.

-   **Queue-flow discrete-event oracle ($I_{\text{dyn}}$):** A discrete-event SimPy [83] simulation to model dynamic message emission rates, queue buffer saturation, and network latency. It measures the drop in delivered message rate for surviving consumers under load, using declared rates, payload sizes, and QoS contracts that $I^*$ ignores. Its mechanism differs from reachability, but it shares the same pub-sub topology, and its first-order effect—consumers that lose a failed publisher’s messages—is again subscriber loss. While $I_{\text{dyn}}$ models declared rates and buffer limits, it operates on configured parameters free of physical operating-system dynamics like socket buffer backpressure, thread scheduling, or garbage collection pauses. It provides labels for all $1{,}321$ Applications, averaging over five seeds, and takes $12.7$ CPU-hours for the full corpus, compared to seconds for $I^*$. A sensitivity check restricted to the first $30$ Applications per fold in lexicographic order is reported in Supplementary §S38 (Table S62). $I_{\text{dyn}}$ agrees with $I^*$ at a mean $\rho = 0.711$ $[0.625, 0.794]$. Across seeds, a single $I_{\text{dyn}}$ run agrees with another at $\rho = 0.43$–$0.96$ per fold; the five-seed mean used as the label has an estimated reliability of $0.79$–$0.99$ (Spearman–Brown), which bounds any ranker’s agreement, and every ranker in Table 6 stays below its fold’s bound.

-   **Composite multi-criteria failure oracle ($I_{\text{comp}}$):** An auxiliary benchmark uses the Validate-stage failure simulator. We run it on all $1{,}321$ Applications with QoS weighting and a primed baseline flow. Each removal is scored as a linear combination of four degradation components: $I_{\text{comp}}(v) = 0.35\,\text{RL}(v) + 0.25\,\text{FR}(v) + 0.25\,\text{TL}(v) + 0.15\,\text{FD}(v)$, representing Reachability Loss ($\text{RL}$), Fragmentation ($\text{FR}$; $0.70$ structural component loss $+\,0.30$ severity), Throughput Loss ($\text{TL}$), and Flow Disruption ($\text{FD}$). The weights are from one of three AHP matrices that encode a declared vector rather than elicited judgment, so $I_{\text{comp}}$ serves as a declared multi-objective stress test to assess resilience to network fragmentation and throughput disruption, rather than just subscriber loss. Since fragmentation and flow disruption occur with almost every removal, $I_{\text{comp}}(v) > 0$ for nearly every Application. $I_{\text{comp}}$ is never used as a training label.

## 4.4 Input–Label Separation and the Reference Criterion

Features are extracted strictly from $G_{\text{analysis}}$, while simulation oracles execute on $G_{\text{structural}}$, and no simulation output is used as an input feature; a regression test in the replication package ensures this separation.

Procedural separation does not eliminate construct overlap, which is the main risk discussed in this paper. High agreement with a simulator does not necessarily imply predictive skill: a ranking may correlate strongly with a simulator because it reproduces the simulator’s propagation rule, not because it infers impact from independent evidence.

**The reference criterion.** We established the formal concept of the reference criterion post hoc to understand why simple dependency counts performed so strongly. A ranking is a *reference* for an oracle $O$ if it is a closed-form simplification of $O$’s own computation using the same inputs. A reference measures how much of $O$ comes from its own rule, not predictive skill, so comparisons with it are not claims of superiority. All other rankers, namely the training-free baseline and the learned and hybrid methods, are *predictors*. For $I^*$, the first propagation wave corresponds to the set of `InDeg` counts (see Remark 1), which is classical publish–subscribe afferent coupling [54, 55]; the references are therefore its first-order expansion (Eq. 6), `InDeg`, `Reach`, and their raw-graph equivalents. For $I_{\text{dyn}}$, the rate-weighted first-order expansion (Eq. 7) truncates its computation to direct subscriber loss weighted by declared publication rates, so it is the reference for that simulator; the $I^*$ references are also reported for comparison. For $I_{\text{comp}}$, no ranking is a truncation; its fragmentation and flow terms respond to removing high-degree and high-betweenness nodes, so `Topo-QoS` and raw degree are considered close to it, and their performance is interpreted with the same caution as the references for $I^*$. The learned methods are not references by this definition, but they use in-degree features and are trained on the oracle they are scored against, so they share some overlap (§6.2 measures this). References are therefore reported to show how much agreement can be obtained by encoding a simulator’s assumptions directly, and predictors are evaluated against them to determine whether learning adds information beyond explicit dependency structure. Two analyses limit the circularity instead of removing it. Every ranker is evaluated on all three oracles, and its agreement with $I_{\text{dyn}}$ is also reported after removing the effect of $I^*$ (and separately, the first-order term) (§6.1). However, none of these analyses replaces validation against real failures in live distributed systems, which this study does not include (§7.5). All results are therefore conditional on simulation fidelity.

# 5. Experimental Setup

The experimental design evaluates competing explanations of cascade-impact ranking performance. Some rankers derive impact analytically from explicit dependency structure, some combine analytical and learned components, and others learn directly from graph representations. The goal is not only to identify high-performing rankers, but also to determine whether ranking performance originates primarily from the dependency representation or from the learning algorithm operating on it. RQ1 therefore compares learned approaches with analytical rankings derived from the same dependency structure, and RQ2 isolates the contributions of dependency representation, degree information, relation typing, QoS information, and model family.

**Training-free baseline.** `Topo-QoS` is computed on the Application–Library `DEPENDS_ON` graph (Rules 1 and 5): $$\tag{5}
\text{Topo-QoS}(v) = 0.6 \cdot \text{BT}_{w}(v) + 0.4 \cdot \text{AP}(v),$$ where $\text{BT}_{w}$ is betweenness over edge distances $d(e) = 1/(w(e) + 10^{-6})$, so tightly coupled edges attract shortest paths, and AP flags articulation points. Because of an implementation defect, the articulation term reads zero for every node, so the reported score ranks as QoS-weighted betweenness. Restoring the term lowers `Topo-QoS` from $0.553$ to $0.533$, so the defect does not favor the reference counts. We archive the unweighted Topo baseline in the replication repository.

Because several analytical rankings are derived from the same architectural information the simulators use, high correlation with a simulator does not by itself imply prediction (§4.4). These analytical approximations serve as strong references because they are derived directly from the corresponding failure-propagation assumptions. Three primary training-free rankings restate the reachability oracle’s propagation rule and are reported as references. The first is the post hoc first-order expansion of $I^*$ (Analytic $I^*$): $$\tag{6}
\hat{I}^*_1(v) = \sum_{t \in \text{pub}(v)} \frac{|\text{sub}(t)|}{|\text{pub}(t)|},$$ where $|\text{pub}(t)| \ge 1$ holds for all published topics $t \in \text{pub}(v)$ by construction ($v$ publishes to $t$), preventing any division by zero. The second is `InDeg`$(v)$, the number of direct dependents of $v$ on the Application–Library `DEPENDS_ON` graph, which for an Application equals publish–subscribe afferent coupling and is exactly the set $I^*$’s first wave reaches (Remark 1). The third is `Reach`$(v)$, the number of its transitive dependents normalized by $|V| - 1$, which is the set a reachability cascade can visit. For the queue-flow simulator $I_{\text{dyn}}$, the corresponding reference is the rate-weighted first-order expansion $$\hat{I}^{\mathrm{rate}}_{\mathrm{dyn},1}(v) \;=\; \sum_{t \in \mathrm{pub}(v)} \frac{r_t}{|\mathrm{pub}(t)|}\,\lvert \mathrm{sub}(t) \rvert,
\tag{7}$$ where $r_t$ is the declared publication frequency of topic $t$. Eq. 7 weights each term of the first-order expansion of $I^*$ (Eq. 6) by the topic’s declared publication rate. It is therefore a first-order truncation of the queue-flow simulator $I_{\text{dyn}}$, which reads the same rates, and it is reported as a reference for $I_{\text{dyn}}$ rather than as a predictor. It was evaluated after the registered analyses and is exploratory. Because it incorporates the same rate information used by $I_{\text{dyn}}$, it is the natural reference against which learned approximations of that simulator are evaluated; in practice, it can also serve as a training-free ranking for queue-flow impact (§7.4). In addition, we archive raw-multigraph topic counts (Pubs-raw) and transitive closure without Rule 5 (Reach-R1) in the replication repository. A reference shows how much of an oracle a restatement of its rule recovers, which is the size of the circularity, not predictive skill. References carry no contrast against `Topo-QoS`, and a learner’s distance from them is reported as such, not as a test. The one exception is the paired comparison between the rate-weighted reference and the learned queue-flow approximation (§6.1), which is labeled exploratory.

## 5.3 Metrics, Protocols and Statistics

**Population.** Every ranker is scored on the Application set $V_{\text{app}}$.

Metrics. We use Spearman $\rho$ to measure ranking against the simulation oracles. To distinguish between active components and those with zero impact, we report both the full-population Spearman $\rho$ and the active-stratum Spearman $\rho_{>0}$, which only includes components with true impact greater than zero. To identify critical sets, we use Overlap@$K$, the fraction of the true top-$K$ recovered by the predicted top-$K$, where $K$ is about 20% of $|V_{\text{app}}|$. We also report PR-AUC, $F_1@\tau$, and nDCG@10 in the replication repository.

Protocols. In the LOSO setup, we train learned models on eleven scenarios and test on the twelfth, repeating this for all 12 folds and five random seeds. The reported value is the average $\rho$ across seeds. For zero-shot transfer, we evaluate models built on all twelve scenarios across the five system models without any fine-tuning. Training-free rankers are not fitted to any data, so for them, both protocols become per-scenario analyses on the same twelve scenarios and five models. We include them in the same tables to ensure every row is scored on the same scenarios and labels.

Statistics. The analysis emphasizes effect sizes with confidence intervals and relative ranking quality, rather than identifying a single highest-performing model. The summary $\rho$ is the average Spearman correlation for each fold or system, with a 95% confidence interval from a bootstrap that resamples folds ($B = 2{,}000$) [84]. We compare results using paired two-sided Wilcoxon signed-rank tests across folds [85]. With 12 folds, the smallest possible two-sided $p$-value is $0.00049$. Fisher-$z$ averaging does not change the row order in Table 5. Weighting folds by $|V_{\text{app}}|$ keeps the top five the same (the reference `InDeg` rises to $0.810$) but increases `Topo-QoS` to $0.596$, corresponding to the raw-multigraph learned rankers ($0.595$–$0.606$). Spearman $\rho$ gives tied scores their average rank. Overlap@$K$ breaks ties at the $K$ boundary by node order, which is arbitrary for integer counts, so §6.1 also reports tie-aware recall curves. Because LOSO folds share ten of eleven training scenarios, we also test every registered contrast with the Nadeau–Bengio corrected resampled $t$-test [86] and, when weighting by $|V_{\text{app}}|$, with an exact sign-flip permutation test.

**Analysis plan and the status of each result.** The evaluation protocol is version-controlled in the replication repository. We registered fifteen numbered amendments across the study, encompassing sensitivity, ablation, and reclassification arms, with none withheld. We assign every reported result to one of three tiers. *Confirmatory*: the original plan’s primary contrast (`HGT-QoS` vs. `Topo-QoS`) and unweighted contrast (`HGT` vs. `Topo-QoS`), Holm-corrected across the two. *Registered secondary*: hypotheses committed before their respective arms executed—including the matched $2\times2$, hybrid rankers, reference counts, dependency-graph learners, derivation value, full-population queue-flow labels, and sensitivity arms, each Holm-corrected within its family. We conducted all secondary analyses after observing the primary null. *Exploratory*: post hoc investigations, reference reclassifications (which altered no figures; §4.4), and the rate-weighted reference for $I_{\text{dyn}}$ (Eq. 7) with the input attribution of the learned queue-flow approximation, both added after all other results existed. **Plan deviation**: the registered nested inner selection was simplified to a fixed configuration during primary sweeps; a sensitivity analysis assesses the registered selection (§6.2). Because sequential amendment registration accumulates family-wise error throughout rounds, we also evaluate an omnibus Holm correction across all 13 decision-bearing contrasts. Both hybrid contrasts against `Topo-QoS` remain significant under this omnibus adjustment (Hybrid-GAT $p_{\text{omni}} = 0.019$, Hybrid-HGT $p_{\text{omni}} = 0.041$). In contrast, the primary contrast remains null ($+0.069$, nominal $p = 0.266$, $p_{\text{omni}} \ge 0.46$). Main-text tables report per-family Holm corrections to reflect the pre-specified hypothesis families.

Taken together, the rankers allow comparison of representation-centric and model-centric explanations of ranking performance. If performance arises primarily from the dependency representation, analytical and learned rankers built on that representation should perform similarly. If learning adds information, learned rankers should outperform analytical alternatives built on the same dependencies. §6 reports the results against these two expectations.

# 6. Results

The evaluation asks not only which model ranks best but also where that ranking performance comes from. We therefore read the results along three dimensions: the contribution of explicit dependency representations, the relative performance of analytical, hybrid, and learned approaches, and the distinction between rankings that restate a simulator’s rule and those that predict its outcomes.

All results are reported on the Application population ($V_{\text{app}}$) against the primary oracle $I^*(v)$, and, for the rankers of Table 6, also against the queue-flow oracle $I_{\text{dyn}}(v)$ and the multi-criteria oracle $I_{\text{comp}}(v)$ (§4.3). Only the primary and secondary contrasts are confirmatory; every other contrast is registered as secondary or exploratory (§5.3). Per-fold results, secondary strata, and extended protocol notes are in the public experiment pages (§5.1). Figure 4 summarizes the main findings.

## 6.1 RQ1: Ranking Accuracy

**Summary.** *For the reachability and queue-flow oracles, explicit dependency graphs, rather than model complexity, carry most of the ranking signal. The strongest learned model, the graph attention network on the dependency graph (`GAT-P-QoS`, $\rho = 0.748$), approaches without exceeding the direct-dependent reference ($0.764$; not statistically distinguishable, but equivalence at $\pm 0.05$ not established), and ablations show that it draws on its degree features (losing $0.14$ without them; see §6.2). For the more expensive queue-flow oracle $I_{\text{dyn}}$ ($12.7$ CPU-hours), a learned approximation trained on its labels reaches $\rho = 0.799$, above the unweighted first-order expansion ($0.706$, Holm $p = 0.019$) because it reads declared publication rates and payload sizes; the rate-weighted reference (Eq. 7), which reads the same rates without training, reaches $0.830$, matching or exceeding the learned approximation ($+0.031$, 10 of 12 folds; exploratory). Under multi-criteria failure conditions ($I_{\text{comp}}$), hybrid rankers remain stable ($0.58$) while pure neural models drop sharply ($0.144$–$0.334$), and training-free scores aligned with the oracle’s terms rank higher still. On the raw multigraph, the main registered comparison (`HGT-QoS` vs. `Topo-QoS`) showed no significant difference ($\Delta\rho = +0.069$, $p = 0.266$). To recover $80\%$ of the true top-$20\%$ set, `GAT-P-QoS` must flag the top $40\%$.*

Learned rankers are trained on eleven scenarios and scored on the twelfth; training-free rankers are scored on all twelve (26 to 300 Applications, $K$ between 5 and 60). Table 5 reports all of them against $I^*$, with the reference rankings of §5.2 in a separate block: they restate $I^*$’s rule, so their rows measure the circularity and carry no contrast.

Two patterns emerge. First, reading the dependency graph instead of the raw multigraph improves attention-based learners (`GAT-P-QoS` $0.748$ vs. `GAT-QoS` $0.635$), although the typed transformer becomes unstable on it (`HGT-P-QoS` $0.514$). Second, analytical rankings derived from the same dependency structure match or exceed every learned model ($0.764$–$0.808$, against at most $0.748$). The analyses below examine both observations.

**The reference level.** As noted in Remark 1, `InDeg` represents publish–subscribe afferent coupling [54, 55, 56] and counts exactly the Applications reached by the first propagation wave of $I^*$. `Reach` counts the transitive dependents that a reachability cascade can visit. Their values on $I^*$ ($0.764$, $\rho_{>0} = 0.516$; $0.732$) show how much of the oracle is recovered by expressing again its rule, rather than measuring predictive skill. Exploratory raw-multigraph references are evaluated in the replication repository: counting published topics (Pubs-raw) achieves $0.731$, and transitive closure without Rule 5 (Reach-R1) gets $0.674$. Among the references, that derivation matters in one case: without Rule 5, `Reach` drops by $0.058$ (9/12 folds, Holm $p = 0.0068$; derivation ablation). Untyped raw-graph metrics do not recover the reference: total degree reaches $0.199$ and reverse PageRank $0.089$, while PageRank is constant for every Application because they have no incoming raw edges.

**The first-order expansion of the oracle.** The strongest reference is the post hoc closed-form first-order expansion of $I^*$ (Eq. 6, §5.2). It reaches mean $\rho = 0.808$ $[0.755, 0.853]$ ($\rho_{>0} = 0.631$): direct subscriber loss is most of what $I^*$ measures, and `InDeg` is a coarser version of the same quantity. As a reference, it bounds the mean rather than every fold: on four folds (AV, Financial Trading, Healthcare, Industrial SCADA), `InDeg` slightly exceeds it (by $0.005$–$0.038$).

**Learners on the dependency graph approach the reference.** Trained on the dependency graph rather than the raw multigraph, the strongest learned model, `GAT-P-QoS`, achieves $\rho = 0.748$, approaching but not exceeding the direct-dependent reference. This is $0.016$ below the direct-dependent count for individual seeds, and the five-seed ensemble is $0.007$ above it ($0.772$, Table 6). These differences are not statistically significant, nor do they show equivalence: the $90\%$ interval of the per-fold difference is $\pm 0.076$, so a two one-sided test at the registered margin of $\pm 0.05$ does not pass ($p = 0.17$ per seed, $0.13$ for the ensemble; equivalence arm F3). At this sample size, the learner and the count are indistinguishable and not ranked. The closeness to the reference depends on the degree features each learner receives (§3.5): removing `in_degree` and $w_{\text{in}}$ lowers `GAT-P-QoS` to $0.612$ (§6.2). We archive a version that uses `InDeg` as its prior in the replication repository, since it is a reference prior. `HGT-P-QoS` only reaches $0.514$ and is highly dependent on the seed (mean within-fold seed SD $0.254$; §7.5).

**Hybrid rankers secure statistically significant gains beyond baseline priors.** Hybrid-HGT achieves $\rho = 0.657$ ($+0.103$, Holm $p = 0.0068$) and Hybrid-GAT reaches $0.683$ ($+0.130$, Holm $p = 0.0029$) compared to `Topo-QoS`, each outperforming the baseline in 11 out of 12 folds. Both results remain statistically significant under the omnibus Holm correction ($p_{\text{omni}} = 0.041$ and $0.019$), the Nadeau–Bengio corrected $t$ ($p = 0.019$ and $0.014$), and $|V_{\text{app}}|$-weighted averaging (exact sign-flip $p = 0.038$ and $0.005$). In this comparison, a hybrid uses $p(v)$ as an input and adds a learned correction to its logit, nesting its comparator. When compared to their own base learners, neither hybrid shows a significant difference (Hybrid-HGT vs. `HGT-QoS` $+0.035$, $p = 0.73$; Hybrid-GAT vs. `GAT-QoS` $+0.048$, $p = 0.30$). The prior also reduces transfer performance: in zero-shot tests, both hybrids perform worse than their base learners (§6.3). On their own, the raw-multigraph learned rankers do not differ significantly from `Topo-QoS` (`HGT-QoS` $+0.069$, $p = 0.266$; `GAT-QoS` $+0.082$, $p = 0.233$).

**Beyond the reachability oracle.** Table 6 compares the rankers against two other oracles. On the full-population $I_{\text{dyn}}$, which matches $I^*$ at $\rho = 0.711$ $[0.625, 0.794]$, the reference methods outperform all GNNs (first-order expansion $0.706$, `InDeg` $0.664$, compared to $0.496$–$0.615$ for GNNs), and `Topo-QoS` achieves $0.471$. Since $I_{\text{dyn}}$ shares its topology and first-order effect with $I^*$, the partial correlation shows how much of each ranking remains after removing the oracle it was fitted to or restates. After removing the rank of $I^*$, `InDeg` keeps $0.272$ $[0.188, 0.366]$, `Reach` $0.117$, `Topo-QoS` $0.134$, and the GNNs $0.107$–$0.173$, with all intervals excluding zero. If we remove the first-order expansion instead, the order reverses: `InDeg` stays at $0.079$. Meanwhile, the raw-multigraph GNNs retain most of their value ($0.212$–$0.217$), indicating that the learners capture queue-flow signals beyond the unweighted first-order term, although less than the rate-weighted reference ($0.573$). The queue-flow oracle separates what the dependency structure provides from what declared rates add. The unweighted first-order expansion (Eq. 6) reaches $0.706$ on $I_{\text{dyn}}$. Weighting each of its terms by the topic’s declared publication rate (Eq. 7) raises it to $0.830$ $[0.778, 0.872]$ without training (exploratory). A gradient-boosted model trained on $I_{\text{dyn}}$ labels, using counts, the first-order expansion, and the registered QoS feature block, which also carries each Application’s declared publication rate and payload size, reaches $0.799$. It outperforms the unweighted expansion ($+0.094$, Holm $p = 0.019$) and `InDeg` ($+0.135$, Holm $p = 0.019$; Family B), but falls below the rate-weighted reference, which exceeds it by $+0.031$ $[+0.013, +0.049]$ on 10 of 12 folds (nominal Holm $p = 0.009$; exploratory). The feature block provides the gain over the unweighted expansion ($+0.095$ over the same model without it, Holm $p = 0.014$), while on $I^*$ it adds nothing ($-0.003$, $p = 0.62$; Family C). An exploratory attribution splits the block (Supplementary §S39): the declared rate and payload columns alone add $+0.097$ (9/12 folds, Holm $p = 0.021$), and the seven QoS-derived columns ($w(t)$-weighted scores and policy shares) add $-0.005$ ($p = 0.68$). Declared rates, rather than QoS policies, provide most of the additional information on this oracle, and the analytical formula uses that information at least as effectively as the learned model. The GNN trained on the same labels approaches neither: `GAT-P-QoS`$\to$dyn reaches $0.598$, below the first-order expansion ($-0.108$, Holm $p = 0.014$) and the gradient-boosted approximation ($-0.201$, Holm $p = 0.0015$), and is no better than the same GNN trained on $I^*$ ($-0.008$; control F5); unlike the tree model, it received neither rates nor payloads (§7.2). The learned approximations are trained on the oracle they are evaluated on, so their possible value is cost, since labeling $I_{\text{dyn}}$ took $12.7$ CPU-hours for the corpus (§6.4); the rate-weighted reference offers the same saving without training. When trained on $I^*$ instead, the same gradient-boosted model is less robust across the three oracles than the first-order expansion alone (worst-case $\rho$ $-0.121$, Holm $p = 0.001$; Family A).

**The multi-criteria oracle favors different rankers.** On $I_{\text{comp}}$, which includes fragmentation, throughput, and flow disruption (§4.3), learned rankers without a prior perform poorly ($0.144$–$0.334$; sum-aggregation GNNs from §6.2 reach $0.41$–$0.44$). The two hybrids that use `Topo-QoS` as a prior maintain $0.58$. Training-free scores that correspond to the oracle’s terms rank higher: `Topo-QoS` achieves $0.702$ $[0.649, 0.753]$ (higher than the direct-dependent reference at $0.650$; the reference is ahead on only 3 of 12 folds, $p = 0.110$), and raw total degree reaches $0.719$. `Reach` drops to $0.302$. This lead reflects overlap with $I_{\text{comp}}$’s fragmentation and flow terms, similar to the references’ lead on $I^*$ (§4.4), rather than predictive skill. No ranker is best across all three oracles.

**Identifying the critical set.** Rank correlation across all Applications is not the main concern in a CI gate; the key question is whether the true top-ranked items are flagged. Figure 5 shows, for each ranker, the proportion of the true top-20% set on $I^*$ that appears within its top $k\%$, with ties resolved by averaging. At $k = 20\%$, `GAT-P-QoS` recovers $0.48$ of the critical set and `Topo-QoS` recovers $0.38$, matching their Overlap@$K$ ($0.454$ and $0.388$). This means about half of what a top-20% gate flags is not in the true top 20%, and about half of the true top 20% is missed. To recover 80% of the critical set, `GAT-P-QoS` must flag the top 40% ($0.81$), and `Topo-QoS` does not reach 80% within 50%. The reference methods do only slightly better: at $k = 20\%$, `InDeg` recovers $0.49$ (tie-breaking bounds $0.48$–$0.50$), and 80% recall requires the top 45% by `InDeg` ($0.83$) or by the first-order expansion ($0.89$). Only the first-order expansion reaches 90% within the top 50%, and `Reach` does not reach 80% within 50%. In the exploratory $n = 30$ sample of $I_{\text{dyn}}$ (right panel of Figure 5), `GAT-P-QoS` reaches $0.65$ at 40% and $0.80$ at 50%, compared to $0.83$ at 40% for the `InDeg` reference. In practice, requiring a gate to flag 40%–50% of components to catch 80% of critical points would likely cause alert fatigue in production CI/CD pipelines. This suggests that SaG is best operationalized as a prioritized informational triage list for architectural reviews, rather than as an automated blocking gate (§7.4 proposes a two-tiered triage protocol).

## 6.2 RQ2: Sources of Predictive Performance

**Summary.** *Attention-based learners improve when using the dependency graph, where messages reach the scored Applications from their dependents (`GAT-P-QoS` $0.748$ vs. `GAT-QoS` $0.635$), whereas the typed transformer does not in the tested configuration (`HGT-P-QoS` $0.514$ vs. `HGT-QoS` $0.622$). The dependency-graph GAT’s closeness to the reference comes from its degree features: without them, it loses $0.14$ (Holm $p = 0.005$). A sum-aggregation GNN, which can count dependents, loses only $0.01$ without these features, though the difference is not significant after correction. When capacity is matched, relation typing has no effect; with weighted in-degree included in both arms, the “QoS” inputs also add no measurable benefit ($+0.030$, Holm $p = 0.33$). Across these ablations, the largest drops come from removing degree information ($-0.136$ for `GAT-P-QoS` and $-0.270$ for `GAT-QoS`), whereas relation typing ($-0.013$) and the choice of aggregator ($-0.016$) have little effect. For attention-based learners, the gain from the dependency representation ($+0.113$) exceeds every change of model architecture tested, suggesting that most of the recoverable signal lies in explicit dependency structure rather than in higher-order message passing.*

**What the dependency-graph learner needs.** Each learner receives in-degree and $w_{\text{in}}$ as node properties, and on the dependency graph, it also aggregates the dependent neighborhood. This means its similarity to `InDeg` could come from either source. Ablation experiments (Table 8) separate these effects. Removing the two degree columns reduces `GAT-P-QoS` by $0.136$, and removing the three centralities most correlated with in-degree reduces it by $0.161$ (F1, rule F1a). This shows that the approach to the reference depends on the degree features. Message-passing theory predicts this: softmax attention normalizes over neighbors and computes a weighted mean, so it cannot count them, whereas a sum aggregator can [69, 70]. A GINE network with the same parameter budget supports this, keeping $0.721$ and $0.711$ without the same columns, only $0.01$–$0.02$ below its full-feature score. However, the aggregator contrasts are not significant after Holm correction ($+0.108$ and $+0.124$, $p_{\text{Holm}} = 0.157$; rule F2b), so the study does not claim an aggregator effect. No dependency-graph learner, with or without degree features, is equivalent to `InDeg` within $\pm 0.05$ (equivalence bounds $0.063$–$0.276$; F3). In zero-shot, the degree columns matter little ($0.810$–$0.821$ without them), because the system models most of the ranking by separating inert from active components (§6.3).

On the raw multigraph, this does not say much about typing, since no message gets an Application there: a gradient-boosted model using the same per-node features but no graph (`GBM-Feat`) achieves $0.642$, similar to `GAT-QoS`, and removing HGT’s reverse pass (the only way messages get Applications) has no effect (`HGT-QoS-U`, $-0.010$, $p = 0.91$). On the dependency graph, where messages do reach Applications, `HGT-P-QoS` gets $0.514$ with a mean within-fold seed SD of $0.254$, compared to $0.748$ and $0.030$ for `GAT-P-QoS`. This is for one fixed configuration (width 100), and averaging predictions from five seeds raises it to $0.618$. We interpret this as seed instability for that configuration, not as evidence against relational typing in general. **The registered selection rule.** The plan selected every hyperparameter by nested selection, which was not used in the published results (§5.3). When applied later on the stage-1 grid (arm N), it changes `HGT-QoS` from $0.622$ to $0.677$ ($+0.055$) and `GAT-P-QoS` from $0.748$ to $0.693$ ($-0.054$), neither of which is significant (Holm $p = 0.259$). Table 5 shows the fixed, published configuration; Arm N is a registered secondary sensitivity analysis. The search harness also stops early on a held-out training scenario instead of the published node-level split. On the three folds where it chose the published hyperparameters, it does not reproduce the published scores (differences up to $0.10$), so these differences are not due to hyperparameter selection alone.

# 7. Discussion, Threats to Validity, and Limitations

## 7.1 Dependency Representation versus Model Complexity

The central finding of this study is that, for the reachability and queue-flow simulators, explicit dependency representations contributed more to ranking performance than model complexity. Deriving a dependency graph from publish–subscribe deployment manifests enabled both analytical and learned approaches: attention-based learners improved on it compared with the raw multigraph (`GAT-P-QoS` $0.748$ vs. `GAT-QoS` $0.635$), and rankings computed directly from it, such as the direct-dependent count ($0.764$; not statistically distinguishable from `GAT-P-QoS`, $0.748$) and the rate-weighted first-order approximation ($0.830$), equaled or exceeded the best learned models ($0.748$ and $0.799$). Pure learners on the raw multigraph did not outperform the training-free baseline, because messages never reached the scored components. Explicit dependency derivation is therefore not merely a preprocessing step for graph learning; in the evaluated corpus, it is the principal source of predictive signal. The multi-criteria simulator is the exception: there, raw degree and betweenness, whose terms align with fragmentation, ranked highest.

## 7.2 When Learning Adds Value, and Relative to What

The study does not show that learning is never useful; it shows where learning adds value and against which comparator. Relative to the training-free baseline, learning helped in two ways. First, hybrids that correct a closed-form prior significantly outperformed that baseline ($+0.103$ and $+0.130$, 11 of 12 folds), and in an exploratory comparison they were the most consistent learned models across the three simulators. Second, learned models transferred zero-shot to unfamiliar architectures better than the baseline ($\approx 0.81$ vs. $0.53$). Relative to analytical references built on the same dependencies, however, no learned model showed additional skill. The references were indistinguishable from or exceeded the learned models in-distribution and ranked higher in transfer ($0.863$–$0.938$), and ordering among components that actually propagate failures remained weak for every learned model ($\rho_{>0} \le 0.342$). Learning is therefore likely to contribute most where impact depends on mechanisms that no available analytical approximation captures, a condition this corpus did not exercise. A per-regime breakdown of these results by architecture type is archived in the replication repository (`results/engine_regimes.json`; Supplementary §S34).

**How message passing contributes.** On the raw multigraph, learning mainly used node properties. Three checks explain how these learned rankers worked. First, gradient-boosted decision trees using only per-node features (no graph message passing, `GBM-Feat`) reach $\rho = 0.642$ under LOSO, similar to `GAT-QoS` ($0.635$). Second, in the raw multigraph, all structural links point away from Applications, so standard forward GAT convolutions do not send messages to the scored nodes—removing all edges does not change their outputs. Third, HGT reaches Applications only through reverse edge passes, and removing them has no effect (`HGT-QoS-U`, $-0.010$, $p = 0.91$). So, on the raw multigraph, neural models acted as non-linear combiners of precomputed centralities and degree metrics, not as relational message-passing models. On the derived dependency graph, directed edges go from dependents to dependencies: three layers of message passing gather information from the true dependent neighborhood, letting `GAT-P-QoS` outperform `GBM-Feat` by $+0.106$. Since every learner also gets an in-degree feature (§3.5), this margin does not mean attention finds the dependent count on its own, and ablation tests show it does not: without the degree columns, `GAT-P-QoS` loses $0.136$, while a sum-aggregation network of the same size loses $0.011$ (§6.2).

**Homogeneous versus heterogeneous architectures.** On the raw multigraph, where message passing into Applications was inactive, adding typing made no measurable difference (main effect $-0.014$, interaction $+0.001$). On the dependency graph, where message passing is active, the heterogeneous transformer (`HGT-P-QoS`) was unstable across seeds in the tested configuration (width 100, fixed setup; mean within-fold seed standard deviation $0.254$, mean $\rho = 0.514$), while the homogeneous `GAT-P-QoS` was stable ($0.030$, $\rho = 0.748$). This means that, in this setup, relation-specific parameters did not improve accuracy, though they reduced stability. This does not mean typing is always harmful. Only `HGT-QoS` was run under the registered selection rule (§6.2); averaging five seeds’ predictions raises `HGT-P-QoS` to $0.618$ (still below the references), and denser topologies or architectures with messages reaching scored nodes may behave differently.

**Why the learned queue-flow approximation does not exceed the formula.** The gradient-boosted approximation (`GBM-P-QoS→dyn`, $0.799$) outperforms the unweighted first-order expansion ($0.706$) because it reads declared publication rates and payload sizes, which $I_{\text{dyn}}$ uses and the unweighted expansion ignores. Once rates enter the analytical expansion (Eq. 7), it reaches $0.830$ and matches or exceeds the learned approximation. The attention-based approximation (`GAT-P-QoS→dyn`, $0.598$) received neither rates nor payloads, and it scores within $0.008$ of the same model trained on $I^*$ (control F5). Whether a learned model given the same inputs as the formula, or trained to correct it, can exceed the formula is left to future work (§7.6).

## 7.3 Restatement versus Prediction

Several of the highest-scoring rankings largely restate a simulator’s propagation rule: the direct-dependent count and the first-order expansion for the reachability simulator, and the rate-weighted first-order approximation for the queue-flow simulator. The reference criterion (§4.4) distinguishes recovering a simulator’s definition from predicting its outcomes, and it changes how both analytical and learned results should be read. A learned model that approaches a reference has learned the simulator’s first-order rule, not necessarily anything beyond it. Because simulation-labeled benchmarks are common in architecture analysis, the criterion offers a general check for evaluations of this kind: before crediting a learned model with predictive skill, compare it against the simplest ranking that restates the simulator’s own computation.

## 7.4 Practical Consequences

**Choosing a ranker by simulator cost.** The usefulness of a ranker depends on how costly the simulator it approximates is. If the simulator is inexpensive, like the reachability simulator $I^*$ ($0.01$–$0.72$ s per pass over a corpus architecture’s Applications; §6.4), practitioners can compute its ranking directly from the manifest. Publish–subscribe afferent coupling, a direct-dependent count used in architecture research for two decades [54, 55], is not statistically distinguishable from any graph neural network tested at a fraction of the cost; because it restates the simulator’s first wave (§7.3), its value is cost, not predictive skill. If the simulator is expensive, like the queue-flow simulator $I_{\text{dyn}}$ ($12.7$ CPU-hours to label the corpus), a rate-weighted first-order expansion computed from declared publication rates approximates it at $\rho = 0.830$ in milliseconds, matching or exceeding a gradient-boosted approximation trained on its labels ($0.799$). This study does not show that either simulator, or any of its approximations, predicts real outages.

**Choosing a ranker by failure notion.** Table 11 summarizes the evidence by oracle. Practitioners must interpret these recommendations as conditional on simulation fidelity. If the discrete-event or cascade simulator does not capture specific physical failure modes (e.g., partial network partitions or disk thrashing), ranking efficacy on physical clusters could diverge. On the reachability oracle $I^*$, the best learned ranker is the dependency-graph GAT (`GAT-P-QoS`, $0.748$), followed by the hybrids ($0.657$–$0.683$); all require training, and none is statistically distinguishable from the direct-dependent reference ($0.764$). Where the reachability ranking itself is wanted, running $I^*$ directly is the simplest and cheapest option at corpus size. Where the queue-flow notion of impact matters ($I_{\text{dyn}}$), the rate-weighted first-order expansion ($0.830$) is the recommended ranker; it matches or exceeds the learned approximation trained on queue-flow labels ($0.799$), and this is the only simulator on which declared information carries measurable signal beyond the dependency structure, from publication rates and payload sizes rather than from QoS policies or QoS-weighted scores. Where failure involves fragmentation and throughput loss ($I_{\text{comp}}$), training-free topological scores (`Topo-QoS`, $\rho = 0.702$) rank highest because their betweenness and articulation terms directly align with fragmentation; among learned models, pure neural rankers collapse ($\le 0.334$), while hybrids retain robustness ($\rho = 0.585$). On unfamiliar topologies like the five system models, learned rankers transfer zero-shot at about $0.81$ against $0.526$ for the training-free baseline. Still, active-stratum agreement is weak ($\rho_{>0} \le 0.342$), and the result rests on five models by one author.

**Mitigating Alert Fatigue with a Two-Tiered Triage Protocol.** Using a top-20% threshold on the direct-dependent count (`InDeg`) recovers about half of the true top-20% set on $I^*$ ($0.49$), while the rest of the flagged items are not in that set; the best learned ranker does no better (`GAT-P-QoS`, $0.48$). Figure 5 shows the trade-off: recovering 80% of the critical set takes the top 45% by `InDeg` ($0.83$) or the top 40% by `GAT-P-QoS` ($0.81$), `Topo-QoS` does not reach this level within the top 50%, and no predictor reaches 90% within the top 50%. To catch most critical components, a gate would need to flag nearly half the system, making these rankers unsuitable as automated pass/fail filters. In a system with over 100 services, flagging 40–50 would overwhelm developers with alerts.

To operationalize these rankings constructively, we propose a conceptual *two-tiered triage protocol* as an architecture inspection heuristic, rather than an automated blocking gate. We emphasize that this protocol is an architectural proposal requiring human-factors and operational workflow validation before industrial adoption:

1.  **Tier 1 (Commit-stage triage):** When reviewing pull requests, compute the direct-dependent count (about 11 ms, an estimated 0.086 mWh, 0.31 J) and the rate-weighted first-order expansion (Eq. 7; about a millisecond). Show the top 5 components by each as an informational note in the pull request review. This highlights potential cascade risks for peer review without blocking developers or causing alert fatigue.

2.  **Tier 2 (Staging and sprint verification):** During nightly builds or sprint architecture reviews, run the simulators on the Tier-1 shortlist within a fixed inspection budget, such as the ten highest-ranked services, and reserve redundant broker routing or chaos fault injection for the components the simulation confirms.

## 7.5 Threats to Validity

**Construct validity and oracle circularity.** All labels are simulated, and no ranker is validated against observed failures in physical deployments. We conducted no empirical fault injection (e.g., chaotic network partitions, process crashes, or disk exhaustion) on running distributed clusters. Because all rankers and references are evaluated against simulator-generated labels, the findings establish what can be predicted within the evaluated simulation framework, not what necessarily predicts real-world failures; external validation remains necessary. Discrete-event simulations omit complex real-world distributed runtime dynamics: kernel TCP buffer bloat, socket starvation, thread pool exhaustion, garbage collection freezes, asymmetric network partition drops, and cascading retry storms. In physical deployments, such dynamics can induce non-local, non-monotonic cascade failures: for example, a low-degree peripheral logging or monitoring service that encounters a slow disk or socket buffer bloat can cause upstream worker threads to block on synchronous backpressure, exhausting connection pools across the cluster and precipitating a total system outage. In such scenarios, physical failure impact decouples from structural graph degree, and training-free topological rankings will misestimate criticality. Evaluating SAG under live physical fault injection is therefore indispensable to establish whether structural rankings remain effective when nonlinear transport dynamics dominate. The circularity between the primary oracle and the rankers is analyzed in §4.4: the dependency counts are references for $I^*$, the rate-weighted expansion is a reference for $I_{\text{dyn}}$, closed-form centrality is proximate to $I_{\text{comp}}$, and the learned rankers inherit part of the overlap through their degree features, which ablation experiments show they depend on. Inert components are separated by construction, which is why $\rho_{>0}$ is reported beside $\rho$. We decided to reclassify the counts as references after all results were finalized, and this change did not affect any numbers. The two other oracles bound, but do not remove, the threat: $I_{\text{dyn}}$ shares the topology and the first-order effect, and $I_{\text{comp}}$’s weights encode a declared rather than an elicited priority vector. No learned ranker exceeded the analytical references on any simulator: the learned queue-flow approximation outperformed only the unweighted expansion, and the rate-weighted expansion, itself a reference for $I_{\text{dyn}}$, matched or exceeded it. The evaluation is confined to Applications, so dependency Rules 2–4 and 6, which govern brokers and hosts, are untested.

**Internal validity, reproducibility, and drift.** Rankers consume $G_{\text{analysis}}$ while simulation oracles execute on $G_{\text{structural}}$, verified by regression tests. We held model capacity, depth, and early stopping constant across comparison arms. The registered selection rule was not applied to the published learned results, a deviation disclosed in §5.3; a post hoc sensitivity check applies it to `HGT-QoS` and `GAT-P-QoS` (§6.2), and every other statement regarding a learned ranker is conditional on one fixed configuration. The learned rankers are also seed-sensitive. Across the five seeds of a fold, the mean within-fold standard deviation of $\rho$ is $0.099$ for `HGT-QoS`, $0.254$ for `HGT-P-QoS`, $0.024$ for `GAT-QoS` and $0.030$ for `GAT-P-QoS`, and single `HGT` seeds differ from others in the same fold by more than $1.0$. Averaging the five seeds’ *predictions* instead of their $\rho$ values raises every learned ranker, most of all the unstable ones (`HGT-P-QoS` from $0.514$ to $0.618$); the tables report the registered statistic, the mean of per-seed $\rho$. Across revision cycles and compute devices, learned cells drifted by up to $0.172$ ($\pm 0.041$ on `HGT-QoS`), more than several effects this paper reports (the primary contrast, $+0.069$; the QoS main effect, $+0.073$). For that reason, every learned cell in Tables 5, 7 and 9 is reported from one named CPU sweep whose per-seed logs reproduce the published mean exactly, the sensitivity verification sweep re-ran every learned comparator to an exact match, and a hierarchical bootstrap that resamples seeds within folds widens the learned rows’ intervals only slightly. The Connectivity Degradation Index samples nodes with hash-dependent tie-breaking, so `PYTHONHASHSEED=0` is fixed. We reconcile all reported values mechanically against released artifacts.

**External validity and the single-modeler threat.** Synthetic topologies come from a single generator family, which may induce parametric regularities not representative of heterogeneous industrial architectures. The five system models are hand-authored approximations (22–41 Applications) of open-source projects, each written by the first author from public documentation. All five RQ3 results are exposed to this threat, and it is not mitigated: no second modeler authored any model independently, and no inter-modeler reliability or agreement metric is reported. The system models also differ structurally from the synthetic folds: a larger share of their Applications has zero simulated impact, and their fan-in is more concentrated, favoring `Reach` and inflating full-population $\rho$. Furthermore, two of the five (Train-Ticket and Online Boutique) are synchronous RPC systems re-expressed as asynchronous publish–subscribe meshes by decomposing each RPC call into reciprocal request and reply topics mediated by broker intermediaries. While this translation faithfully mirrors bidirectional dataflow, mapping synchronous request–reply call graphs into decoupled pub-sub event topics may introduce semantic distortions into dependency relations, because it neglects synchronous blocking, client-side timeouts, and upstream thread starvation. We did not evaluate architectures with tens of thousands of components; we timed the counting path up to $10{,}000$ components (§6.4), and we did not evaluate the learned rankers or the oracles. We did not reproduce published learned criticality models (FINDER, DrBC) because they do not support typed multigraphs or pub-sub semantics.

**Sustainability and energy estimation validity.** Energy metrics reported for continuous integration workflows (§6.4) are coarse estimates derived from baseline processor thermal design power (28.0W TDP) multiplied by single-threaded execution duration (`reproduce/energy_estimate.py`). They do not capture runtime hardware power dynamics, including dynamic voltage and frequency scaling (DVFS), DRAM or storage energy overheads, or platform idle power. Crucially, modern multi-core processors can briefly surge well beyond baseline TDP under active Turbo Boost (e.g., up to $64$ W package power limits under sustained vector loads) or throttle down during I/O stalls. Furthermore, these numbers were not gathered via on-chip hardware telemetry counters (e.g., Intel/AMD Running Average Power Limit, RAPL) or calibrated external digital power meters. While adequate for order-of-magnitude engineering trade-offs between milliseconds and hours of computation, these figures must not be construed as empirical physical power measurements or precise greenhouse gas emissions accounting.

**Conclusion validity.** The only confirmatory results are the plan’s two contrasts, the null primary and the null secondary (§5.3). Everything else, including the two hybrid contrasts, is registered secondary or exploratory and was designed after the primary null was known. LOSO folds share ten of eleven training scenarios, so the Wilcoxon $p$-values are nominal and anti-conservative; the Nadeau–Bengio corrected test, which accounts for the overlap, leaves the hybrid contrasts significant and the primary null. For training-free rankers, the folds are simply twelve scenarios from one generator, so the effective sample is small, and with twelve folds a bootstrap CI over folds is coarse; over five system models it is indicative only. Equivalence, which a claim that one ranker “matches” another requires, is not established for any pair at $\pm 0.05$.

## 7.6 Limitations and Future Work

Five directions follow from the study’s central question, in order of priority:

1.  **Validation against real failures:** controlled fault injection on ROS 2, Kafka and MQTT deployments (for example with Chaos Mesh or ChaosBlade), reference systems with known faults such as Train-Ticket [33], and incident data from industrial publish–subscribe systems. This should be coupled with runtime distributed tracing standards (e.g., OpenTelemetry, W3C Trace Context) to empirically validate whether static declared dependency paths faithfully reflect dynamic runtime message flow trajectories under normal and degraded conditions.

2.  **Infrastructure and broker validation:** extending cascade-impact evaluation beyond Applications to message brokers, topics, and compute hosts (evaluating Rules 2–4 and 6), which were outside the Application-scoped evaluation of this study.

3.  **Independent modelers:** replication of the five system models by additional modelers, with inter-modeler agreement reported.

4.  **Alternative impact models:** testing whether the conclusions hold for simulators with different failure mechanisms, including synchronous call semantics, which the current dependency rules do not model.

5.  **When learning exceeds analytical methods:** identifying impact-generation mechanisms whose predictive signal is not captured by explicit dependency structure. This includes learned corrections on top of the rate-weighted approximation, and learned approximations that receive the same rate and payload information as the analytical formulas.

Further extensions are automatic extraction of architecture graphs from ROS 2 launch files, Kubernetes manifests and Helm charts; integration with service mesh telemetry and distributed tracing (e.g., OpenTelemetry, Jaeger) for runtime dependency drift detection; hardware-measured energy accounting (for example via RAPL); a full hyperparameter search for every learned model; and validation of the proposed explanation layer.

# 8. Conclusion

This paper presented Software-as-a-Graph (SaG), a pre-deployment framework that derives explicit dependency graphs from publish–subscribe deployment manifests and supports analytical, hybrid, and learned approaches to cascade-impact ranking. Using twelve synthetic architectures, three failure simulators and five stylized models of open-source systems, the study examined when graph learning improves on rankings derived directly from explicit architectural dependencies.

For the reachability and queue-flow simulators, explicit dependency representations provided most of the predictive signal. Attention-based learners benefited from the derived dependency graph ($\rho = 0.748$ vs. $0.635$ on the raw multigraph), but simple analytical rankings built on the same dependencies were indistinguishable from or exceeded the learned models. Counting direct dependents ($\rho = 0.764$) was not statistically distinguishable from the best learned model on the reachability simulator ($0.748$; equivalence at $\pm 0.05$ not established). On the expensive queue-flow simulator, a rate-weighted first-order approximation computed in milliseconds ($0.830$) matched or exceeded a learned approximation trained on $12.7$ CPU-hours of simulation labels ($0.799$). In this corpus, representation choice mattered more than model complexity.

Learning nonetheless added measurable value in two respects. Hybrids that correct a closed-form prior significantly outperformed the training-free baseline, and learned models transferred zero-shot to unfamiliar architectures better than that baseline ($\approx 0.81$ vs. $0.53$). In both cases, however, dependency-based references remained competitive or stronger, and ordering among components that actually propagate failures remained weak.

These results have implications for both research and practice. For researchers, they show the importance of evaluating graph-learning approaches against analytical alternatives aligned with the simulator, and of distinguishing prediction from restatement of a simulator’s rule. For practitioners, they suggest that training-free dependency analysis provides effective and inexpensive support for prioritizing architectural review. Learned models can be expected to add value only where no analytical approximation aligned with the simulator is available, a condition this corpus did not exercise.

These findings concern simulated failures on synthetic architectures and single-modeler system models, and their validation against real outages is the natural next step (§7.6). More broadly, the study suggests that the central challenge in architecture-level cascade-impact analysis is not selecting increasingly sophisticated learning algorithms, but deriving meaningful dependency representations and understanding when learning adds value beyond them. By making this comparison explicit and by releasing a reproducible benchmark with reconciled results, Software-as-a-Graph provides a foundation for more principled evaluation of analytical and learned methods for pre-deployment architecture analysis.
