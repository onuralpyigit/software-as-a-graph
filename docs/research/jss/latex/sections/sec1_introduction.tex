\section{Introduction}
\label{sec:1}

\subsection{Motivation and Problem}
\label{sec:1.1}

Large distributed systems now often use asynchronous publish-subscribe (pub-sub) middleware. Examples include ROS 2 for autonomous driving \cite{macenski2022robot}, Apache Kafka for enterprise event streams \cite{kreps2011kafka}, DDS in cyber-physical systems \cite{omg2015dds}, MQTT in IoT \cite{oasis2019mqtt}, and cloud-native microservices \cite{dragoni2017microservices,newman2015building}. Pub-sub separates producers and consumers by space, time, and synchronization \cite{eugster2003faces}. Instead of direct references, components communicate via topics and brokers, and Quality-of-Service (QoS) policies set at deployment control reliability, durability, priority, and deadlines.

This decoupling also makes it harder to see how failures spread. Since publishers and subscribers are not directly connected, problems like outages, blocking, and backpressure can move through undetected paths involving brokers, shared topics, colocated hosts, and shared libraries \cite{motter2002cascade,buldyrev2010cascade}. Failures usually appear in two ways. In sequential cascades, a slow subscriber fills up a broker queue and gradually starves its publishers \cite{albert2000error}. In simultaneous blasts, a crash in a shared library or a host outage can bring down all colocated services at once. These issues are not visible in architecture diagrams or static call graphs. The best time to handle these risks is before deployment, during design and continuous integration \cite{avizienis2004basic,bass2012software}, when runtime telemetry is unavailable. Therefore, architects must identify the most critical application services, topics, and links using only configuration manifests.

Current practices leave a serious gap, which we call the Architecture–Code Gap. A distributed system might have no compile-time bugs in any service but still face major outages due to hidden single points of failure, unbuffered queue bottlenecks, or mismatched QoS contracts \cite{perry1992foundations,garcia2009identifying}. Approaches like the Architecture Tradeoff Analysis Method (ATAM) depend on manual input \cite{kazman1998atam}. Static code analysis inspects services in isolation \cite{sonarsource2024clean,chidamber1994metrics}. Chaos engineering \cite{basiri2016chaos} needs a working cluster, and pre-production tests like fault injection \cite{meiklejohn2021service} and dependency tracing \cite{yu2021microrank} require runnable environments. In continuous integration, heavy fault injection or chaos experiments use significant computing power and energy, so pre-deployment static analysis is a greener option if it is accurate enough \cite{calero2015green,verdecchia2023greenai,schwartz2020greenai}. Graph-based representations have long supported reliability and defect analysis \cite{yacoub2002reliability,zimmermann2008predicting}, and graph learning has recently been applied to network criticality \cite{fan2020keyplayers,fan2019learning} and to microservice architectures \cite{khodabandeh2025linkpred}. Such models can combine structural and contractual information, but it remains unclear whether their predictive performance arises from the learning algorithm or from the dependency representation it operates on, and when learning adds value beyond analytical methods derived from the same dependencies. Software-as-a-Graph (SaG) addresses this question by deriving explicit dependency graphs from deployment manifests and enabling a controlled comparison of analytical, hybrid and learned approaches to cascade-impact ranking before deployment.

\subsection{The Software-as-a-Graph (SaG) Approach}
\label{sec:1.3}

Software-as-a-Graph (SaG) is a pre-deployment analysis framework for event-driven architectures (Figure~\ref{fig:1}). It models an architecture as a typed, directed multigraph over Applications, Brokers, Topics, Execution Hosts and Shared Libraries (Section~\ref{sec:3.1}), and derives an explicit DEPENDS\_ON dependency graph through publish--subscribe rules (Section~\ref{sec:3.3}). On this basis, it supports analytical, hybrid and learned approaches to cascade-impact ranking (Sections~\ref{sec:4} and~\ref{sec:6.2}). This study uses it to determine when learned models add value beyond rankings derived directly from explicit dependencies.

Predictors read only the analysis graph. Ground truth comes from three simulators that run on the raw structural topology (Section~\ref{sec:4.3}) and encode different failure notions: structural reachability ($I^*$), discrete-event queue saturation ($I_{\text{dyn}}$) and multi-criteria fragmentation ($I_{\text{comp}}$). To avoid depending on one simulator's assumptions, every ranker is evaluated against all three. Because simulators and predictors read the same architecture, some analytical rankings restate a simulator's own propagation rule. A reference criterion (Section~\ref{sec:4.4}) reports these as references that measure circularity rather than as predictors. To bound, though not remove, this circularity, we also report partial correlations after removing the primary simulator, and we time the cost of running each simulator directly (Section~\ref{sec:rq4}). All conclusions are strictly conditional on simulation fidelity; validation against real failures in physical distributed environments remains future work (Section~\ref{sec:8.3}).

\noindent\textbf{Findings in brief.} Explicit dependency representations provide most of the predictive signal for the reachability and queue-flow simulators.

Making dependencies explicit enables graph learning. On the raw multigraph, every relation points away from Applications, so message passing never reaches the scored nodes, and the registered primary contrast (a heterogeneous graph transformer against the training-free baseline on that graph) was null ($\Delta\rho = +0.069$, $p = 0.266$). On the dependency graph, the same learners improve by $+0.08$ to $+0.11$, and graph attention reaches Spearman $\rho = 0.748$ against the reachability simulator.

The same representation also enables simple analytical rankings that match or exceed the learned models. Counting direct dependents, which is publish--subscribe afferent coupling, reaches $0.764$, and ablations show that the learner approaches this count by drawing on its degree features ($-0.14$ without them). On the expensive queue-flow simulator ($12.7$ CPU-hours to label the corpus), a rate-weighted first-order approximation reaches $0.830$ in milliseconds, matching or exceeding a gradient-boosted approximation trained on the simulator's labels ($0.799$). Declared publication rates and payload sizes carry measurable signal only on this simulator; declared QoS policies and QoS-weighted scores add none.

Learning adds measurable value in two places. First, hybrids that correct a closed-form prior significantly outperform the training-free baseline ($+0.103$ and $+0.130$, each on 11 of 12 folds). In an exploratory comparison, they are also the most consistent learned models across simulators, although on the multi-criteria simulator training-free scores aligned with its terms rank higher. Second, learned models transfer zero-shot to five stylized models of open-source systems better than the training-free baseline ($\rho \approx 0.81$ vs.\ $0.53$), mainly by separating inert from active components. Dependency counts rank higher still, and ordering among active components remains weak ($\rho_{>0} \le 0.342$).

In practice, the results favor training-free dependency analysis for routine use. Recovering 80\% of the true critical set requires reviewing about 40\% of Applications, so rankings suit prioritized review rather than blocking gates (Section~\ref{sec:8.1}).

\subsection{Research Questions}
\label{sec:1.4}

Establishing when learning is unnecessary is as informative as showing when it succeeds. Software engineering research has repeatedly found that simple metrics can match more complex models once the right information is available \cite{zimmermann2008predicting,premraj2011network,hellendoorn2017deep,errica2020fair}, and that analytical rankings are easier to explain, validate, and run in Continuous Integration and Continuous Deployment (CI/CD) pipelines. We therefore evaluate learned models against analytical rankings derived from the same dependencies, not only against structural baselines. Four research questions guide the study:

\begin{itemize}\tightlist
\item \textbf{RQ1 (Ranking accuracy):} \emph{How accurately do analytical, hybrid, and learned approaches rank components by cascading-failure impact on unseen architectures, and how close do they come to reference rankings that restate a simulator's propagation rule?}
\item \textbf{RQ2 (Sources of predictive performance):} \emph{At matched model capacity, which factors contribute most to ranking performance: the dependency representation, degree information, relation typing, Quality-of-Service (QoS) information, or the model family (attention or sum aggregation; graph neural network or gradient-boosted trees)?}
\item \textbf{RQ3 (Transfer):} \emph{How well do learned models trained on synthetic architectures transfer zero-shot to stylized models of five open-source systems, hand-authored by a single modeler, and does their ordering of components that actually propagate failures hold?}
\item \textbf{RQ4 (Cost):} \emph{What do analytical and learned approaches cost at CI/CD time in latency and estimated energy, which stage dominates, and how does this compare with running each simulator directly?}
\end{itemize}

The evaluation uses a version-controlled analysis plan. Only two contrasts in the plan are confirmatory. We registered the matched $2\times2$, the hybrids, the reference counts, the dependency-graph learners, the full-population queue-flow labels, and the sensitivity arms as planned extensions. We registered each before its own tests ran but after we knew the main result, and we report them as secondary results. The rest of the analysis is exploratory (Section~\ref{sec:6.3}). One change from the plan, not applying the registered nested hyperparameter selection, is disclosed and tested. The replication repository records the revision history and shows how these four research questions fit into the plan.

\subsection{Contributions}
\label{sec:1.5}

Evaluated with leave-one-scenario-out (LOSO) cross-validation on twelve synthetic architectures, against three failure simulators, and zero-shot on five hand-authored models of open-source systems, this paper makes five contributions:

\begin{enumerate}\tightlist
    \item \textbf{Explicit dependency derivation for publish--subscribe architectures} (Section~\ref{sec:3}). Typed rules derive dependency graphs from deployment manifests and expose sequential cascades through shared topics and simultaneous blasts through shared libraries. The derived graph is the main source of predictive signal: learners gain $+0.08$ to $+0.11$ on it compared with the raw multigraph, and its library-mediated rule adds $+0.058$ in transitive reach. We define infrastructure and colocation rules for completeness, while focusing our empirical evaluation strictly on developer-authored Application services.
    \item \textbf{A reference criterion for interpreting simulator-based evaluations} (Section~\ref{sec:4.4}). The criterion distinguishes rankings that restate a simulator's rule from rankings that predict it, so that analytical and learned methods can be interpreted on the same terms. Applied here, it shows that publish--subscribe afferent coupling recovers most of the reachability simulator.
    \item \textbf{A controlled study of when graph learning adds value beyond dependency analysis} (Sections~\ref{sec:rq1}--\ref{sec:rq3}). Matched-capacity comparisons and ablations separate the contributions of five factors: the dependency representation, which matters most; degree information, without which the learner loses $0.136$; relation typing, which has no effect; QoS information, where declared rates and payloads add signal only on the queue-flow simulator and QoS policies or QoS-weighted scores add none (revealing that declared QoS contracts carry negligible predictive utility for cascade ranking); and the model family. Hybrids that correct a closed-form prior significantly outperform the training-free baseline, but they transfer less well than pure learned models.
    \item \textbf{Analytical and learned approximations of an expensive simulator} (Sections~\ref{sec:6.2} and~\ref{sec:rq1}). On a queue-flow simulator that takes $12.7$ CPU-hours to label the corpus, a rate-weighted first-order approximation reaches $\rho = 0.830$ in milliseconds without training, matching or exceeding a gradient-boosted approximation trained on the simulator's labels ($0.799$; exploratory, added after the registered analyses).
    \item \textbf{A reproducible benchmark, cost analysis and practitioner guidance} (Sections~\ref{sec:6}, \ref{sec:rq4} and~\ref{sec:8.1}).
    \begin{itemize}\tightlist
        \item The benchmark comprises seventeen architectures (2{,}812 components), three simulators labeling all 1{,}321 synthetic Applications, a version-controlled analysis plan with disclosed amendments, byte-identically regenerable datasets, and mechanically reconciled results.
        \item Latencies measured on the same graphs, with coarse Thermal Design Power (TDP)-derived energy estimates, support practical guidance on when training-free dependency analysis suffices.
    \end{itemize}
\end{enumerate}

A previous conference paper \cite{yigit2025graph} introduced the publish--subscribe multigraph, the Application-level subscriber-to-publisher dependency (Rule~1 of Table~\ref{tab:2}), and a closed-form betweenness–articulation score similar to the training-free baseline (Eq.~\eqref{eq:topo}, unweighted and with weights $0.7$/$0.3$), which it validated against a reachability-loss simulation on synthetic topologies and two ROS~2 benchmarks. This paper adds the Library and infrastructure rules, QoS weighting and the QoS edge encoding, the reference criterion, the learned and hybrid engines, the analytical and learned simulator approximations, LOSO and zero-shot evaluation, the second and third oracles, the matched control, and the cost analysis.
