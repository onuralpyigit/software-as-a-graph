\section{Introduction}
\label{sec:1}

\subsection{Motivation and Problem}
\label{sec:1.1}

Large distributed systems increasingly communicate through asynchronous publish--subscribe (pub-sub) middleware: ROS~2 in autonomous driving \cite{macenski2022robot}, Apache Kafka in enterprise event streams \cite{kreps2011kafka}, DDS in cyber-physical systems \cite{omg2015dds}, MQTT in IoT \cite{oasis2019mqtt}, and cloud-native microservices \cite{dragoni2017microservices,newman2015building}. Pub-sub decouples producers and consumers in space, time and synchronization \cite{eugster2003faces}. Components interact through topics and brokers rather than direct references, and deployment-time Quality-of-Service (QoS) policies govern reliability, durability, priority and deadlines.

The same decoupling hides how failures spread. Publishers and subscribers share no direct link, so outages, head-of-line blocking and backpressure propagate along concealed paths through brokers, shared topics, colocated hosts and shared libraries \cite{motter2002cascade,buldyrev2010cascade}. These failures take two forms. In \emph{sequential cascades}, a slow subscriber fills a broker queue and gradually starves its publishers \cite{albert2000error}. In \emph{simultaneous blasts}, a shared-library crash or host outage takes down every colocated service at once. Neither architecture diagrams nor static call graphs show these mechanisms. The cheapest time to reduce the risk is before deployment, at design and continuous-integration time \cite{avizienis2004basic,bass2012software}, when no runtime telemetry exists. Architects therefore need to know, from configuration manifests alone, which components, topics and links are systemically critical and why.

Existing practice leaves this gap open, which we call the \textbf{Architecture--Code Gap}: a system can have bug-free code in every service and still be fragile through hidden single points of failure or mismatched QoS contracts \cite{perry1992foundations,garcia2009identifying}. Architecture evaluations such as ATAM rely on manual elicitation \cite{kazman1998atam}. Static code analysis inspects services in isolation \cite{sonarsource2024clean,chidamber1994metrics}. Chaos engineering \cite{basiri2016chaos} needs a provisioned cluster, while pre-production alternatives like service-level fault injection testing \cite{meiklejohn2021service} and microservice dependency tracing \cite{yu2021microrank} require runnable execution environments. Homogeneous centrality flattens typed topologies into untyped graphs \cite{freeman1977centrality,brandes2001faster}. Learned models, graph neural networks in particular, could combine these structural cues, but only if they read a graph on which failure paths are explicit. What is missing is such a representation for pub-sub systems, and evidence on what learning achieves on it: which learned rankers work, what they need, and whether they add anything over the coupling metrics that architecture research already has. This paper provides that evidence for one well-defined task, ranking components by simulated cascade impact before deployment.

\subsection{The Software-as-a-Graph (SaG) Approach}
\label{sec:1.3}

\textbf{Software-as-a-Graph (SaG)} is a pre-deployment static analysis framework for event-driven architectures (Figure~\ref{fig:1}). It (1)~models an architecture as a typed, directed multigraph over Applications, Brokers, Topics, Execution Hosts and Shared Libraries (Section~\ref{sec:3.1}); (2)~derives from it, through publish--subscribe rules, an explicit \texttt{DEPENDS\_ON} dependency graph (Section~\ref{sec:3.3}); and (3)~evaluates learned cascade-impact rankers---graph neural networks on the raw multigraph and on the dependency graph, hybrids, and learned surrogates, against a training-free baseline (Sections~\ref{sec:4} and~\ref{sec:6.2}). Predictors read only the analysis graph. Ground truth comes from three simulators that run on the raw structural topology (Section~\ref{sec:4.3}).

\noindent\textbf{What the ground truth is, and is not.} All ground truth in this study is simulated. The primary oracle $I^*$ is a reachability simulation that runs on the same manifest the predictors read, and its first propagation wave is exactly the number of a component's direct dependents (Section~\ref{sec:4.4}). Dependency counts are therefore reported as references that restate the oracle, never as predictors. The study measures agreement between learned rankers and simulators, not the prediction of observed outages. Because ranking against $I^*$ rewards restating its propagation rule, we bound the circularity with two further simulators and with partial correlations, and report the cost of running $I^*$ itself (Section~\ref{sec:rq4}); validation against observed failures remains open (Section~\ref{sec:8.3}).

\noindent\textbf{Findings in brief.} Where graph learning works, it works on the derived dependency graph: on the raw multigraph no forward message reaches the ranked Applications, and graph attention networks gain $+0.08$ to $+0.11$ by reading the dependency graph instead, while a heterogeneous transformer there is unstable across seeds. The best of them, a graph attention network, reaches $\rho = 0.748$ against the reachability oracle $I^*$. Rankings that restate $I^*$'s propagation rule set a reference level on it: the oracle's first-order expansion reaches $0.808$ and the number of direct dependents (publish--subscribe afferent coupling \cite{martin2003agile,rud2006ais}) $0.764$. The dependency-graph learner is statistically indistinguishable from that count but not equivalent to it, and only with its degree features: without them it loses $0.14$. The registered primary contrast, a heterogeneous graph transformer on the raw multigraph against a training-free baseline (QoS-weighted betweenness), was null ($+0.069$, $p = 0.266$), and applying the plan's selection rule afterwards does not change that. Two hybrids, learned engines corrected by that baseline, beat it on 11 of 12 synthetic architectures ($+0.103$ and $+0.130$, Holm-significant), but not their own base learners. On a queue-flow simulator whose labels cost $12.7$ CPU-hours, a learned surrogate over dependency-graph features, trained on those labels, ranks held-out architectures above every closed-form approximation ($0.799$ against $0.706$), and it is the only place where declared QoS contracts carry measurable signal; a GNN given the same labels does not. Zero-shot transfer to five open-source system models reaches $\rho \approx 0.81$, but agreement among components with nonzero impact is weak ($\rho_{>0} \le 0.34$). Feature extraction for learned ranking costs $4.5$--$72\times$ one reachability simulation. Learning thus adds little where the oracle is cheap and pays where it is expensive.

\subsection{Research Questions}
\label{sec:1.4}

\begin{itemize}\tightlist
\item \textbf{RQ1 (Ranking accuracy):} \emph{How accurately do learned engines (graph neural networks on the raw multigraph and on the dependency graph, hybrids, and learned surrogates) rank components by cascading-failure impact on unseen architectures, against a training-free baseline, and how close do they come to reference rankings that restate the oracle's propagation rule?}
\item \textbf{RQ2 (What learning needs):} \emph{What do learned engines need: which graph they read, their degree features, relation-specific (typed) parameters, or QoS inputs, once model capacity and edge-channel width are matched?}
\item \textbf{RQ3 (Transfer):} \emph{How well do learned engines trained on synthetic architectures transfer zero-shot to independently authored models inspired by five open-source systems?}
\item \textbf{RQ4 (Cost):} \emph{What does learned ranking cost at CI/CD time, which stage dominates, and how does it compare with running the simulation directly?}
\end{itemize}

\noindent The evaluation follows a version-controlled analysis plan. Only the plan's two contrasts are confirmatory; the matched $2\times2$, the hybrids, the reference counts, the dependency-graph learners, the full-population queue-flow labels and the round-8 arms were registered in later amendments, each before its own arms ran but after the primary result was known, and are reported as registered secondary results; the rest is exploratory (Section~\ref{sec:6.3}). One deviation from the plan, its unapplied selection rule, is disclosed and tested. Supplementary Section~\ref{S-supp:amendments} logs every amendment and maps these four research questions onto the plan.

\subsection{Contributions}
\label{sec:1.5}

Evaluated under leave-one-scenario-out (LOSO) cross-validation over twelve synthetic architectures and on five hand-authored models of open-source systems, this paper contributes:

\begin{enumerate}\tightlist
    \item \textbf{An evaluation of learning-based cascade-impact ranking on derived dependency graphs} (Sections~\ref{sec:6}--\ref{sec:7}): seventeen architectures (2{,}812 components), three simulation oracles labelled for every Application, graph neural networks on the raw multigraph and on the dependency graph, hybrid engines and learned surrogates, with a version-controlled analysis plan, its amendments and one disclosed deviation, and artifacts that regenerate byte-identically.
    \item \textbf{What graph learning needs, and a largely negative result where the oracle is cheap} (Sections~\ref{sec:rq1}--\ref{sec:rq2}). Graph attention networks gain $+0.08$ to $+0.11$ by reading the dependency graph, reaching $0.748$, indistinguishable from the direct-dependent count; the gain rests on the degree features they are given, and relation typing adds nothing at matched capacity. The registered primary contrast is null, and the hybrids beat the training-free baseline but not their base learners.
    \item \textbf{A positive result for learned surrogates where the oracle is expensive} (Section~\ref{sec:rq1}). A gradient-boosted surrogate trained on queue-flow labels beats every closed-form approximation of that oracle on held-out architectures, its QoS features carry the gain, and an attention-based GNN given the same labels fails.
    \item \textbf{One operational account of oracle circularity} (Section~\ref{sec:4.4}): a criterion for which rankings are references for which oracle, applied to all three, with partial correlations that show how much of each ranking survives outside the oracle it restates.
    \item \textbf{Explicit dependency rules for publish--subscribe architectures} (Section~\ref{sec:3}), extending the application-level rule of \cite{yigit2025graph} with library-mediated blasts and infrastructure rules, and stating the typed query behind afferent coupling.
    \item \textbf{A like-for-like cost profile} (Section~\ref{sec:rq4}) of the counting path, the oracle and the learned pipeline on the same graphs.
\end{enumerate}

\noindent A previous conference paper \cite{yigit2025graph} introduced the publish--subscribe multigraph, the Application-level subscriber$\to$publisher dependency (Rule~1 of Table~\ref{tab:2}) and a closed-form betweenness--articulation score of the same form as the training-free baseline (Eq.~\eqref{eq:topo}, unweighted and with weights $0.7$/$0.3$), and validated that score against a reachability-loss simulation on synthetic topologies and two ROS~2 benchmarks. Everything else is new in this paper: the Library and infrastructure rules (Rules~2--6, including library-mediated blasts), QoS weighting, the reference counts, the learned and hybrid engines, the QoS edge encoding, LOSO and zero-shot evaluation, the second and third oracles, the matched control and the cost profile.
