\section{Discussion, Threats to Validity, and Limitations}
\label{sec:8}

\subsection{Dependency Representation versus Model Complexity}
\label{sec:representation}

The central finding of this study is that, for the reachability and queue-flow simulators, explicit dependency representations contributed more to ranking performance than model complexity. The derived dependency graph enabled both analytical and learned approaches. Attention-based learners improved on it relative to the raw multigraph, and the improvement survives a control that passes raw-graph edges in both directions (Section~\ref{sec:rq2}).
It also survives the removal of every feature that computes part of the reachability simulator, without which the raw-graph learners collapse.
Yet rankings computed directly from the same graph, the direct-dependent count for the reachability simulator and the rate-weighted first-order expansion for the queue-flow simulator, were not distinguishable from, or exceeded, the best learned models. Pure learners on the raw multigraph did not outperform the training-free baseline, because messages never reached the scored components. In this corpus, explicit dependency derivation is therefore the principal source of predictive signal, not a preprocessing step for learning. The multi-criteria simulator is the exception: there, raw degree and betweenness, whose terms align with fragmentation, ranked highest.

\subsection{When Learning Adds Value, and Relative to What}
\label{sec:8.2}

The study does not show that learning is never useful; it shows where learning adds value and against which comparator. Relative to the training-free baseline, learning helped in two ways, both weak evidence for learning. Hybrids that correct a closed-form prior outperformed that baseline, also with its defect corrected, but not their own base learners, so the gain belongs to the baseline's weakness rather than to the correction; given the direct-dependent count as their prior, they reproduce it. And learned models transferred zero-shot better than the baseline, mainly by separating inert from active components. Relative to analytical references built on the same dependencies, no learned model showed additional skill: the references were indistinguishable from or exceeded the learned models in-distribution, ranked higher in transfer, and ordering among components that actually propagate failures remained weak for every learned model ($\rho_{>0} \le 0.342$).
The most direct test of learning beyond an aligned analytical ranking, learners that start from the rate-weighted approximation, found no improvement on it (Section~\ref{sec:rq1}).
Learning is therefore likely to contribute most where impact depends on mechanisms that no available analytical approximation captures, a condition this corpus did not exercise. A per-regime breakdown by architecture type is given in Supplementary Section~\ref{supp:regimes}.

\noindent\textbf{How message passing contributes.} On the raw multigraph, learning used node properties, not relations: gradient-boosted trees on the same per-node features and no graph (\texttt{GBM-Feat}) reach $\rho = 0.642$ under LOSO, similar to \texttt{GAT-QoS} ($0.635$); forward GAT convolutions send no message to Applications; and removing HGT's reverse pass, its only route to them, has no effect. On the derived dependency graph, three layers of message passing gather the dependent neighborhood. Attention still needs the degree columns to approach the dependent count, whereas sum aggregation recovers most of it from structure alone (Section~\ref{sec:rq2}).

\noindent\textbf{What the study can say about relation typing.} Little. On the raw multigraph, where typing was compared at matched capacity, messages never reach Applications, so that comparison is between per-node models and carries no information about relational message passing (Supplementary Table~\ref{tab:contrasts_matched}). On the dependency graph, where messages do reach Applications, the projection has only two relation types, and the heterogeneous transformer (\texttt{HGT-P-QoS}) ran in one untuned configuration (width 100) in which some seeds converged to rankings anti-correlated with the oracle (mean within-fold seed standard deviation $0.254$, mean $\rho = 0.514$), while \texttt{GAT-P-QoS} was stable ($0.030$, $\rho = 0.748$). That is an optimization failure of one configuration, not evidence about typing; testing typing would need a substrate with active message passing and more relation types, and a tuned heterogeneous model.

\noindent\textbf{Why the learned queue-flow approximation does not exceed the formula.} The gradient-boosted approximation ($0.799$) beats the unweighted first-order expansion ($0.706$) because it reads the declared publication rates and payload sizes that $I_{\text{dyn}}$ uses. Once rates enter the analytical expansion (Eq.~\eqref{eq:rate-expansion}), it reaches $0.830$ and exceeds the learned approximation (exploratory), so the deficit is not one of missing inputs. Starting the learners from the formula does not help either: given it as an input, the tree model only matches it, and a GAT given it as a prior stays below it (Section~\ref{sec:rq1}).

\subsection{Restatement versus Prediction}
\label{sec:restatement}

Several of the highest-scoring rankings largely restate a simulator's propagation rule: the direct-dependent count and the first-order expansion for the reachability simulator, and the rate-weighted first-order approximation for the queue-flow simulator. The reference criterion (Section~\ref{sec:4.4}) distinguishes recovering a simulator's definition from predicting its outcomes, and it changes how both analytical and learned results should be read. A learned model that approaches a reference has learned the simulator's first-order rule, not necessarily anything beyond it. Because simulation-labeled benchmarks are common in architecture analysis, the criterion offers a general check for evaluations of this kind: before crediting a learned model with predictive skill, compare it against the simplest ranking that restates the simulator's own computation.

\subsection{Practical Consequences}
\label{sec:8.1}

\noindent\textbf{Choosing a ranker by simulator cost.} If the simulator is cheap, like $I^*$ ($0.01$--$0.72$~s per pass over a corpus architecture's Applications), its ranking can be computed directly from the manifest, and publish--subscribe afferent coupling \cite{martin2003agile,rud2006ais}, not distinguishable from any GNN tested, costs a fraction of that; its value is cost, not predictive skill, because it restates the simulator's first wave. If the simulator is expensive, like $I_{\text{dyn}}$ ($12.7$ CPU-hours for the corpus), the rate-weighted expansion approximates it at $\rho = 0.830$ in milliseconds and exceeds a gradient-boosted approximation trained on its labels ($0.799$; exploratory). Neither simulator, nor any approximation of it, has been shown to predict real outages.

\noindent\textbf{Choosing a ranker by failure notion.} Table~\ref{tab:guidance} summarizes the evidence by oracle. It is conditional on simulation fidelity: where a simulator misses a physical failure mode (partial partitions, disk thrashing), rankings on real clusters could diverge. For reachability impact, running $I^*$ itself is the simplest and cheapest option; no learned ranker is distinguishable from the direct-dependent count. For queue-flow impact, the rate-weighted expansion is the recommended ranker, and declared publication rates and payload sizes, not QoS policies, are the only declared information that carried signal. For fragmentation and throughput loss, betweenness-based scores rank highest because they align with the oracle's terms. On unfamiliar topologies, learned rankers transfer better than the training-free baseline, but active-stratum agreement is weak and the evidence rests on five models by one author.

\noindent\textbf{Mitigating Alert Fatigue with a Two-Tiered Triage Protocol.} Using a top-20\% threshold on the direct-dependent count (\texttt{InDeg}) recovers about half of the true top-20\% set on $I^*$ ($0.49$), while the rest of the flagged items are not in that set; the best learned ranker does no better (\texttt{GAT-P-QoS}, $0.48$). Figure~\ref{fig:recall} shows the trade-off: recovering 80\% of the critical set takes the top 45\% by \texttt{InDeg} ($0.83$) or the top 40\% by \texttt{GAT-P-QoS} ($0.81$), \texttt{Topo-QoS} does not reach this level within the top 50\%, and no predictor reaches 90\% within the top 50\%. A gate that catches most critical components would flag nearly half the system, so these rankers are unsuitable as automated pass/fail filters.

We instead propose a two-tiered triage protocol as an inspection heuristic; it is a proposal that needs human-factors and workflow validation before adoption:
\begin{enumerate}\tightlist
    \item \textbf{Tier 1 (Commit-stage triage):} When reviewing pull requests, compute the direct-dependent count (milliseconds, well under a joule) and the rate-weighted first-order expansion (Eq.~\eqref{eq:rate-expansion}; about a millisecond; an exploratory result, not confirmed on new data). Show the top 5 components by each as an informational note in the pull request review. This highlights potential cascade risks for peer review without blocking developers or causing alert fatigue.
    \item \textbf{Tier 2 (Staging and sprint verification):} During nightly builds or sprint architecture reviews, run the simulators on the Tier-1 shortlist within a fixed inspection budget, such as the ten highest-ranked services, and reserve redundant broker routing or chaos fault injection for the components the simulation confirms.
\end{enumerate}

\noindent\textbf{Cost and Green CI/CD.} Counting dependents is the cheapest ranker and a single $I^*$ pass the next; the features learned rankers read cost more than the simulator they approximate (Table~\ref{tab:cost-ll}). For the queue-flow simulator, the rate-weighted expansion replaces an estimated $355.6$~Wh of simulation for the corpus with milliseconds of computation. Training-free dependency analysis is therefore the lower-energy choice at both commit and staging time \cite{schwartz2020greenai,verdecchia2023greenai,calero2015green}; the energy figures are TDP-based estimates, not measurements (Section~\ref{sec:threats}).

\subsection{Threats to Validity}
\label{sec:8.3}
\label{sec:threats}

\noindent\textbf{Construct validity and oracle circularity.} All labels are simulated: no ranker is validated against observed failures, and no fault was injected into a running cluster, so the findings establish what can be predicted within the evaluated simulators, not what predicts real failures. The simulators omit runtime dynamics such as buffer bloat, thread-pool exhaustion, garbage-collection pauses and retry storms, and some real outages are sustained by load feedback rather than by structure \cite{bronson2021metastable,huang2022metastable}; there, structural rankings, analytical or learned, may misestimate criticality. Validation on real topologies and real failures is therefore the first priority (Section~\ref{sec:limitations}). The circularity is analyzed in Section~\ref{sec:4.4}: the dependency counts restate $I^*$, the rate-weighted expansion restates $I_{\text{dyn}}$, closed-form centrality is term-aligned with $I_{\text{comp}}$, and the learned rankers inherit part of the overlap through the features they read and through being fitted to the oracle. The counts were reclassified as references after all results were final; no number changed. The two other oracles bound, but do not remove, the threat, and all three are well approximated by low-order functions of the dependency graph (a first-order expansion recovers $0.808$ of $I^*$ and a rate-weighted one $0.830$ of $I_{\text{dyn}}$), so the benchmark cannot exhibit a regime in which learning exceeds an aligned analytical ranking; its absence here is a property of these oracles, not evidence that none exists. The reverse-edge control shares one set of weights across both directions; a direction-typed variant was not tested. Rules~2--4 and~6, which govern brokers and hosts, are untested.

\noindent\textbf{Internal validity, reproducibility, and drift.} No ranker reads simulator output (regression tests verify this), although the raw-graph learners read the structural edges the oracles traverse. Capacity, depth and early stopping were held constant across comparison arms; the registered selection rule was not applied to the published learned results (Section~\ref{sec:6.3}), so every learned result is conditional on one fixed configuration. The learned rankers are seed-sensitive: the mean within-fold standard deviation of $\rho$ is $0.099$ for \texttt{HGT-QoS}, $0.254$ for \texttt{HGT-P-QoS} and $0.024$--$0.030$ for the GATs, and one of 60 \texttt{HGT-QoS} runs and four of 60 \texttt{HGT-P-QoS} runs converge to rankings anti-correlated with the oracle (none for either GAT). They are kept in the per-seed means, as registered, so the \texttt{HGT} rows reflect training instability as much as typing. Across revision cycles and compute devices, the absolute value of a learned cell drifted by up to $0.172$, so learned cells from different sweeps or devices should not be compared. Every learned-versus-learned contrast this paper tests is instead paired within one CPU sweep in which the re-run comparators reproduce their published per-seed $\rho$ (exactly, or within $1.2\times10^{-4}$ for one); the exception, the nested-selection check, compares two harnesses and is reported as a protocol comparison (Section~\ref{sec:4.2}). Paired contrasts were not repeated on a second device. Node order is a further source of variance: three permutations of the input order move \texttt{GAT-P-QoS} by about $0.04$ per fold around a mean $0.019$ below the published value (Section~\ref{sec:rq2}), so learned-ranker differences of that size are not interpretable. CDI uses hash-dependent tie-breaking, so \texttt{PYTHONHASHSEED=0} is fixed, and all reported values are reconciled mechanically against released artifacts.

\noindent\textbf{External validity and the single-modeler threat.} Synthetic topologies come from a single generator family, which may induce parametric regularities not representative of heterogeneous industrial architectures. The five system models are hand-authored approximations (22--41 Applications) of open-source projects, each written by the first author from public documentation. All five RQ3 results are exposed to this threat, and it is not mitigated: no second modeler authored any model independently, and no inter-modeler reliability or agreement metric is reported. The system models also differ structurally from the synthetic folds: a larger share of their Applications has zero simulated impact, and their fan-in is more concentrated, favoring \texttt{Reach} and inflating full-population $\rho$. Two of the five (Train-Ticket and Online Boutique) are RPC systems re-expressed as publish--subscribe meshes; the translation keeps bidirectional dataflow but drops synchronous blocking, timeouts and thread starvation. No topology in the study was extracted from a real deployment manifest. We did not evaluate architectures with tens of thousands of components; we timed the counting path up to $10{,}000$ components (Section~\ref{sec:rq4}), and we did not evaluate the learned rankers or the oracles. We did not reproduce published learned criticality models (FINDER, DrBC) because they do not support typed multigraphs or pub-sub semantics.

\noindent\textbf{Sustainability and energy estimation validity.} Energy figures (Section~\ref{sec:rq4}) are wall-clock time multiplied by the processor's $28$~W base power (\path{reproduce/energy_estimate.py}), not readings from RAPL counters or power meters. They ignore frequency scaling, turbo power above base (up to $64$~W on this processor), DRAM and idle power, and attribute whole-package power to single-threaded work. They support order-of-magnitude comparisons between milliseconds and hours of computation, not energy or emissions accounting.

\noindent\textbf{Conclusion validity.} Only the plan's two co-primary contrasts are confirmatory, and both were null (Section~\ref{sec:6.3}); everything else was designed after that result was known. LOSO folds share ten of eleven training scenarios, so Wilcoxon $p$-values are nominal and anti-conservative; the Nadeau--Bengio corrected test leaves the hybrid contrasts significant and the primary null. Twelve folds from one generator make the effective sample small, bootstrap CIs coarse, and the study underpowered for equivalence at $\pm 0.05$ (the $90\%$ interval of the \texttt{GAT-P-QoS}--\texttt{InDeg} difference is $\pm 0.076$); ``matches'' therefore means not significantly different. Weighting folds by $|V_{\text{app}}|$ raises \texttt{Topo-QoS} to the level of the raw-graph learned rankers.

\subsection{Limitations and Future Work}
\label{sec:8.4}
\label{sec:limitations}

Six directions follow from the study's central question, in order of priority:
\begin{enumerate}\tightlist
    \item \textbf{Real topologies and real failures:} automatic extraction of SaG models from real artifacts (ROS~2 launch files with HAROS or ROSDiscover \cite{santos2019haros,timperley2022rosdiscover}, docker-compose and Kubernetes manifests), so that the derivation is exercised on real manifests, followed by controlled fault injection on ROS~2, Kafka and MQTT deployments (for example with Chaos Mesh or ChaosBlade), reference systems with known faults such as Train-Ticket \cite{zhou2018trainticket}, and incident data from industrial publish--subscribe systems. This should be coupled with runtime distributed tracing standards (e.g., OpenTelemetry, W3C Trace Context) to empirically validate whether static declared dependency paths faithfully reflect dynamic runtime message flow trajectories under normal and degraded conditions.
    \item \textbf{A confirmation corpus:} scenarios generated after the analysis is frozen, on which the registered secondary and exploratory claims of this paper, all specified after the primary null, are re-tested.
    \item \textbf{Infrastructure and broker validation:} extending cascade-impact evaluation beyond Applications to message brokers, topics, and compute hosts (evaluating Rules~2--4 and~6), which were outside the Application-scoped evaluation of this study.
    \item \textbf{Independent modelers:} replication of the five system models by additional modelers, with inter-modeler agreement reported.
    \item \textbf{Alternative impact models:} testing whether the conclusions hold for simulators with different failure mechanisms, including synchronous call semantics, which the current dependency rules do not model, and oracles with non-first-order mechanisms such as backpressure onto publishers, retry amplification and heterogeneous service capacity, where an aligned analytical approximation may not exist.
    \item \textbf{When learning exceeds analytical methods:} identifying impact-generation mechanisms whose predictive signal no aligned analytical approximation captures, and testing learners there; in this corpus, learners started from the rate-weighted approximation did not improve on it.
\end{enumerate}
Further extensions are integration with service mesh telemetry and distributed tracing (e.g., OpenTelemetry, Jaeger) for runtime dependency drift detection; hardware-measured energy accounting (RAPL counters required privileges unavailable for this study); a queue-flow run with QoS policies disabled; a tie-aware listwise loss with scenario-level validation; a full hyperparameter search for every learned model; and validation of the proposed explanation layer.
