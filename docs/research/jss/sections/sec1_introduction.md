# 1. Introduction

## 1.1 Motivation

Many modern distributed software systems use asynchronous, event-driven, publish-subscribe (pub-sub) architectures. These are widely used in areas like autonomous driving (ROS 2 [1]), enterprise event streams (Apache Kafka [2]), cyber-physical systems (DDS [3]), IoT deployments (MQTT [4]), cloud-native microservices [5, 6], and distributed AI/LLM clusters. In pub-sub systems, producers and consumers are separated by space, time, and synchronization [7]. Components communicate through message topics and brokers, so they do not need to reference each other directly. Middleware also provides Quality-of-Service (QoS) features like reliability, durability, message priorities, and delivery deadlines, which help systems stay reliable under heavy load or network problems.

This separation helps systems scale, but it also makes it harder to see how components interact. Unlike synchronous systems such as RESTful HTTP or gRPC, which have clear caller-callee paths, pub-sub systems lack direct links between publishers and subscribers. As a result, failures, blocking, and backpressure can spread along hidden paths involving brokers, shared topics, hosts, and libraries [8, 9]. These problems usually show up in two ways: sequential cascades, where a slow subscriber fills up a broker queue and slows down publishers [10]; and simultaneous failures, where a shared library crash or host outage affects all services on that host. Standard architecture diagrams and call graphs do not show these processes well. The best time to address these risks is before deployment, especially during design and continuous integration, following dependable computing principles [11, 12]. At this stage, there is no runtime telemetry or operational logs. Architects and Site Reliability Engineers need to find critical components, topics, and links, understand their importance, and take steps like replicating brokers, splitting overloaded topics, or isolating shared libraries to reduce risk. Here, systemic criticality means a component is likely a single point of failure or a hub that can spread errors widely across the system. Analyzing architecture directly from configuration files with pre-deployment Static System Analysis removes the need for staging clusters and live fault injection, which reduces overhead. However, static analysis before deployment is slower than in-process simulation: extracting topological features takes $79.3\,\text{s}$ for a 520-component system and $239.3\,\text{s}$ for 2,000 components. In comparison, the in-process discrete-event cascade simulator is much faster, taking only $0.08$ to $4.5\,\text{s}$ (§§7.5.1 and 8.2). The graph neural network (GNN) forward pass is even faster at $56\,\text{ms}$. In twelve tested scenarios, static analysis without caching is $2$ to $18$ times slower than in-process simulation (median $5.6$ times slower, with the biggest gap on the largest system). This shows that static analysis mainly avoids extra infrastructure rather than speeding up CPU execution, unless it uses incremental topology caching.

## 1.2 Problem Statement: The Architecture–Code Gap and the Black-Box

Pre-deployment dependability analysis in distributed systems has two main tasks. The first is predictive forecasting: can a data-driven, relation-specific graph neural network predict cascading failure blast radii and find critical components better than standard topological metrics? While closed-form metrics show overall network connectivity, it is unclear whether they capture how failures spread across different connection types; we test this directly (§7.1). We train and test the predictive model against independent simulation results, using it to rank and identify critical sets. To go beyond ranking, we use Explainable Criticality Attribution (Explanation Layer). A ranked list shows where risk is highest, but not how to fix it. So, we pair the predictor with an interpretable structural quality profile based on ISO/IEC 25010 [13] and ISO/IEC 25019 [14]. This layer diagnoses structural risk types using standard software quality models. For example, it can distinguish between an unreplicated single point of failure, a cascade hub, or a maintainability bottleneck, helping guide targeted fixes. This layer explains, but does not rank. Both the ranking and explanation models use the same graph but do not share parameters or outputs; by default, the link between them is off and used only for ablation (§4.2). This independence lets Software-as-a-Graph (SaG) find components that are structurally central but not operationally critical, which neither model could do alone. The gap between designed and actual architecture is well known: Perry and Wolf [15] described architectural erosion thirty years ago, and technical debt literature has tracked it since [16, 17]. The **Architecture–Code Gap** here refers to asynchronous middleware, where failure risks are not visible to build pipelines: *a distributed system can have perfect, bug-free code in each service, but still be vulnerable to outages from hidden single points of failure (SPOFs) or mismatched middleware Quality-of-Service (QoS) contracts.* This is especially true in pub-sub systems where producers and consumers do not have static links. Traditional architecture reviews (like ATAM [18, 12]) rely on manual input; static code analysis [19, 20, 21, 22] looks at services one by one; chaos engineering [23] needs staging clusters; and homogeneous centrality [24, 25, 26, 27] flattens different types of topologies into one. Section 2 covers each approach in detail. Even with advances in machine learning, current AI tools for system dependability often work as black boxes. Deep neural models usually give risk scores or hidden representations without clear, actionable reasons for their predictions. In critical software engineering, this is not enough; developers and Site Reliability Engineers need clear explanations of vulnerabilities and architectural problems to support code changes or infrastructure updates.

## 1.3 The Software-as-a-Graph (SaG) Approach

To address both the Architecture–Code Gap and the black-box AI problem, this work introduces Software-as-a-Graph (SaG), an AI-based pre-deployment Static System Analysis (SSA) framework for asynchronous and event-driven distributed systems. SaG’s core contribution is a four-stage pipeline that predicts systemically critical components and explains their structural root causes using pre-deployment data. SaG applies Architecture-as-Code by: (1) modeling the architecture as a typed, directed multigraph of Applications, Brokers, Topics, Execution Hosts, and Shared Libraries (Section 3.1); (2) mapping physical connections into a QoS-weighted semantic DEPENDS_ON layer to capture both sequential cascades and simultaneous failures (Section 3.2); (3) training a Heterogeneous Graph Transformer (HGT) to predict multi-hop cascading failures (Section 4); and (4) using an explainable, standards-based Reliability–Maintainability (RM) profile (Section 5) to identify the causes of component weaknesses.

A key feature of SaG is its strict input–label independence guarantee: the learned models and attribution baselines use only the analytical graph $G_{\text{analysis}}$. Ground-truth failure impacts come from separate discrete-event simulators running on the raw structural topology $G_{\text{structural}}$ (Section 4.4). This separation keeps feature construction and evaluation ground truth independent. Section 3 explains the full architectural flow and how the pipeline stages interact (see Figure 1).

#### The Core Claim and Bound. The main claim of this paper is that pre-deployment Architecture-as-Code manifests contain enough relational and QoS information to predict multi-hop cascading failures and identify critical components, without running code, collecting telemetry, or setting up staging clusters. In particular, relation-specific heterogeneous graph attention (HGT-QoS) adds important inductive bias to capture how failures spread indirectly across brokers, topics, and shared libraries, even when the system changes. This claim depends on two tested conditions: 

1.  **The Typing–QoS Substitution Effect:** Relational typing and continuous QoS edge encodings act as empirical substitutes rather than additive complements. While each independently produces substantial gains over an unweighted baseline ($+0.134$ and $+0.187$, Holm $p = 0.0015$), combining both exhibits diminishing returns because both channels supply redundant indicators of edge relation identity (§7.2).

2.  **Communication Paradigm Alignment:** Relational inductive bias transfers zero-shot to asynchronous publish–subscribe event meshes (where failure propagation flows forward via message starvation), but reverses on synchronous RPC call trees (where failures cascade backward via timeouts and retries), showing that graph directional biases must correspond to architectural communication semantics (§7.4).

#### Operational Guidance
To help teams use SaG effectively, it offers a range of methods suited to different software engineering needs:

-   HGT-QoS (Heterogeneous Learning): Recommended for complex asynchronous publish–subscribe event meshes (such as ROS 2, DDS, MQTT) where cascading failures move through multi-hop broker topologies, shared libraries, and hardware hosts in new or changing architectures.

-   Topo-QoS (Closed-Form Centrality): Recommended for lightweight, zero-training CI/CD gates that need instant deterministic scoring without GPU resources or model training cost ($\rho = 0.553$).

-   Dual-Engine Consensus Protocol: Recommended for production pre-deployment gating (Section 8.1). Because label-free uncertainty cannot reliably predict when an ML model struggles out-of-distribution ($\rho_s = -0.126$), SaG evaluates HGT-QoS and Topo-QoS at the same time: components in the unanimous top-$K$ intersection receive high-confidence triage, while ranking differences trigger architectural review.

- -   Explanation Layer ($Q(v)$ - ISO/IEC 25010): Used after ranking as a diagnostic tool rather than a continuous ranker (Section 5), breaking down flagged components into standardized Reliability (Availability vs. Fault Tolerance) and Maintainability profiles to guide targeted refactoring (for example, broker replication vs. circuit breakers).
#### Rationale for Graph Learning vs. Direct Simulation

Even though discrete-event simulation $I^*(v)$ gives ground-truth criticality and runs in $0.08$ to $4.5\,\text{s}$, it is important to explain why we train a graph model. Manifest analysis avoids the need for staging clusters and chaos testing tools, so it saves infrastructure rather than energy; Section 8.2 measures the energy used by the analysis and CI/CD pipelines. Incremental caching could cut per-commit latency to under a second ($56\,\text{ms}$) by updating only changed subgraphs, but this is still a hypothesis, since actual speed depends on where the pull request sits in the topology. Without caching, static analysis is always slower than simulation in our tests. Message passing works for both labeled and unlabeled entities, so it can score shared libraries and hosts that node-level simulation does not cover. Two other reasons do not apply: cascade simulation is almost deterministic in this dataset (median test–retest $0.982$), and manifest-level fault injection does not need runnable containers. Section 7.1 checks if graph learning gives better rankings than closed-form baselines; whether signals combine with or substitute for architectural typing; whether the framework’s simulation oracles agree with each other; and whether the reported orderings are robust to the free parameters of the scorer and of the ground truth. RQ4 (Real-World Generalization): How effectively does the framework transfer zero-shot to real-world distributed systems across autonomous driving (ROS 2), cloud-native microservices, smart home IoT, and industrial edge computing?

-   **RQ5 (Analysis Cost):** *What does pre-deployment analysis cost at CI/CD time, which pipeline stage dominates that footprint, and how does it compare against the discrete-event simulation it is intended to displace?*

## 1.5 Key Contributions

This paper makes three main contributions:
1. *Heterogeneous Graph Learning for Dependability, and Its Boundaries* A relation-specific Heterogeneous Graph Transformer forecasts cascading blast radii from Architecture-as-Code manifests, using 16-dimensionalD QoS edge encodings and anextray component reliability head Section 4). When tested separately under distribution shifts across twelve architectures, relation-specific HGT shows out-of-distribution gains ($\Delta\rho = +0.234$ over an untyped baseline, $p = 0.0005$), marking the move to the parameterized bidirectional HGT architecture. Importantly, typing and continuous QoS encodings act as empirical substitutes rather than complements, even after transforming to a variance-stabilized scale. The typing factor also brings a $15.4\times$ capacity gap and changes message-passing directionality, which the reported controls do not separate. Compared to an unparameterized QoS-weighted centrality baseline, learned ranking does not show a statistically significant advantage ($+0.085$, $p = 0.151$. This result sets a boundary for the design rather than for graph learning itself. We report the substitution effect and the empirical boundary as main findings Sections 7.1–7.2)7.2).

2.  A Formal Typed Architecture Model: A multigraph representation that derives logical dependencies from physical pub-sub connections and distinguishes sequential cascade propagation from simultaneous multi-consumer library failures (Section 3).

3.  Empirical Benchmark, Real-World Transfer, and Cost Profile: A study across seventeen system architectures totaling 2,812 components, including twelve synthetic topologies (2,461 components across LOSO folds) and five open-source reference systems (351 components) with strict graph-view separation. We analyze pipeline costs, showing that the neural forward pass makes up only $0.02\%$ of runtime. In contrast, cold deterministic feature extraction dominates and costs $2$–$18\times$ more than the simulation it was meant to replace (median $5.6\times$ over twelve scenarios, $79.3\,\text{s}$ compared to $4.5\,\text{s}$ at its maximum), challenging the idea that static analysis is always faster than in-process simulation without incremental caching (Sections 6–7).

These results can change depending on the conditions. In the two most recent test runs, using the same seeds and data, the training-free results were identical. However, the learned fold averages varied by as much as $0.172$, which is twice the $+0.085$ margin used in the main comparison (Section 8.3). The direction of this difference is always the same, but its size depends on the released artifacts and is not a fixed property of the method.

#### Relationship to the authors’ prior work

An earlier conference paper [28] introduced the first version of the multigraph model and deterministic quality approach on synthetic systems. This JSS paper builds on that by adding the full predictive HGT pathway with 16-dimensional QoS edge encoding (§4), inductive LOSO cross-validation (§7.2), zero-shot testing on five open-source systems (§7.4), cost and sustainability analysis (§7.5), multi-oracle validation and graph-view separation (§§4.3–4.4), and system-wide sensitivity checks (§7.3). Only some formal parts from the conference paper remain in updated sections of §§3 and 5. Two earlier conclusions do not hold in this new analysis. Specifically, the deterministic quality model is not a strong ranking tool for this dataset ($\rho = 0.205$, lower than unweighted centrality, §7.1), and its weights perform worse than a uniform prior (§7.3). The dataset, oracles, and evaluation group all differ from [28], so these are updates to current knowledge, not failures to reproduce the original experiment. Section 2 reviews related work. Section 3 formalizes the SaG multigraph model and dependency projections. Section 4 details the Heterogeneous Graph Transformer and simulation oracles. Section 5 presents the ISO/IEC-grounded explanation layer. Section 6 outlines the experimental protocol, and Section 7 reports empirical results for RQ1–RQ5. Section 8 discusses practical consequences, sustainability, threats to validity, and limitations. Section 9 concludes.
