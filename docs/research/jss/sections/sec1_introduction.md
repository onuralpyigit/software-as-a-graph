# 1. Introduction

## 1.1 Motivation and Problem

Large distributed systems now often use asynchronous publish-subscribe (pub-sub) middleware. Examples include ROS 2 for autonomous driving [1], Apache Kafka for enterprise event streams [2], DDS in cyber-physical systems [3], MQTT in IoT [4], and cloud-native microservices [5, 6]. Pub-sub separates producers and consumers by space, time, and synchronization [7]. Instead of direct references, components communicate via topics and brokers, and Quality-of-Service (QoS) policies set at deployment control reliability, durability, priority, and deadlines.

This decoupling also makes it harder to see how failures spread. Since publishers and subscribers are not directly connected, problems like outages, blocking, and backpressure can move through undetected paths involving brokers, shared topics, colocated hosts, and shared libraries [8, 9]. Failures usually appear in two ways. In sequential cascades, a slow subscriber fills up a broker queue and gradually starves its publishers [10]. In simultaneous blasts, a crash in a shared library or a host outage can bring down all colocated services at once. These issues are not visible in architecture diagrams or static call graphs. The best time to handle these risks is before deployment, during design and continuous integration [11, 12], when runtime telemetry is unavailable. Therefore, architects must identify the most critical components, topics, and links using only configuration manifests.

Current practices leave a serious gap, which we call the Architecture–Code Gap. A distributed system might have no compile-time bugs in any service but still face major outages due to hidden single points of failure, unbuffered queue bottlenecks, or mismatched QoS contracts [13, 14]. Approaches like the Architecture Tradeoff Analysis Method (ATAM) depend on manual input [15]. Static code analysis inspects services in isolation [16, 17]. Chaos engineering [18] needs a working cluster, and pre-production tests like fault injection [19] and dependency tracing [20] require runnable environments. In continuous integration, heavy fault injection or chaos experiments use significant computing power and energy, so pre-deployment static analysis is a greener option if it is accurate enough [21, 22, 23]. Homogeneous centrality reduces typed topologies to untyped graphs [24, 25]. Graph neural networks can combine structural and contractual information, but only if the graph clearly shows failure paths. Software-as-a-Graph provides this representation, turning static deployment manifests into predictive insights before deployment and enabling a two-tier triage process to reduce developer alert fatigue.

## 1.2 The Software-as-a-Graph (SaG) Approach

Software-as-a-Graph (SaG) is a static analysis framework used before deployment for event-driven architectures (see Figure 1). First, it models the architecture as a typed, directed multigraph that includes Applications, Brokers, Topics, Execution Hosts, and Shared Libraries (§3.1). Next, it uses publish-subscribe rules to create a clear DEPENDS\_ON dependency graph (§3.3). Then, it tests learned cascade-impact rankers—such as graph neural networks on both the raw multigraph and the dependency graph, hybrids, and learned surrogates—against a baseline that does not use training (§§4 and 5.2). The predictors only use the analysis graph. Three simulators provide ground truth by running on the base structural topology (§4.3). To measure architectural risk without relying on single or unproven assumptions, SaG uses a tri-oracle evaluation suite. This suite covers structural reachability ($I^*$), dynamic discrete-event queue saturation ($I_{\text{dyn}}$), and multi-criteria service fragmentation ($I_{\text{comp}}$). The main reachability oracle $I^*$ works directly on communication topologies defined in the manifest, so its first-order propagation matches direct dependency counts (§4.4). To avoid mixing up structural alignment regarding predictive learning, the method tracks dependency counts as baseline references and carefully tests how well learned models generalize to dynamic queue flows and structural fragmentation. To address circularity, the evaluation uses three independent simulation methods, checks partial correlations outside the main oracle, and measures the exact computational cost of running $I^*$ (§6.4). Verifying these results against real-world failures is still an important goal (§7.3). The conclusions and guidance here are valid as long as the simulations are accurate.

Findings in brief. When graph learning is applied to the derived dependency graph, it achieves high-accuracy cascade prediction. Graph attention networks improve by $+0.08$ to $+0.11$ over the raw multigraph, reaching a Spearman correlation of $0.748$ against the reachability oracle. They also transfer well to five stylized models based on open-source systems, with correlation near $0.81$ and PR-AUC of $0.838$, though discrimination within the active stratum of a cascade drops. Causal ablation studies show that this strong reachability performance is closely tied to the number of direct dependents, which corresponds to the first propagation wave of the reachability oracle. The model captures this important topological signal through degree features, losing $0.14$ in performance without them. This shows that classical architectural coupling offers a fast, low-energy triage baseline. In high-fidelity dynamic queue-flow simulation, which takes $12.7$ CPU-hours (about $355.6$ Wh), learned models perform best: a gradient-boosted surrogate using dependency-graph features and declared rate/payload inputs ranks held-out architectures at correlation $0.799$, clearly beating all closed-form approximations, and declared QoS contracts add useful information; for failures involving multi-criteria structural fragmentation, hybrid engines that combine neural models with topologic priors remain stable, while pure neural models do not. On the raw multigraph, where forward messages do not reach Applications, the main comparison between a heterogeneous graph transformer and the training-free baseline showed no significant difference. Extracting features for learned ranking takes $4.5$ to $72.5$ times as long as a single reachability simulation. As a result, learning is most valuable when simulation is costly, supporting a sustainable two-tier deployment approach.

## 1.3 Research Questions

-   **RQ1 (Ranking accuracy):** *How accurately do learned engines rank components by cascading-failure impact on unseen architectures, against a training-free baseline, and how close do they come to reference rankings that restate the oracle’s propagation rule?*

-   **RQ2 (What learning needs):** *What do learned engines need: which graph they read, their degree features, relation-specific parameters, or QoS inputs, once model capacity and edge-channel width are matched?*

-   **RQ3 (Transfer):** *How well do learned engines trained using synthetic architectures transfer zero-shot to stylized architectural models hand-authored by a single modeler based on five open-source systems, and does within-cascade discrimination hold on the active stratum?*

-   **RQ4 (Cost and Sustainability):** *What does learned ranking cost at CI/CD time with respect to latency and computational energy, which stage dominates, and how does it compare with running the simulation directly?*

The evaluation uses a version-controlled analysis plan. Only two contrasts in the plan are confirmatory. We registered the matched $2\times2$, the hybrids, the reference counts, the dependency-graph learners, the full-population queue-flow labels, and the sensitivity arms as planned extensions. We registered each before its own tests ran but after we knew the main result, and we report them as secondary results. The rest of the analysis is exploratory (§5.3). One change from the plan, an unused selection rule, is disclosed and tested. The replication repository records the revision history and shows how these four research questions fit into the plan.

## 1.4 Contributions

This paper is evaluated using leave-one-scenario-out (LOSO) cross-validation on twelve synthetic architectures and five hand-crafted models based on open-source systems. It contributes:

1.  **The Software-as-a-Graph (SaG) framework and multi-oracle evaluation suite** (§§5–6): seventeen architectures spanning 2,812 components across twelve synthetic scenarios and five stylized system models; three distinct simulation oracles labelled for every Application; graph neural networks on the raw multigraph and on the dependency graph; hybrid engines and learned surrogates; and a version-controlled analysis plan, committed data manifests, and 1,548 byte-identically verified figures.

2.  **High-accuracy cascade prediction and causal demystification of graph learning mechanics** (§§6.1–6.2): Graph attention networks on the derived dependency graph achieve correlation $0.748$, gaining $+0.08$ to $+0.11$ over raw multigraphs; causal ablations show that their performance rests on degree features, while sum aggregation naturally counts neighbors, explaining why classical afferent coupling provides a zero-cost triage baseline for reachability.

3.  **A high-performance dynamic surrogate for Green CI/CD** (§6.1): A gradient-boosted surrogate trained on dynamic queue-flow labels using analytical first-order expansion, rate, and payload features alongside topological counts reaches $\rho = 0.799$ on held-out architectures, considerably outperforming closed-form approximations ($+0.094$, $p = 0.019$, nominal; folds share scenarios) and amortizing $12.7$ CPU-hours ($\sim 355.6$ Wh theoretical TDP proxy) of discrete-event simulation into sub-second inference.

4.  **Resilient hybrid architectures under multi-criteria fragmentation** (§6.1): Demonstrating that combining neural models with domain priors prevents catastrophic ranking collapse under structural fragmentation and flow disruption on architectures resembling the training distribution ($\rho = 0.585$ vs. $\le 0.334$), whereas pure learned models transfer better to substantially different architectures ($0.760$–$0.805$ vs. $0.662$–$0.695$).

5.  **Explicit graph derivation rules for publish–subscribe architectures** (§3): Extending the application-level rule of [26] with library-mediated blast radii, host colocation, and middleware QoS edge encodings.

6.  **A like-for-like computational cost and sustainability analysis** (§6.4): Measuring exact latencies and energy footprints across counting, simulation, and learned inference, establishing an actionable two-tier triage pipeline for continuous integration to reduce developer alert fatigue.

A previous conference paper [26] introduced the publish-subscribe multigraph, the Application-level subscriber-to-publisher dependency (Rule 1 of Table 2), and a closed-form betweenness–articulation score similar to the training-free baseline (Eq. 5, unweighted and with weights $0.7$/$0.3$). We validated that score against a reachability-loss simulation on synthetic topologies and two ROS 2 benchmarks. All other contributions in this paper are new: the Library and infrastructure rules (Rules 2–6, including library-mediated blasts), QoS weighting, the reference counts, the learned and hybrid engines, the QoS edge encoding, LOSO and zero-shot evaluation, the second and third oracles, the matched control, and the cost profile.
