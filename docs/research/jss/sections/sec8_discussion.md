# 8. Discussion, Threats to Validity, and Limitations

## 8.1 Discussion and Practical Consequences

**When to use Topo-QoS, and when to use HGT-QoS.** The findings do not support an unequivocal recommendation of the learned model over the closed-form alternative; we present empirical trade-offs directly.

-   **Training-free ranking (`Topo-QoS`) vs. Simulation.** `Topo-QoS` requires no training or checkpoints, reaching $\rho = 0.553$ zero-shot across twelve synthetic architectures and $0.526$ across five open-source ones, with no learned advantage ($+0.085$, $p = 0.151$). This equality reflects domain inductive bias: in asynchronous pub-sub architectures lacking severe backpressure, cascading failure is reachability-driven (recovered at $\rho = 0.965$ by topology alone), leaving relational GNNs minimal headroom over path centrality. On large diameters ($N \ge 500$, Enterprise), global paths resolve bottlenecks that 3-hop convolutions localize ($0.795$ vs. $0.461$). It is thus the zero-maintenance default for CI; where queue parameters exist ($N < 150$), direct simulation ($0.08$–$4.5\,\text{s}$) provides exact ground truth.

-   **When to deploy `HGT-QoS`.** `HGT-QoS` is justified when systems feature dense, irregular topologies with multi-tenant shared library or host dependencies under $N < 150$, where relational attention gains $+0.210$ to $+0.229$ over `Topo-QoS` (the synthetic Microservices and ATM folds, §7.2.1; note that on the transcribed Online Boutique mesh the ordering reverses on the full population, $0.769$ against $0.888$), and when teams require scoring of unsimulated non-runnable infrastructure entities (physical execution hosts, hardware network links) that node-level message flow simulation leaves unscored without dedicated physical failure models. Otherwise, untyped QoS-weighted GNNs offer a better efficiency trade-off ($\rho = 0.604$ with $28{,}168$ parameters vs. `HGT-QoS`’s $0.638$ with $434{,}620$), as combining typing and QoS yields minimal additive benefit.


-   **Capabilities without a closed-form counterpart.** Per-relation attention (§7.3.3) offers a typed diagnostic, but measured spread across relation types is narrow ($0.15$–$0.23$) and governed by destination in-degree, making it active but diagnostically unreliable on present evidence.

-   **Ingestion boundary and active-stratum reality.** Deployment must condition on communication synchrony (Table 13): on asynchronous pub-sub systems (ROS 2, DDS, MQTT, Kafka), `HGT-QoS` transfers positively on active components ($\rho_{>0} \in [+0.183, +0.702]$), whereas on synchronous call trees it inverts ($-0.031$ to $-0.192$) and should not be deployed — use static call-graph tools instead. While full-population transfer isolates inert services ($\rho = 0.760$), zero-shot ranking of active components remains unresolved without runtime telemetry.

**Dual-Engine Consensus Protocol.** In pre-deployment continuous integration, an automated heuristic fallback that conditionally routes predictions to a closed-form baseline based on label-free prediction dispersion $\hat{\sigma}$ is unviable because prediction variance exhibits a slightly negative correlation with out-of-distribution advantage ($\rho_s = -0.126$, §7.2.1). Rather than relying on fragile single-model uncertainty heuristics, SaG tackles this boundary through a principled **Dual-Engine Consensus Protocol**. The pipeline evaluates the learned relational model (`HGT-QoS`) and the closed-form topological baseline (`Topo-QoS`) concurrently. Entities identified in the top-$K$ critical set by both engines are classified as unanimous high-priority risks, while rank divergences are surfaced for architectural review. Given non-zero retraining drift across GPU sweeps ($0.041$ on fold mean, §8.3), production CI/CD deployments should freeze version-controlled model checkpoints rather than retraining on commit hooks.

**Role of the Explanation Layer.** The RM profile ($Q(v)$, §5) decomposes ISO/IEC 25010 structural mechanics to direct targeted refactoring (distinguishing Availability replication from Fault-Tolerance circuit breakers), while neural and centrality predictors govern triage priority. Its elicited AHP weights trail a uniform prior, which we recommend pending user studies.

## 8.2 Performance and Computational Sustainability Implications

**What sustainability means for a pre-deployment gate.** Green software engineering assesses energy across development, assurance, and execution [29, 88, 89, 90, 91, 30, 31]. Live chaos sweeps require cluster-hours across provisioned nodes; pre-deployment static analysis avoids provisioning clusters entirely. We state the benefit as infrastructure avoidance rather than measured energy savings, since we did not profile avoided execution. We bound the expended computation: taking Table 12’s wall-clock at base SoC power ($28\,\text{W}$), one pass over all twelve scenarios costs at most $3.0\,\text{kJ}$ ($0.83\,\text{Wh}$), with Enterprise accounting for $2.2\,\text{kJ}$, against $\le 0.31\,\text{kJ}$ ($0.086\,\text{Wh}$) for the oracle sweep. These upper bounds overstate draw because single-threaded execution shares package power and includes interpreter I/O. Direct joule profiling via RAPL/NVML [30, 32, 33] remains future work; gate energy is negligible except for staging clusters ($< 1\,\text{Wh}$), but it is not an empirical reduction.

**Where the cost actually sits.** We withdraw the efficiency claim: cold static analysis does not reduce CPU computation over simulation. The gate costs $2$–$18\times$ the cascade traversal across the twelve scenarios (median $5.6\times$; Table 12), rising to its maximum on Enterprise ($79.3\,\text{s}$ against $4.5\,\text{s}$) where CDI’s $O(|V|^2 + |V||E|)$ cost meets the densest derived projection in the corpus. It is more expensive in every scenario, so the comparison direction does not depend on which one is quoted. In CI, sustainability requires incremental caching: caching base metrics across commits and extracting features only for PR-delta subgraphs decreases latency to a sub-second forward pass ($56\,\text{ms}$). We emphasize this is an engineering hypothesis: delta latency depends on the PR diff’s topological centrality (leaf worker vs. central broker), and we focus on benchmarking commit-diff extraction across PR topologies.

## 8.3 Threats to Validity

**Construct Validity.** Ground-truth impact $I^*(v)$ derives from simulation rather than live outages. While $I^*$ correlates with dynamic queue flow $I_{\text{dyn}}$ ($\rho = 0.627$ against a $0.811$–$1.000$ ceiling, §7.3.2), top-$K$ Jaccard reaches only $0.27$–$0.37$, and $I^*(v)$ is recovered at $\rho = 0.965$ by topology-only relabeling, confirming the target captures reachability rather than runtime queue collapse or retry storms. More fundamentally, $I^*(v)$ is a deterministic functional of the graph the predictors read, so RQ1 asks a learned model to recover a closed-form graph computation from features that already summarise that graph — a task on which a strong closed-form comparator is expected, which bounds what the parity result says about graph learning generally. The remedy is internal: $I_{\text{dyn}}$ agrees with $I^*$ at only $\rho = 0.627$ and so carries the non-topological structure this design lacks. Retargeting the LOSO contrasts on it needs per-node predictions at the twelve-fold artifact’s fidelity, so it requires a full re-run and is the first experiment we intend to report. Validating topological cascades against production incident telemetry remains the central empirical frontier. Transcribing the open-source architectures also relied on standardized heuristics applied by a single coder, so there is no inter-coder agreement figure. Those five systems carry the whole of RQ4, and a transcription choice that systematically favored one predictor would be invisible to us; independent re-transcription of at least two of them is required before these numbers read as firmer than indicative.

**Internal Validity.** Feature leakage is prevented by strict graph separation: predictors consume $G_{\text{analysis}}$, while simulation oracles traverse $G_{\text{structural}}$ (CI-asserted). Parity is maintained via matched datasets, depths, and early stopping. Comparing `HGT-QoS` to `GAT-N-QoS` conflates typing with a $15.4\times$ capacity gap ($434{,}620$ vs. $28{,}168$) and bidirectional passing ($103{,}725$ reverse parameters in `HGTConv`), which four registered control arms would isolate (`GAT-N-C`, `GAT-N-QoS-C`, `GAT-N-QoS16-C`, `HGT-QoS-U`; §8.4). They are implemented in the replication package and registered with a decision rule fixed in advance, but none has been run at the reported budget, so this confound is disclosed rather than resolved. Six active QoS dimensions govern profiles, with one reserved extension point.

**External Validity.** The corpus comprises 2,812 components across seventeen architectures spanning six domains: robotics (ROS 2), smart cities, healthcare, finance, enterprise ESB, and edge IoT (EdgeX Foundry, Home Assistant). Heterogeneity exposes the active-stratum boundary condition: pub-sub cascades propagate forward via starvation ($\rho_{>0} \in [+0.183, +0.702]$, Table 9), whereas synchronous RPC microservices cascade backward along call trees via timeouts [48], where active correlation inverts ($-0.031$ to $-0.192$) and baselines fail (Table 10). Directional biases must condition on synchrony. Scaling beyond 2,000 nodes requires incremental caching or mini-batching (GraphSAINT [92]).

**Conclusion Validity.** Distributions are evaluated using a non-parametric correlation (Spearman $\rho$), bootstrap intervals ($B = 2{,}000$), and Wilcoxon signed-rank tests. Analyses are stratified because pooling node types conflates disparate strata (Execution Host $\rho = 0.138$ vs. Application $\rho = 0.597$), leaving the pooled figure ($0.217$) at less than two-fifths of the evaluated stratum. Because folds share training graphs, nominal Wilcoxon $p$-values are optimistic and interpreted descriptively alongside 12-fold sign consistency; synthetic graphs derive from a single generator family.

**Repeatability and GPU Re-Baseline.** Seed spread and run-to-run displacement are distinct quantities; only the former is reported in Table 6. At fixed code and seeds, the pipeline is deterministic: consecutive runs reproduced every reported figure identically. Across hardware platforms and code revisions, displacement is non-zero. Between the two most recent committed sweeps — transitioning from initial CPU runs to a full clean GPU (CUDA) re-baseline on an identical corpus digest — all $180$ training-free cells reproduced identically ($|\Delta\rho| = 0.000000$), confirming absolute determinism of graph extraction. In contrast, the $240$ learned cells shifted by up to $0.519$ at seed level and $0.172$ at fold mean (`GAT-N` on Healthcare, $0.600 \rightarrow 0.428$). This displacement stems from three documented technical factors: (1) resolving an upstream PyTorch Geometric device-placement bug in `HGTConv` (`saag/prediction/models/core.py`) that was masked on CPU; (2) eliminating stale checkpoint resumption artifacts by enforcing clean cache regeneration across all 12 folds; and (3) hardware non-determinism in CUDA atomic scatter/gather reductions during message passing. Crucially, under clean full GPU convergence, `HGT-QoS` regularly outperforms `HGT` ($0.638$ vs. $0.551$), while displacement is smallest for `HGT-QoS` ($0.041$ on fold mean). Read the sign of that result as robust and its magnitude as pinned to these artifacts. The Table 8 contrasts are better placed, being differences within one sweep. The per-arm ledger is in the replication package (`reproduce/rerun_drift.py`). Revisions also altered the active stratum ($n_{>0}$ shift $26\%$–$56\%$), making $\rho_{>0}$ non-comparable across revisions. Learned figures are pinned to commit artifacts; provenance tracking in Data Availability makes this auditable.

## 8.4 Limitations and Future Work

**Correction of the Real-World Baseline.** On raw multigraphs, betweenness vanishes for Application nodes; evaluating on `DEPENDS_ON` flow projections enables `Topo-QoS` across all five real-world systems (Table 9). **Explanation Layer Validation.** The explanation layer is presented as a design pattern rather than a validated contribution (§5): its elicited AHP weights rank worse than a uniform prior (§7.3), it trails unweighted centrality, and no user study has tested whether its archetypes help a developer act. We recommend the uniform prior and retain the elicited constant as the shipped default for one reason, stated. Hence, this is not inertia: the same shrinkage constant parameterizes the $I_{\text{comp}}$ severity weights, so moving it would silently relabel the composite oracle and every figure scored against it. Decoupling the two, then a mutation benchmark (inject a known single point of failure or cascade hub and test whether the layer names the right archetype) and a developer study, are the prerequisites for any evidential claim here. **Uncontrolled Confounds in Typing.** Table 8 holds substrate, depth, and training splits constant, but capacity ($434{,}620$ vs. $28{,}168$) and reverse directionality ($103{,}725$ parameters in `HGTConv`) remain unmatched; the $+0.134$ effect reflects the joint transition to HGT. Four control arms that isolate these factors — `GAT-N-C` and `GAT-N-QoS-C` (capacity-matched untyped models), `GAT-N-QoS16-C` (edge-channel width) and `HGT-QoS-U` (unidirectional passing) — are implemented in the replication package and registered in the analysis plan together with a decision rule fixed before any of them was run. None has yet been run at the reported budget. Running them is the single change that would most alter what §7.2 is entitled to claim, and the registered rule commits us to narrowing that claim if the margin does not survive. **No Comparison Against a Published Method.** Every comparator in this paper is either our own closed-form score or an ablation of our own model. §2.4 reviews learned node-criticality models (FINDER [64], DrBC [65], PowerGraph [66]) without replicating any of them, so the RQ1 finding is a statement about this heterogeneous transformer against these baselines, not about graph learning for criticality ranking in general. Reproducing DrBC or FINDER on this corpus — both address the ranking task directly — is the comparison that would generalize the claim, and its absence is the clearest gap in the evaluation. **Absence of Live Incident Telemetry.** Simulation oracles ($I^*, I_{\text{comp}}, I_{\text{dyn}}, I_M$) ensure determinism but do not replace incident logs or chaos tests; validating topological cascades against production outages is necessary. **Model Selection and Incremental Caching.** Early stopping uses an inner validation split; held-out scenario validation is a prioritized extension. Prediction dispersion fails as an out-of-distribution fallback signal (§7.2.1). Practical CI deployment requires incremental graph caching over PR diffs. **Future Directions.** Key extensions include: (1) modeling hybrid distributed architectures (e.g., synchronous REST/gRPC frontends feeding asynchronous Kafka pipelines) by conditioning edge directional semantics on synchrony (`SYNCHRONOUS_CALL` with backward timeout cascading vs. `PUBLISH_SUBSCRIBE` with forward starvation); (2) modeling distributed LLM serving backbones (vLLM, DeepSpeed); (3) measuring hardware energy via RAPL/NVML in joules, replacing the bounded estimate of §8.2; (4) retargeting the RQ1 and RQ2 contrasts on $I_{\text{dyn}}$, whose queueing structure is not recoverable in closed form from the input graph, so that the comparison tests graph learning rather than the recovery of a topological functional; (5) separating whether $w(e)$ carries contract semantics or acts as a traffic proxy, by holding the declared QoS triple fixed while varying payload size and publication frequency and scoring `Topo-QoS` against a topology-only relabelling of the oracle; (6) reproducing a published learned-criticality baseline; and (7) advancing to prescriptive synthesis generating pull requests with circuit breakers.
# 8. Discussion, Threats to Validity, and Limitations

## 8.1 Discussion and Practical Consequences

#### When to use Topo-QoS, and when to use HGT-QoS

The results do not clearly favor the learned model over the closed-form alternative. Instead, we outline the trade-offs using actual measurements rather than relying on theory.

1.  **Training-free ranking (`Topo-QoS`).** The `Topo-QoS` method does not require model training, storing checkpoints, or retraining. It achieves $\rho = 0.553$ in zero-shot tests across twelve synthetic architectures and $0.526$ across five open-source systems. Learned models do not show a statistically significant improvement in ranking performance ($+0.085$, $p = 0.151$, with the confidence interval including zero; and $0.888$ versus $0.649$ in favor of the baseline on Cloud Microservices). As a result, `Topo-QoS` is a reliable default for scalar criticality. **One learned mechanism, not two (`GAT-N-QoS` or `HGT`).** Using either relation typing or a QoS edge channel alone leads to clear improvements over an untyped, unweighted model ($+0.234$ and $+0.287$, respectively; Holm-corrected $p \le 0.0015$). Combining both adds little extra benefit. Untyped QoS-weighted graph neural networks (GNNs) are more efficient, reaching $\rho = 0.604$ with $28{,}168$ parameters, compared to `HGT-QoS`’s $0.638$ with $434{,}620$ parameters. In contrast, unweighted homogeneous models (`GAT-N`, $\rho = 0.317$) perform worse than training-free heuristics, showing that GNNs without relational signals are not effective for this task.

3.  **Capabilities without a closed-form counterpart.** Some features are not possible with closed-form methods. Typed relational attention can identify which channels mediate cascades (see Supplementary §S8), and edge-level criticality ($I_{\text{edge}}$, Eq. 9) helps assess individual dependencies for placing circuit breakers. These features support using typed models when extra computational cost is acceptable.

#### Dual-Engine Consensus Protocol

An earlier version of this study suggested using an automated fallback based on prediction dispersion $\hat{\sigma}$. However, this approach did not hold up: $\hat{\sigma}$ actually correlates negatively with the margin over `Topo-QoS` at $\rho_s = -0.126$ (§7.2.1), so we removed that recommendation. Now, since both engines run quickly, SaG uses a dual-function (`–predictor-mode dual`) scoring manifest that runs `HGT-QoS` and `Topo-QoS` simultaneously. This method flags unanimous top-$K$ components for immediate action and highlights major ranking differences for human review.

#### Role of the Explanation Layer

The RM attribution profile ($Q(v)$, §5) gives clear, standards-based architectural diagnostics following ISO/IEC 25010. It separates single-point-of-failure risks (Availability) from wider fault propagation (Fault Tolerance), helping teams decide if a component needs replication or decoupling. Numeric rankers and simulation oracles do not offer this kind of practical guidance.

## 8.2 Performance and Computational Sustainability Implications

#### What sustainability means for a pre-deployment gate

Green software engineering considers energy use during development, testing, and running software [29, 83, 84, 85, 86, 30, 31]. Chaos engineering and fault injection tests need many cluster-hours and extra resources like virtual machines and network emulators. Pre-deployment static analysis avoids the high carbon and financial costs of setting up cloud staging clusters and live chaos tests. Still, measuring exact energy savings needs hardware-based measurements [30].

#### The efficiency claim we withdraw, and where the cost actually sits

We are no longer claiming an efficiency advantage. The pipeline uses computing resources both on developer machines and in continuous integration (CI) systems. Static analysis does not lower CPU use compared to simulation; for example, checking system connectivity ($82.7\,\text{s}$ on Enterprise) is about eleven times slower than a breadth-first search (BFS) cascade ($7.2\,\text{s}$). We do not make any broad claims about computational effectiveness compared to simulation. Most of the computing cost comes from calculating CDI for all connected nodes, not just articulation points, to avoid skewed Availability scores. In CI, sustainability comes from deterministic graph caching. By saving base graph metrics across git commits and re-extracting features only for pull-request changes, the gating step becomes a fast neural forward pass ($56\,\text{ms}$). So, static gate sustainability depends on improving graph algorithms and caching, not on machine-learning overhead.

## 8.3 Threats to Validity

#### Construct Validity

Ground-truth impact $I^*(v)$ comes from discrete-event cascade simulations on structural models, not from real outages. While $I^*$ matches dynamic queue flow $I_{\text{dyn}}$ fairly well ($\rho = 0.620$ compared to a $0.811$–$1.000$ test–retest ceiling, see Supplementary §S9), top-$K$ Jaccard scores are only $0.27$–$0.37$ because of non-linear thresholds. Also, $I^*(v)$ can be recovered at $\rho = 0.965$ using only topology, which shows it reflects reachability more than dynamic buffer drops. We have not tested any oracle against real incident logs, which is the main limitation here.

#### Internal Validity

Feature leakage is avoided by keeping graphs separate: predictors use $G_{\text{analysis}}$, while simulation oracles use $G_{\text{structural}}$ (as checked in CI). We keep things fair by matching training sets and depths, and by using early stopping. However, differences in capacity ($434{,}620$ vs. $28{,}168$) and orientation are still unresolved issues (§8.4). The QoS schema uses six active dimensions, with one extra reserved for future use.

#### External Validity

The evaluation includes twelve synthetic scenarios and five open-source systems. Zero-shot transfer does not generalize well to active components (mean $\rho_{>0} = +0.265$), and even reverses on microservice call trees (§7.4.1). As Zhou et al. [45] note, microservices cascade backward through call trees due to RPC timeouts and retries, while pub-sub cascades move forward because of message starvation. GNNs need to account for communication synchrony. Handling more than 2,000 nodes requires incremental graph caching or mini-batching (GraphSAINT [87]).

#### Conclusion Validity

We evaluate heavy-tailed models using non-parametric correlations (Spearman $\rho$, Kendall $\tau$), bootstrap confidence intervals ($B = 2{,}000$), and Wilcoxon signed-rank tests. All analyses are carefully stratified to avoid Simpson’s paradox (pooled $\rho = 0.098$ vs. per-type $0.119$–$0.566$). Metrics that exclude zeros help separate ranking from inertness detection. Folds use ten shared training graphs, and synthetic graphs come from one generator family, which limits how broadly results can be applied.

## 8.4 Limitations and Future Work

#### Correction of the Real-World Baseline

Earlier versions left out `Topo-QoS` from Table 8, thinking it was because open-source adapters lacked QoS contracts. But all five adapters actually declare QoS parameters. The real reason was that we calculated betweenness on the raw multigraph instead of the `DEPENDS_ON` projection. After fixing this, `Topo-QoS` is now included for all systems.

#### Explanation Layer Validation

SaG distinguishes Availability from Fault Tolerance, but no human studies yet confirm whether this helps practitioners. Also, the AHP weights used for ranking perform worse than a uniform prior (§7.3). Future work intends to test counterfactual mutations and conduct user studies.

#### Uncontrolled Confounds in Typing

Table 7 keeps substrate, training set, depth, and early stopping the same, but the parameter budget ($434{,}620$ vs. $28{,}168$) and reverse message-passing directionality ($103{,}725$ parameters in `HGTConv`) do not match. Since $I^*(v)$ measures downstream reachability, upstream visibility gives an advantage that is not related to typing. Three control variants are registered in the SaG benchmark suite (`saag/evaluation/variant_registry.py`): `GAT-N-C` (homogeneous baseline with about $434\text{k}$ parameters), `GAT-N-QoS-C` (homogeneous with QoS edge encoding and matched capacity), and `HGT-QoS-U` (unidirectional HGT with only forward message passing). Running these controls across all twelve LOSO folds is the main empirical goal for the next benchmarks.

#### Model Selection and Caching

Early stopping uses an inner validation split on the main graph, and validating on held-out scenarios is a key next step. Prediction dispersion does not reliably indicate when to fall back to out-of-distribution handling (§7.2.1). For production, incremental graph caching over pull request changes is needed to spread out the cost of $O(|V|^2 + |V||E|)$ feature extraction.

#### Future Directions: Distributed AI, Power Testbeds, and Self-Healing

Key following steps are: (1) modeling distributed large language model (LLM) serving systems like vLLM and DeepSpeed; (2) directly measuring hardware energy use with RAPL/NVML to compare static gating and live chaos sweeps in joules; and (3) moving from predictive diagnostics to prescriptive actions, such as generating automated pull requests with circuit breakers and broker replicas.
