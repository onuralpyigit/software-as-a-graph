# 2. Related Work

## 2.1 Dependability Analysis of Distributed Systems

Runtime approaches to dependability, such as broker clustering, backpressure, autoscaling, failover and chaos engineering [18], require a running cluster, can disrupt service, and consume substantial compute. That compute is itself an acute concern of green software engineering and Green AI [21, 29, 22, 23], where the carbon footprint of provisioning massive execution clusters in continuous integration creates strong incentives for lightweight, energy-efficient static alternatives. Pre-production alternatives, including service-level fault injection testing [19] and microservice dependency localization via PageRank (MicroRank [20]), provide lighter options before deployment. Benchmark systems with cataloged, replayable faults, such as Train-Ticket [30], make observed failure impact measurable on a running deployment, which is the validation this study does not yet have (§7.4). Architecture-based reliability prediction has a long history. Yacoub and Ammar’s methodology for architecture-level reliability risk analysis [31] pioneered combining component dependency graphs with complexity and failure severity to rank components by risk. Cheung’s absorbing Markov chain [32] and the state-, path- and additive models surveyed by Goseva-Popstojanova and Trivedi [33] and Immonen and Niemelä [34] are classic examples, as are the Palladio Component Model [35], layered queueing networks [36] and the AADL Error Model Annex [37]. These approaches answer broader questions but need operational profiles and failure rates that are unavailable at commit time. SaG asks a narrower question from manifests alone: whose failure reaches furthest in the declared topology?

Telemetry-driven methods diagnose faults in running microservices. Examples are Seer [38] and Sage [39], MicroRCA [40], TraceRCA [41], and GNN-based DeepTraLog [42], Eadro [43] and MicroCause [44] (reviewed in [45]). In synchronous microservices, cascades stem from thread-pool exhaustion, RPC timeouts and retry storms [46]. In pub-sub systems they spread through queue saturation and message starvation. All of these methods need traces or metrics from a live system; SaG works before any code runs. SaG’s question is also that of change impact analysis [47] and of dependency management in microservice fleets [48]. Ranking by impact relates to learning-to-rank defect prediction [49], which optimizes the ranking measure directly, as our listwise loss does (§4.2).

## 2.2 Static Code Analysis and Static System Analysis

Static code analysis (SCA) tools such as SonarQube [16] measure complexity [50], cohesion and coupling [17, 51] within individual services to flag defect-prone modules [52, 53, 54, 55]. Comparing sophisticated graph measures against simple structural metrics has a rich history in software engineering defect prediction: Zimmermann and Nagappan [56] evaluated network analysis on dependency graphs, while Premraj and Herzig’s replication study [57] demonstrated that simple code and coupling metrics largely matched network measures. SCA cannot see inter-service messaging, broker saturation or cross-host propagation. Architecture recovery tools reconstruct system-level structure from code [58, 59], and HAROS [60] checks ROS systems statically before launch. SaG’s static system analysis (SSA) uses the declared topology instead, propagating code-level metrics across architectural dependencies. Architecture-level coupling metrics count a service’s consumers, as afferent coupling [26], the Absolute Importance of the Service [27] and service fan-in [61]. In publish–subscribe systems these counts are not a single edge lookup, because consumers reach producers only through topics, brokers and shared libraries. They are a typed two-hop query (publisher $\to$ topic $\leftarrow$ subscriber), which SaG’s dependency rules state explicitly; Because this count is exactly the first propagation wave of the reachability oracle used here, this paper reports it as a reference that restates the oracle, not as a predictor (§4.4). This lets teams find structural anti-patterns [62, 63] and architectural technical debt [64] in CI/CD [65, 66].

## 2.3 Multi-Criteria Weighting

Aggregating QoS policies or failure effects into one auditable weight is a multi-criteria decision problem, for which the Analytic Hierarchy Process (AHP) [67] is standard; SaG uses it for the topic weights of §3.2 and the composite oracle of §4.3. AHP’s consistency ratio detects inconsistent judgments but not matrices back-filled from a chosen answer, a distinction this study reports for its weights (Supplementary §S4).

## 2.4 Graph Learning and Explainability

Closed-form indices [24, 25, 68, 69], one of which supplies this study’s training-free baseline, and cascade models of network robustness [10, 8, 9] assume homogeneous, usually undirected graphs, so a single untyped score conflates structurally different elements such as topics, libraries and hosts. Learned node-importance methods, including FINDER [70], DrBC [71] and PowerGraph [72], share the homogeneity assumption, as does learned approximation of betweenness and closeness [73]. Homogeneous GNNs (GCN [74], GraphSAGE [75], GAT [76]) discard relation identity unless it is supplied as a feature. Softmax attention normalizes over neighbors and so computes a weighted mean that cannot count them, whereas sum aggregation can [77, 78], and counting larger substructures is beyond many message-passing architectures [79]; since the strongest reference here is a neighbor count, this distinction matters (§6.2). Heterogeneous GNNs (RGCN [80], HAN [81], HGT [82], MAGNN [83]) learn relation-specific transformations. We evaluate both families under matched capacity (§6.2). Khodabandeh et al. [84] apply graph attention to microservice call graphs to predict future interactions. We instead predict the impact of removing a node from a declared topology. GNN explainers such as GNNExplainer [85] and PGExplainer [86] explain models in terms of their internal features. SaG’s proposed explanation layer (Supplementary §S24) instead names ISO/IEC 25010 quality sub-characteristics [87] and a remediation class for each flagged component; it is not evaluated here.

This study belongs with work showing that simple baselines are often competitive with sophisticated learners [88, 89, 90, 91], and, in software engineering specifically, with the finding that network measures on dependency graphs [56] add little over simple coupling metrics once those are measured [57]. Its contribution is of that kind: an evaluation of learning on derived dependency graphs for a pre-deployment ranking task, with a largely negative result where the oracle is cheap and its strongest simple restatement is a known architecture metric, and a positive one for learned surrogates where the oracle is expensive.
