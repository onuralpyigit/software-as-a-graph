Mini-ATM Testbed Run

The simulators grade themselves against quantities the framework computes. The testbed produces something independent: the same scenario running as real processes in containers, talking over real DDS, with a real fault injected. This page follows two such runs of the 15-component mini-ATM system and sets each beside the simulator's version of the same run.

How it works

From a scenario file to a fidelity report in five commands

1 · BUILDDeployment planHosts, residents, topic QoS, each app's trigger policy and service time. Writes a Dockerfile and a compose file.testbed build --input mini_atm.json --duration 40 --qos-semantics dds
2 · RUNContainers and chaosOne container per host. Stub applications publish and consume over Cyclone DDS while the orchestrator applies the faults on schedule.testbed run --faults faults.json --mode docker
3 · RECORDTelemetryEvery publish, delivery and DDS status change is written as an OpenTelemetry-shaped event, one file per host.telemetry/N1.jsonl, N2.jsonl
4 · CALIBRATEFit parametersTopic rates, service-time distributions and trigger policies are fitted from the steady state before the fault.testbed calibrate
5 · COMPAREFidelityThe simulator runs the same scenario, faults and duration. The two traces are compared. A report, never a gate.testbed fidelity [--calibrated]
What gets built

Two containers, six stub applications, two broker relays

DDS has no broker, so each broker is emulated as a relay: writers publish to an ingress partition and the routing relay republishes to the egress partition that readers use. That makes a broker outage real. tracks has two relays; the lowest-id relay with a live heartbeat does the routing.

    Fidelity

    How closely did the simulator match?

    Steady state is compared over the window before the fault, after a 2 s warm-up. Errors are relative, per topic or per reader. The second pair of columns repeats the comparison with the simulator fed the parameters fitted from this run's own telemetry.

    Calibration

    What the telemetry gives back

    The calibrator sees only the trace. Here it is checked against the values the deployment plan declared, which the stub applications were actually running with.
