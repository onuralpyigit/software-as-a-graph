Mini-ATM Testbed Run

The Failure Lab asks four simulators what happens when one component of the 15-component mini-ATM system fails. This page asks the same question of something independent: the scenario running as real processes in containers, talking over real DDS, with the failure actually injected. Pick a component and the page sets the lab's predictions beside what the containers did. Pick one of the nine incidents (a slowdown, dropped or flooded messages, a flapping link, a hang, two failures at once, a reboot, a rolling restart) and it sets the simulator's version of the incident beside the real one.

How it works

From a scenario file to a fidelity report in five commands

1 · BUILDDeployment planHosts, residents, topic QoS, each app's trigger policy and service time. Writes a Dockerfile and a compose file.testbed build --input mini_atm.json --duration 40 --qos-semantics dds
2 · RUNContainers and chaosOne container per host. Stub applications publish and consume over Cyclone DDS while the orchestrator applies the fault on schedule.testbed run --faults faults.json --mode docker
3 · RECORDTelemetryEvery publish, delivery and DDS status change is written as an OpenTelemetry-shaped event, one file per host.telemetry/N1.jsonl, N2.jsonl
4 · CALIBRATEFit parametersTopic rates, service-time distributions and trigger policies are fitted from the steady state before the fault.testbed calibrate
5 · COMPAREFidelityMessageFlowSimulator runs the same scenario, fault and duration. The two traces are compared. A report, never a gate.testbed fidelity [--calibrated]
What gets built

Two containers, six stub applications, two broker relays

DDS has no broker, so each broker is emulated as a relay: writers publish to an ingress partition and the routing relay republishes to the egress partition that readers use. That makes a broker outage real. tracks has two relays; the lowest-id relay with a live heartbeat does the routing.

    What these runs do and do not show

      How this was produced. python cli/simulate_graph.py testbed build | run | calibrate | fidelity on examples/mini_atm.json, 40 s per run, seed 0, Docker mode with Cyclone DDS 11.0.1, DDS QoS semantics. One run per failed component. The simulated traces come from saag.testbed.orchestrate.simulate_like, the function the fidelity command uses.
