Deployment Walkthrough

The method works on an architecture before it runs. This page follows one system across that line. Before deployment, it decides where each component should run and is honest about what that buys. After deployment, it measures the running system and checks its own predictions against it.

Before · 1 · the question

Eight components, four hosts, two racks: where should everything run?

The topology says what talks to what. A deployment spec adds what the topology cannot know: how much each host holds, how often hosts and whole racks fail, which components need a standby, and that replicas must sit in different racks.

Before · 2 · candidates

An exact optimizer trades cross-host traffic against a first-order estimate of blast radius. That estimate is a proxy, so every candidate, and five simple baselines, is re-scored on a different instrument: the failure simulator, run over every host and rack outage. After · 5 · measure it

The parameters that were guessed before deployment can now be measured

Before deployment, rates, service times and trigger behaviour are declared or assumed. A running system emits telemetry from which they can be fitted, and the simulator can be compared with what actually happened.
